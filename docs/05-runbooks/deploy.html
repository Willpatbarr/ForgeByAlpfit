Deploy

What this is: how a change actually reaches production today, across three paths — web (live), Firestore rules (the security boundary), and Android (blocked) — plus docs, which deploy separately.

1. Web app → Firebase Hosting DECIDED

This is the live deploy path today. firebase.json points hosting.public at build/web, so the build output has to exist before you deploy it.

  1. Build the web release from the app root (forge_senior_project_version/). 
    cd forge_senior_project_version
flutter build web
  2. Deploy only the hosting target — do not run a bare firebase deploy, which would also attempt rules/indexes. 
    firebase deploy --only hosting
  3. Verify: open the hosting URL Firebase prints and confirm the deployed build reflects your change (hard-refresh to bypass cache).

Web is unbranded today — web/index.html still carries Flutter's default title/description. That is a known gap, not a deploy-step problem — see the decision brief's Milestone 2.

2. Firestore rules & indexes CONFLICT

Rules are the actual security boundary for this app — not the committed config files (see local-setup.html). Deploying rules is not routine busywork; treat it with the same care as a production database migration.

CommandDeploys
firebase deploy --only firestore:rulesfirestore.rules — the actual security boundary.
firebase deploy --only firestore:indexesfirestore.indexes.json — composite index definitions.
Known open hole, being fixed in Milestone 1. The current deployed rules allow allow read: if true; on the entire users collection — every user's email and contactInfo is world-readable by anyone with the web API key today. Do not treat the current rules as a safe baseline to copy from; Milestone 1 splits public-safe fields from gated ones.
Do not deploy from FIRESTORE_RULES_SETUP.md. That file, in the repo root, contains a stale copy of the rules — it is missing the DM-thread rules, several users update branches, and the goals/plans subcollection rules that exist in the real, deployed firestore.rules. Copying rules from that doc and deploying them would silently reopen security holes already closed in the live rules file. It is slated for deletion in Milestone 0 — until then, treat it as poison, not reference material.

The only trustworthy source for current rules is forge_senior_project_version/firestore.rules itself, read directly.

3. Android → Play Console internal testing DEFERRED — blocked until Milestone 2

  1. Build the app bundle. 
    flutter build appbundle
  2. Upload the resulting .aab to Google Play Console, internal testing track.
Blocked today. The Android applicationId is still the Flutter scaffold default com.example.forge_senior_project_version (android/app/build.gradle.kts). Play Console will not accept a com.example.* application id for any real submission. Fixing this requires re-registering the Firebase Android app under a real id and regenerating google-services.json — scoped as Milestone 2, not a same-day fix.

Docs site — deploys separately

This docs/ folder is not part of either deploy path above. It builds and deploys on its own via Cloudflare Pages on every push to the repo — see cloudflare-pages.html for the full setup. Firebase Hosting stays scoped to the app; Cloudflare Pages is for docs.

No CI — a deliberate deferral

There is no GitHub Actions workflow, no Codemagic config, nothing. Every deploy path above is run by hand, on William's own machine, when he decides to run it.

This is a stated deferral, not an oversight — per the decision brief's rejected-services table, CI is adopted when a second developer joins or the first broken build reaches a tester, whichever comes first. Until then, the pre-deploy checklist below is the only safety net.

Pre-deploy checklist

  • flutter analyze comes back clean, or any warnings are understood and intentional.
  • You ran the app locally against production Firestore and confirmed the change works end to end (see local-setup.html — there is no emulator, so this is the only real check).
  • If the change touches firestore.rules: you read the rule diff line by line against the current deployed file, not against FIRESTORE_RULES_SETUP.md.
  • If the change touches firestore.rules: you deployed firestore:rules alone first and re-tested before also shipping a hosting build that depends on the new rule shape.
  • For a web deploy: you ran flutter build web immediately before firebase deploy --only hosting, so the deployed bundle matches your current branch.
  • You know which of the three paths (web / rules / Android) you're actually deploying — never run a bare firebase deploy that could touch more than intended.

What To Do Next

  1. For a normal feature or UI change: flutter build web then firebase deploy --only hosting.
  2. For a rules change: read the current firestore.rules directly, never FIRESTORE_RULES_SETUP.md, and deploy firestore:rules on its own.
  3. Do not attempt an Android release build until Milestone 2's bundle-id fix lands.
