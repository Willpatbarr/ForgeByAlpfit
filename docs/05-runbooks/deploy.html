Deploy

How to deploy the docs site, Firebase rules, and mobile app.

What can deploy today

Nothing can reach either app store until Milestone 3 is done. Three hard blockers, all present right now: bundle IDs are com.example.* on both platforms (neither store accepts that), release builds are signed with the debug keystore, and there is no Apple Developer or Google Play account. Sections 3, 4 and 5 below are written so they're ready — they are not runnable yet.

1. The docs site → Cloudflare Pages

Push to main, Cloudflare Pages builds docs/, the site is live. That's the whole pipeline — static HTML, no build step, no framework.

One-time setup T1

  1. Create a Cloudflare account (free) and open Workers & Pages → Create → Pages → Connect to Git.
  2. Authorise the GitHub app for the ForgeByAlpfit repository only. Not the whole account.
  3. Set the build configuration. This is the step people get wrong — the docs are in a subdirectory of an app repo, not at the root:
    FieldValue
    Production branchmain
    Framework presetNone
    Build command(leave empty)
    Build output directorydocs
    Root directory(leave as repo root)
  4. Deploy. Cloudflare gives you a *.pages.dev URL.
    Verify: open the URL and confirm you land on the docs hub with the stylesheet applied. A page that renders unstyled means the CSS path resolved wrong — check that docs/index.html links assets/forge.css and the section pages link ../assets/forge.css.
  5. Full detail, including custom domain and what to do about preview deployments: cloudflare-pages.html.

Every time after that

  1. Edit HTML under docs/.
  2. Open the file locally in a browser to check it renders. There is no build to run.
  3. Commit and push to main.
  4. Cloudflare builds automatically, typically in under a minute.
    Verify: hard-refresh the live URL and confirm your change is there. If it isn't, check the Pages deployment log before touching anything else.
Why Cloudflare and not Firebase Hosting — even though Hosting is already configured. D9 DECIDED: consistency with William's other projects. The hosting block in firebase.json points at build/web, which is a Flutter web build, not this docs site — they were never the same thing.

2. Firestore rules — the deploy everyone forgets

Rules are a separate deploy from everything else. Editing firestore.rules and pushing to GitHub changes nothing in production. Nothing takes effect until you run the command below. This is the single most forgettable step in the whole project — and it is the one that gates access to every user's data.
  1. Authenticate the CLI once per machine.
    firebase login
  2. Move to the app directory — firebase.json lives there, not at the repo root.
    cd forge_senior_project_version  # or: cd app
  3. Confirm you're pointed at the right project.
    firebase use
    Must be forge-by-alpfit. There is only one project — no staging environment exists, so a rules deploy is a production deploy.
  4. Deploy the rules.
    firebase deploy --only firestore:rules
  5. Deploy the indexes when you've added a query.
    firebase deploy --only firestore:indexes
    Firestore will demand an index at runtime if you forget; the error message in the console contains a one-click creation URL. Note that plans queried by name + updatedAt currently has no declared index — that query will ask for one the first time it runs.
  6. Deploy Storage rules separately if you changed them.
    firebase deploy --only storage
  7. Verify in the console, not in the terminal. Open Firebase console → Firestore → Rules and confirm the published ruleset text matches the file you just deployed. Then use the Rules Playground to run one denial you expect — e.g. an unauthenticated read of a users/ document.
    Verified when: the playground denies the read you expect it to deny. A successful CLI deploy only proves the syntax parsed.
Do not deploy rules copied from FIRESTORE_RULES_SETUP.md. That file in $APP/ holds a stale copy of the rules — it is missing the DM-thread rules, several users update branches, and the goals/plans subcollection rules that exist in the real firestore.rules. Deploying from it would silently reopen holes already closed. It is slated for deletion in M2. Until then treat it as poison, not reference material. The file $APP/firestore.rules is the only source of truth.
The currently deployed rules have a known hole. allow read: if true on /users/{userId} makes every user's email and contact info world-readable, unauthenticated. Do not treat the live ruleset as a safe baseline to copy from. Fixing it is the first issue in Milestone 1.

3. The app → TestFlight (iOS) Blocked until M3

Prerequisites, all in M3: a real bundle ID, an Apple Developer Program membership ($99/yr), the Firebase iOS app re-registered under the new ID, and a signing certificate + provisioning profile. Detail: apple-developer.html.

  1. Do the release checklist first. Every item, every time.
  2. Build the release archive.
    cd $APP && flutter build ipa --release
    This produces an .xcarchive and, if signing is configured in Xcode, an .ipa under build/ios/ipa/.
  3. Upload. Either xcrun altool/notarytool, or open the archive in Xcode Organizer and use Distribute App → App Store Connect. Xcode Organizer is the boring, well-documented path — use it.
  4. Wait for processing in App Store Connect. Usually minutes; occasionally an hour. You'll get an email if it fails processing.
  5. Answer export compliance. The app uses HTTPS only, which is standard-encryption-exempt, but you still have to answer the question before the build is testable.
  6. Add the build to a TestFlight group and invite testers by email. Internal testers (up to 100, on your team) need no review. External testers require a Beta App Review — budget a day.
    Verified when: a device that is not William's has installed from TestFlight and signed in successfully.

4. The app → Play internal testing (Android) Blocked until M3

Prerequisites, all in M3: a real applicationId (Play rejects com.example.* outright), a Google Play Console account ($25 one-time), a real upload keystore, and pinned minSdk/targetSdk. Detail: google-play.html.

  1. Do the release checklist.
  2. Confirm you are not debug-signing. Open $APP/android/app/build.gradle.kts and confirm the release build type no longer uses signingConfigs.getByName("debug"). Today it does. A debug-signed AAB cannot be uploaded, and the failure message is unhelpful.
  3. Build the app bundle.
    cd $APP && flutter build appbundle --release
    Output: build/app/outputs/bundle/release/app-release.aab.
  4. Upload to Play Console → Testing → Internal testing → Create new release. Internal testing has no review delay and allows up to 100 testers.
  5. Add testers by email list and share the opt-in link.
    Verified when: a device that is not William's has installed from the internal testing track and signed in successfully.
  6. Store the keystore somewhere that survives losing the laptop. Losing the upload key is recoverable via Play App Signing key reset; losing it without Play App Signing enabled is not. Enable Play App Signing.

5. Promoting to production

Only after the Rec Center beta has run and M4's legal surface exists. A public store listing for a UGC social app without account deletion, report/block, and a privacy policy will be rejected — and should be.

PlatformPathReview timeRollback
iOSApp Store Connect → select the TestFlight build → submit for App Review~1–3 days, first submission usually longerNo true rollback. You submit a new build. Use phased release so you can pause it.
AndroidPlay Console → promote the internal testing release to ProductionHours to daysHalt the staged rollout, then promote a fixed build. Halting is instant; the fix is not.
Use staged rollout on Android and phased release on iOS. With one developer and no on-call, the ability to stop a bad release at 10% of users is the only incident response you have.

Release checklist

Run this before every app build that leaves your machine. It is short on purpose.

  • Version bump. Increment version: in $APP/pubspec.yaml. It currently reads 0.1.0 with no build number — both stores require a monotonically increasing build number, so move to the x.y.z+n form and bump n on every upload, without exception.
  • Tests pass. flutter test exits 0. (Before M1 this is vacuous — there are no tests.)
  • Analyzer clean. flutter analyze with strict-casts on. Before M1 turns it on, a clean analyze means nothing.
  • Rules are deployed and match the repo. An app build that expects tightened rules against a project still running the old ones fails in ways that look like app bugs. Deploy the rules first, app second.
  • Indexes are deployed if you added or changed a query.
  • Signing is real. iOS: a distribution certificate, not automatic-debug. Android: the upload keystore, not signingConfigs.debug.
  • Changelog written. One paragraph of what changed, in the TestFlight "What to Test" field and the Play release notes. Testers who don't know what changed test nothing.
  • Smoke test the release build on a real device before uploading: sign in, view the feed, create an event, force-quit, reopen, confirm the event survived.
  • Crashlytics is receiving. After the first install of a new build, confirm the version appears in the Crashlytics console — otherwise a crash from this build reports nowhere. See crashlytics.html.

When a build is rejected

RejectionWhat it actually meansWhat to do
App Store Guideline 5.1.1(v) — account deletionNo in-app account deletionNot appealable — M4
App Store Guideline 1.2 — UGC safetyNo report, block or content removalNot appealable — M4
Missing privacy policy URLRequired before a listing can publishM4 — host it on Cloudflare Pages
Invalid bundle ID / package namecom.example.* is reserved scaffold namespaceM3 — then re-register the Firebase apps
"You uploaded a debuggable APK or Android App Bundle"Release build used the debug signing configM3 — real keystore
Missing purpose strings / privacy manifestiOS usage descriptions — Forge already has bothCheck the Firebase SDK privacy manifests
Metadata rejection (screenshots, description, age rating)The listing, not the binaryFix in the console and resubmit — no new build
Anything else—Do exactly what the reviewer note says
  • Guideline 5.1.1(v) — any app with account creation must let a user delete their account from inside the app. Forge's rules currently deny user-doc delete outright. Build the deletion flow in M4.
  • Guideline 1.2 — user-generated content needs a report mechanism, a block mechanism, and a way to remove content. moderation_service.dart is a 0-byte file.
  • Privacy policy URL — both stores require one before the listing can be published. Host it on the Cloudflare Pages site you already have.
  • Bundle ID / package name — changing it means re-registering the Firebase apps. Do it once, deliberately.
  • Purpose strings — iOS needs usage descriptions for camera and photo library. Forge already has both, correctly — the one platform thing done right. If it still trips, check the privacy manifest requirements for the Firebase SDKs in the current Xcode version.
  • Metadata — fix in App Store Connect / Play Console and resubmit; no new build needed. Answer the age-rating questionnaire honestly — social features and UGC raise the rating.
  • Anything else — read the actual reviewer note, fix exactly what it says, resubmit. Do not bundle unrelated changes into a resubmission — it makes the next rejection harder to diagnose.

CI — the guardrail, and nothing more

CI should verify that the project builds and its tests pass.
In scope, when CI existsDeliberately out of scope
flutter pub getAutomated store uploads (Fastlane, Codemagic)
flutter analyze with strict-castsCoverage thresholds and coverage badges
flutter testRequired reviewers, PR templates, branch protection ceremony
Build the Android debug APK to prove it compilesNightly builds, matrix builds, integration-test farms

When to add it: not yet. CI is deferred with two triggers — a second developer joins, or a broken build reaches a tester. Until one of those fires, running two commands before you push is the same guardrail with none of the maintenance. Revisit at github.html.

What To Do Next

  1. Set up Cloudflare Pages for the docs site — it's the only deploy on this page that is unblocked, it takes about ten minutes, and it makes everything else here readable from a phone. Section 1.
  2. Before touching any app build, finish M1 and deploy the fixed rules using section 2 — the rules deploy is separate and is the one that gets forgotten.
  3. Do not pay for an Apple or Google account until M3 starts. Sections 3, 4 and 5 are unreachable before then by design.
