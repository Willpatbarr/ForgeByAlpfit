Onboarding a Second Person

What this is: what someone other than William needs on day one — reading order, access, a first task, and the four things in this repo that will actively mislead them. Short on purpose.

Why this page is short

There is no second person, and there may never be one. Per D6, Forge is a solo project with real external users as the target — a teammate is a "maybe," not a plan. This page exists so that if someone shows up, half a day isn't lost to orientation. It is deliberately not a handbook. Don't grow it until a real person is actually reading it.

The same page is useful for one other case: William coming back to this repo after three months away. The landmines section in particular is written for that.

Day one, in order

  1. Read pages 1–4 of the reading order. Fifteen minutes. Do not skip to the code.
  2. Get GitHub and Firebase access. Everything else can wait.
  3. Follow local-setup.html end to end, including all four verification checks. Don't stop at "it compiled."
    Done when: you registered a throwaway account, created an event, force-quit the app, reopened it, and the event was still there.
  4. Read the landmines below. This is the section that saves you a wasted afternoon.
  5. Take the first task.

Their first useful task

Write the Firestore rules test that proves /users is closed

From Milestone 1. It's the right first task for four reasons:

  • It is self-contained — the emulator, one rules file, one test file. No need to understand the UI.
  • It forces you to read firestore.rules carefully, which is the highest-leverage 206 lines in the project.
  • It creates the test/ directory, which does not exist. You'll be the person who added testing to this project, which is worth more than any feature.
  • It fails first. Write the test, watch it pass against today's allow read: if true (proving the harness works), then fix the rule and watch it flip.

If that person is more product than infrastructure, the alternate first task is "Wire the calendar filter popup to real friends, gyms, and self" from M2 — visible, self-contained, and it deletes fake data from a shipping screen.

Landmines — what will actively mislead you

1. Four stale status documents that describe a different app

These live in forge_senior_project_version/ (app/ after D7). All four were written in February 2026 and never touched again, while roughly the entire build happened after them. Do not read them as documentation. They are conversation transcripts frozen mid-session.

  • PROJECT_STATUS.md — calls the app "Production-Ready Core" and lists auth_service.dart and search_service.dart as empty. Both are fully implemented. Its own file counts contradict its own lists. The single most misleading file in the repo.
  • PROJECT_SUMMARY.md — lists "service layer", "state management" and "backend integration" as Planned. All three are substantially done. Describes a pre-backend app.
  • ARCHITECTURE_ANALYSIS.md — reports three routing/dependency bugs that were fixed long ago, and recommends a Riverpod migration that was recorded and abandoned. See D5 before acting on it.
  • AUTH_IMPLEMENTATION_CONTEXT.md — says "we are building the login screen", that auth_service.dart is empty, and that main.dart calls signInAnonymously(). Every one of those is obsolete.

A fifth file, FIRESTORE_RULES_SETUP.md, is the only one that was ever updated — and it is worse, because it looks current. It contains a stale copy of the security rules. Deploying from it would reopen closed holes. See the warning in deploy. All five are deleted in M2.

2. Twenty-one zero-byte Dart files

21 of the 58 .dart files in lib/ are 0 bytes — including all of core/errors/, all of core/util/, all of core/constants/ except one, and the entire feed MVVM layer (data/, domain/, presentation/viewmodel/).

The folder tree therefore implies a clean-architecture codebase that does not exist. There are no error types, no validators, no date utilities, no Firestore converters, and no dependency injection. Do not open one of these files and start "finishing" it as if picking up mid-implementation. There is no partial implementation to continue. Four service files are also empty and each represents a missing capability, not a stub: moderation_service.dart, push_service.dart, presence_service.dart, link_preview_service.dart.

3. Screens that look finished and aren't

A grep for TODO across lib/ returns two hits, both in dead code. The incompleteness here is invisible to tooling, which is exactly why it catches people. Assume nothing is real until you've watched it write to Firestore.

4. Three things that are true and sound alarming

  • The user table is world-readable right now. allow read: if true on /users. Don't panic and don't "just fix it" without reading M1 first — several screens read user docs and the fix needs a test around it.
  • Firebase config files are committed to git. That is fine. Firebase client config identifies the project; it is not a credential. Nothing needs rotating. The real exposure is the rules file, not the config. Do not start a key-rotation exercise.
  • flutter analyze is clean and it means nothing. analysis_options.yaml is one line with strict-casts off. Never cite a clean analyze as evidence about this codebase until M1 turns strictness on.

What To Do Next

  1. If you are the new person: read pages 1–4 of the reading order, then run local-setup.html to the end, then take the first task.
  2. If you are William granting access: GitHub collaborator and Firebase Editor first — both are $0 and both unblock everything. Leave the store accounts until M3.
  3. Either way: the fastest permanent fix for landmine #1 is to delete the five stale markdown files. It's an M2 issue and it takes about a minute.
