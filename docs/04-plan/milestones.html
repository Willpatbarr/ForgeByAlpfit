M1 — Lock the doors T1 Before first user

This is the milestone that actually blocks everything. Right now firestore.rules:27 reads allow read: if true on the entire users collection. Every user's email and contact info is readable by anyone with the public web API key — which is committed in lib/firebase_options.dart and extractable from the deployed web bundle. You cannot invite real users onto this until it's closed.

Goal: make the data layer safe for people who are not you.

Definition of done

  • An unauthenticated read of another user's email or contactInfo fails, proven by a written test script rather than by eyeballing.
  • App Check is enforced on Firestore and Storage.
  • The directThreads update rule is constrained to the specific fields the client actually writes.
  • A user can delete their account, and their owned data is gone afterwards.

What's in it

WorkDetail
Split the users read rulePublic-safe fields (displayName, accountType, avatarUrl) stay world-readable because search and friend lists need them. email and contactInfo gate behind owner-or-friend. The data model does not change.
Re-audit the call sites that assumed open readssearch_service.dart, friends_service.dart and gyms_service.dart all currently rely on unrestricted reads. Tightening rules without checking these will break search.
Enable App CheckMonitoring mode first, then enforce. Enforcing before monitoring locks you out of your own app. See the runbook.

M2 — Ship-ready identity T1 Before first user

Goal: make the app something a stranger can legally and technically install.

Definition of done

  • Real bundle IDs on Android and iOS, with Firebase apps re-registered and config regenerated.
  • App name, icon, and web/index.html are branded — no "A new Flutter project."
  • A privacy policy is published at a public URL.
  • An Android internal-testing track is live.
  • A branded web build is deployed and shareable by link.

Do the bundle ID once and deliberately. Both platforms still carry the Flutter scaffold default com.example.*, which Google Play rejects outright. The application id can never be changed after first publish, and changing it now means re-registering the Firebase apps and regenerating google-services.json, GoogleService-Info.plist and firebase_options.dart. Suggested: com.alpfit.forge.

M3 — Rec center beta T1 Before first user

Goal: real people who are not you are using the app. This is the milestone the whole plan is pointed at.

Your Bigger Rec Manager Meeting notes describe exactly this arrangement: a beta group split into "The Gym", who host their own community and use it to communicate news and events, and "The User", who participate in that community.

Definition of done

  • The rec center has a gym account with a live community and at least one channel.
  • The gym-approval workflow for joining a community is specified and built.
  • Minimum moderation exists: report a post, and remove a member.
  • At least five people who are not you have signed up, joined, and posted.
  • A feedback channel exists and you have received feedback through it.

What's in it

WorkDetail
Specify the gym-approval workflowYour spec asserts joining "may be instant or require approval, depending on the gym's configuration" — but this is never specified anywhere and is not built. It needs a gym-side setting, a pending-request state, and a way for the gym to see and act on requests.
Minimum viable moderationToday a gym owner can delete posts and comments. There is no report, mute, or ban. Report plus remove is the floor for a public community.
Gym onboarding flowYour spec flags this as "not fully defined at this time." A gym signing up needs a different path than a member.
Wire the two dead like/comment stubssocial_page.dart:1928 and :1944 are no-op buttons. The functions they need already exist and work in the channel view.
Recruit and onboard testersWeb link is the lowest-friction channel; Android internal testing for anyone who wants the app installed.

M4 — Know when it breaks T2 When it hurts

Goal: stop finding out about bugs by text message. The named threshold for this milestone is exactly that — the first time a tester reports a bug you didn't already know about.

Definition of done

  • A deliberately-thrown test error from a production build appears in the error tracker.
  • Unit tests cover goal period rollover, recurrence expansion, and plan generation.
  • A Firestore export has been run once and the output verified.

What's in it

WorkDetail
Error trackingPROPOSED Sentry over Crashlytics, because the beta runs on web and Crashlytics' Flutter web support is poor. See the runbook.
Tests on the date math onlyGoal period rollover, recurrence expansion, and plan instance generation are the algorithmically dense functions where an off-by-one silently corrupts a user's streak or duplicates calendar events. Everything else is UI glue not worth a harness.
Backup / exportProve you can get your data out before you need to. Also the escape hatch for the highest lock-in service in the stack.

Services: Sentry.

Why this order

Something runnable already exists

The usual reason to sequence carefully — getting to a running app fast — is already satisfied. That frees the sequence to optimize for safety instead.

Security before identity

M1 comes before M2 because there is no point making the app installable while its data layer leaks emails. Getting installed is what creates the exposure.

Identity before beta

M2 before M3 because com.example.* cannot be distributed, and a beta with no privacy policy is a beta you have to redo.

Proposals deferred behind proof

The iOS question sits in M5, behind the beta that answers it. The error-tracker choice sits in M4, after the beta reveals whether the surface is web or mobile.
