M1 — Lock the doors T0 Now L

Close the security holes, fix the one guaranteed crash path, and stand up the first tests — so that everything after this is built on something that can be trusted.
Nothing else ships before this. Today firestore.rules says allow read: if true on /users. Every user's email, contact info, friend list and gym list is readable by anyone with the project id, unauthenticated. That is a privacy incident waiting for its first real user, not a style nit.

Definition of done

  • An unauthenticated client can no longer read any document under /users — verified by a failing-then-passing rules test, not by reading the rules file.
  • A signed-in gym member cannot modify any field of another member's channel post except likeIds — covered by a rules test.
  • A client cannot write accountType: 'gym' onto its own user doc.
  • Every write rule for users, directThreads, goals and plans validates field types and string lengths; timestamps are checked against request.time rather than trusted from the client.
  • Storage rejects an avatar upload over the size cap and rejects a non-image content type; storage-cors.json no longer contains "origin": ["*"].
  • An event saved with no start time either cannot be saved, or renders without throwing — the unchecked as Timestamp cast in events_service._mapDocToEvent is gone.
  • A test/ directory exists, flutter test runs green, and it contains at least: rules tests for every rule changed in this milestone, and unit tests for goal period rollover.
  • analysis_options.yaml enables strict-casts and flutter analyze is clean with that setting on.
  • The tightened rules are actually deployed — firebase deploy --only firestore:rules,storage has been run and the console shows the new ruleset.

Risks — what could make this bigger than it looks

  • Tightening /users breaks screens you didn't expect — Search, friend lists, gym member lists, avatars and the social page all read user docs. The app only reads them while signed in, so an if request.auth != null floor should be invisible — but field-level gating of email/contactInfo is a bigger change and may need a public-safe projection.
  • The rules test harness is new ground — There is no test/ directory at all and no CI. Standing up @firebase/rules-unit-testing against the emulator is its own half-day before the first assertion is written.
  • strict-casts may surface more than the four known casts — The analyzer has been configured to find nothing (flutter_lints only). Turning it on is the first honest measurement of the codebase and the count is genuinely unknown until you run it.
  • Fixing nullable startAt may need a data migration — Events already written without a start time exist in the live project. Deciding between backfill, defaulting, or skipping them is a product call, not just a code change.
  • Rules tests will contradict the app — Expect at least one place where the app already relies on a permission that shouldn't exist. That is the point, but it turns a rules issue into an app issue mid-milestone.

M2 — Make "done" true T0 Now L

Kill every surface that looks finished and isn't, so that "the app works" becomes a true sentence rather than a demo-shaped one.
Why this is a milestone and not polish. A grep for TODO across lib/ returns two hits, both in dead code. The incompleteness here is invisible to tooling — it's hardcoded names in a filter popup, four sections that are const [] by construction, a button whose body is a comment, and an RSVP chip that animates convincingly and writes nothing. These are the first things a beta tester touches.

Definition of done

  • The calendar filter popup lists your real friends and real joined gyms, and unchecking one removes those events from the visible calendar.
  • Tapping an item in the Create hub opens a detail sheet with that item's real data — the string "when connected to your data" does not exist in the repo.
  • Tapping Attend on an event-invite DM, force-quitting the app, and reopening it shows Attend still selected, and the event owner can see the response.
  • Typing a comment in the feed and pressing Done posts it. (Today only the keyboard's submit action posts; Done discards.)
  • A channel post's author can delete their own post and their own comments without being the gym.
  • A profile save that fails shows an error and leaves the form dirty — no catch (_) {} remains in profile_page.dart.
  • Zero 0-byte .dart files remain in lib/: each of the 21 is either implemented or deleted, with the choice recorded.
  • The four stale status markdown files are deleted or replaced with a one-line pointer to this docs site.
  • A workout event saved with per-set reps and weight renders those weights when reopened from the calendar.
  • Editing a goal's name no longer resets currentCheckupsCompleted or clears periodHistory.
  • No screen renders Firebase CLI instructions to an end user.
  • Each fix above has at least one test or one written manual verification step in the issue.

Risks — what could make this bigger than it looks

M4 — Beta-ready T1 Before first user L

Build the things a user-generated-content social app legally and practically needs before strangers touch it — account deletion, moderation, a privacy policy, push, and gym approval.
Two of these are hard App Store blockers, not nice-to-haves. Guideline 5.1.1(v) requires in-app account deletion for any app with account creation — and today firestore.rules explicitly denies user-doc delete. Guideline 1.2 requires a report/block mechanism for user-generated content — and moderation_service.dart is a 0-byte file. Neither one can be argued around in review.

Definition of done

  • A user can delete their account from inside the app, and afterwards: their auth account is gone, their user doc is gone, their events/goals/plans are gone, their DM threads are gone or anonymised, and their avatar is removed from Storage.
  • Any post, comment, DM, or user profile can be reported from the UI, and the report lands somewhere a human will see it.
  • A blocked user's content disappears for the blocker and they cannot start a new DM thread.
  • A gym owner has a screen listing reported content in their community and can remove it.
  • A privacy policy and terms of service exist at public URLs, are linked from the app, and registration requires an explicit consent check.
  • Registration collects or confirms age eligibility.
  • A DM sent to a backgrounded device produces a push notification on both platforms; the same holds for an event invite and a channel post in a joined gym.
  • A user can turn each notification category off, and the setting survives a reinstall.
  • A gym can configure its community as open or approval-required, and an approval-required gym shows pending join requests it can accept or reject.
  • A user who forgot their password can reset it by email without contacting William.

Risks — what could make this bigger than it looks

  • Client-side account deletion cannot delete other people's data — Your uid appears in other users' friendIds, in gym memberUserIds, in DM threads, and as authorUid on posts. Rules currently permit only narrow cross-user diffs. Doing this without Cloud Functions is possible but has to be designed, and Functions requires the Blaze plan — a card on file. This is the single most likely item in the plan to force a service decision you've deferred.
  • FCM on iOS needs an APNs key from the Apple account — Push is blocked on M3 being finished, not just started. An APNs auth key, the push capability, and a real provisioning profile are all prerequisites.
  • "Moderation" is undefined in every source document — Your own notes say community management workflows are "not yet fully defined." Before writing code, write down the smallest version: report → gym owner sees it → gym owner removes it. Resist appeals, bans, and auto-filtering.
  • A privacy policy is a real document about real data — You store emails, contact info, DMs, photos, and gym membership. A template will not accurately describe that without editing. It also has to state the deletion path you just built.
  • Gym approval changes an existing join flow — addGym joins instantly today and only the kick half exists. Adding approval means a pending state that both sides can see, and a rules change that M1 will already have tightened.

M5 — The Rec Center beta T1 Before first user M

Actually run the beta — get real people into a community that isn't empty, keep a feedback channel open, and measure the one metric that says whether the thesis holds.
The cold start is the product risk, not a marketing detail. Forge's value is a populated gym community. The first ten users open the app, see an empty channel, and leave. Nothing in any source document addresses this. Seeding content is a build task in this milestone, not something to improvise on launch day.

Definition of done

  • A brand-new user who installs the app is, within their first session, a member of the BYU-I Rec Center community without having to search for it.
  • The Rec Center community has named channels and at least a week of real posts before the first tester is invited.
  • There is a way to send feedback from inside the app that reaches William without him asking for it.
  • Five or more non-William users have signed up, joined the rec center's community, and posted — and everything they did is still there the next time they open the app. (The success bar from vision.html.)
  • The number above is recorded from actual data, not estimated.
  • A written beta runbook exists covering recruiting, install support, what to do when someone reports a bug, and how the beta ends.
