CSE 499 Requirements
This document contains information for the CSE 499 Requirements Documents.
Initial Requirements
Once your proposal is approved you should be actively building your project.  This will include research, learning, prototyping and development. Do not wait to start learning what you need to to complete your project.  Do not wait to mitigate the risks that you defined in your proposal document.  While you are moving your project forward with active development. you are also gaining a better understanding of what your project really will be by the time it is complete.  You will use these learnings to create an initial requirements document in this format.
Title Page: Project Name. Team Members, Description of project
Section 1: Introduction: Purpose of Project
Section 2a: Must Have Requirements
Create a list of a minimum of six must have functional requirements. For each listed requirement you need to state the success measure including how you will demonstrate that the requirement is completed.  Avoid ambiguity - each requirement is specific to one purpose.
Section 2b: Stretch Requirements
Create a list of a minimum of four stretch functional requirements. For each listed requirement you need to state the success measure including how you will demonstrate that the requirement is completed.  Avoid ambiguity - each requirement is specific to one purpose.

  
Final Requirements Specification
The requirements in the requirements document are the basis of your grade for the senior project. It is very important that you are certain of what you can do by the time you submit your final requirements document.
The requirements should be functional requirements, meaning that you can demonstrate that the requirement is met by running the solution, and not by having to look at code.
For the requirements specification you need to provide a list of "must have" requirements and a list of "stretch" requirements.  The grading of your project is based on how well you meet these requirements – review the grading criteria before submitting your requirements document. While six must have requirements is the minimum number required and four is the minimum number of stretch requirements you may have more – project grading is based on all of the must have and stretch requirements in your requirements document.
The requirements document is not an IEEE standard SRS. The IEEE standard is overkill for the CS 499 project requirements specification.
For this document, use the following outline. Some of these sections may not apply to your project. For any section that does not apply you need to state (in that section) why it does not apply.
Title Page: Project Name. Team Members, Description of project
Section 1: Introduction: Purpose of Project
State the problem and how you are solving it
Section 2a: Must Have Requirements
Create a list of a minimum of six must have requirements. For each listed requirement you need to state the success measure including how you will demonstrate that the requirement is completed.  Avoid ambiguity - each requirement is specific to one purpose.
Section 2b: Stretch Requirements
Create a list of a minimum of four stretch requirements. For each listed requirement you need to state the success measure including how you will demonstrate that the requirement is completed.  Avoid ambiguity - each requirement is specific to one purpose.

Section 3: Overview of the Product.
Workflow: A workflow is how the user is going to use the software. The user will start off with X, Y, Z inputs, go through Process A, and receive a certain output. Use the output for input to Process B, and so on. Typically, you can map requirements to the different phases of the workflow.
Resources: You listed a series of resources in your proposal, how are you going to use them? Where do they fit in your product? How do all the parts interconnect? What 3rd party software, packages and libraries will be involved in the building, operation and delivery of the software. What tiers will it be using (front end, peer-to-peer, client/server, multi-tier, etc.).
Data at Rest: How are you going to store user information? Both the user’s profile (login, contact, etc.), along with the data they will generate (application data). Will it be a file or database?
Data on the Wire: How will the information be saved? Transmitted back to a central location? Where will the process take place?
Data State: Provide a process flow, state flow diagram or some other design diagram. This goes back to the workflow. This is the map of where the data flow through the system.
HMI/HCI/GUI: Provide a prototype (screen shot, drawing, pic, etc) of what the user will see while using the application
Section 4: Verification: How will the project be tested.
Demo: How will you demonstrate that your application works as designed? What data will you use? What steps will verify the requirements?
Testing: Each requirement needs to be verified. This is more than just restating the requirements as a To Do statement.  I.e. Verify that App shall allow the user to save input.  Explain how the requirement will be fulfilled, along with criteria defining the range of acceptability. Also, if applicable, define when the requirement is not fulfilled.

Sources/Citation/Resources Links: You must provide links to sources, citations and resources that you are using as part of your requirements specification.
Note:
Format: Being able to read a specification is a major component. Proper use of white space, outline, and use of headers is required.

REQUIREMENTS CHANGES
Requirements changes are not accepted after week 10 of CSE 499 and after week 3 of CSE 499B.
You should plan to complete your project as you defined it. However, as you get deeper into your research and development, if you discover that something is not feasible as you had planned (note: not "a little harder than anticipated"), you may need to re-negotiate items in your requirements document.
In order to request a requirements change after you have turned in your requirements document and it has been approved by your instructor, you will send an email to the instructor with the following:
List of previous requirement(s).
Explanation of why it is no long appropriate and why this was not identified earlier.
List of proposed requirements to be done in lieu of the previous ones.
Justification for why this change will not compromise the integrity of the overall project.
Please note that requirements changes are not made to simply make the project easier or to get a better grade. Usually they require more work, because they require you to go in a different direction than originally planned. They are, however, necessary when the project has reached an insurmountable hurdle so that another course of action can be taken.
As with projects in the real-world, you should do all you can to identify and mitigate high priority risks as early as possible. Thus, you can make plans to mitigate the risks and adjust accordingly. Also, as with the real-world, other stake holders will be more understanding and can more easily adjust their plans earlier in the process. In other words, for this project you can expect the amount of leniency will be greater earlier in the project.
