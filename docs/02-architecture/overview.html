Architecture Overview

What this is: the shape of the system as it actually exists in forge_senior_project_version/lib — every directory, what runs where, what the notes recommended and we are not doing, and the architectural risks that will bite. Read this before opening data-model.html.

  • App → Firebase Auth — no social auth, no email verification, no password reset.
  • App → Firestore — no repository layer, so there is no seam to substitute in a test.
  • App → Storage — no size or MIME cap on write.
  • App Check → Firestore — combined with the open /users read rule, anyone with the project id can read the user table. The Firebase config is committed, so the project id is discoverable. See risks.
  • FCM — lib/services/push_service.dart is 0 bytes; invites and DMs are silent today. Lands in M4, and sending push properly needs a Cloud Function.
  • App → Crashlytics — no error reporting exists today, against an app with known unchecked-cast crash paths. Adopted in M3; it replaced the earlier Sentry proposal once D3 cut web as a target. See the runbook.
  • Docs → Cloudflare Pages — Firebase Hosting is already configured for build/web and stays only if the app itself needs it.
  • Cloud Functions — no package, no functions/ dir, no firebase.json entry; still rejected as premature. Two M4 items are expected to fire its trigger: sending FCM from the client would mean shipping an admin credential, and the account-deletion cascade may not be expressible in rules + client. Decide it there, not now.

Architecture as-is vs as-intended

ARCHITECTURE_ANALYSIS.md and PROJECT_STATUS.md made a set of architectural recommendations in February. Six months and ~16,000 lines later, none of the three headline recommendations were adopted. That is not a failure — a working app got built instead. But the docs still claim the intent, so here is the honest ledger.

  • Adopt Riverpod — ARCHITECTURE_ANALYSIS.md said "Riverpod recommended" and PROJECT_STATUS.md repeated it. Keep setState + StreamBuilder: recommended twice, adopted zero times, and the app works. Introduce Riverpod only where state genuinely crosses screens. The most reversible-but-expensive call in the plan — see decisions.
  • Dependency injection — AuthService already accepts optional FirebaseAuth/FirebaseFirestore; that constructor seam is the only injection we need, and it is currently unexercised. Delete di_providers.dart.
  • Repository base classes — services are top-level free functions calling Firebase directly. Trigger: an actual backend migration, or a second non-Flutter client (same trigger as D1). Until then a repository interface buys one developer nothing. Cost of the debt, stated plainly: any move off Firebase touches all 15 service files and most of the UI.
  • Feature-based clean architecture — the source called it "Excellent separation by feature" and "DON'T START OVER". The folder tree exists everywhere but only presentation/view/ ever has content. Keep the feature folders; delete the empty data/, domain/ and viewmodel/ folders under feed/. One convention honestly applied beats two where one is fictional.
  • Move services — zero functional benefit, touches every import in the app. The question is closed.
  • Firestore converters — start with Event, because Event carries the live crash path. See data-model.
  • Error boundaries — the source logged it as a "structural improvement, not done". One AppException plus a rule that no catch block may be empty.
  • Frontend + API gateway — trigger: a second client that isn't Flutter, or Firestore read cost past $25/mo. Not a rewrite anyone should start from this codebase's current test coverage.
  • Multi-platform targets — the proposal promised "deploy to mobile, desktop and web without extra code". firebase_options.dart configures web/macOS/Windows; Linux throws UnsupportedError. DEFERRED trigger: a gym admin asks to moderate from a desktop browser.
The pattern to notice: every abandoned recommendation left behind an empty file rather than a decision. That is why core/ is a directory tree of blanks. The fix is not to fill them all — it is to delete the ones we have decided against so the tree stops implying an architecture nobody is building.

Known architectural risks

Severity is about blast radius, not effort. Everything Critical or High is reachable with data the app itself writes.

RiskSeverityWhy it happensFix shapeMilestone
/users is allow read: if true — the whole user collection is world-readable, unauthenticated Critical Wider than any code path requires Require request.auth != null, then split the doc M1
channelPosts allow update is unconstrained — any joined member can rewrite any field of any post High Written to permit likes; nothing narrows affectedKeys() Constrain the member path to hasOnly(['likeIds']) M1
Event startAt/endAt: nullable on write, non-null cast on read — a live crash path High Written nullable, read with an unchecked cast Regression test first, then a typed Event model M1
No field validation in any security rule; client-supplied timestamps High No rule checks a type, a length, or a required key Shape validation on the four write-heavy collections M1
Storage has no size or MIME cap; CORS is origin: ["*"] Medium storage.rules allows any owner write of any size Add a 5 MB size cap and an image/.* MIME check M1
Calendar opens 2×(friends + gyms) + 1 live listeners Medium A hand-rolled merger fans out two listeners per friend and gym One collection-group query over events, windowed by date M6 — threshold: a user with >15 friends+gyms, or Firestore reads past 50k/day
N+1 sequential fetches throughout Medium Four call sites loop .get() one document at a time Batch with whereIn chunks; use the denormalised names M6 — except the dead query, which goes in M2
Search is limit(100) + in-memory contains() — silently breaks past 100 users Medium Reads 100 arbitrary user docs and filters them in Dart Prefix range query on displayNameLower, with pagination M3 — before the beta cohort can exceed 100 accounts
No abstraction over Firestore anywhere — no seam for tests or backend swap Medium 14 of 15 services call the Firebase statics directly Give each Firestore handle a default parameter, one file at a time M2 onward, opportunistically
Two competing repetition mechanisms — events expand recurrence client-side, Plans materialise real docs Medium Nothing reconciles the two; an event can be both Pick one DEFERRED M6
DM rules make 3–4 get() calls per message write Medium dmAllowedBetween() reads up to four documents Denormalise the permission answer onto the thread doc M6 — threshold: the first resource-exhausted rule error
Message read is allowed when the thread doc does not exist Medium Race-condition escape hatch, firestore.rules line 161 Remove the !exists(...) branch M1
  • /users read rule — an inline rule comment justifies it: "needed for friend lists, gym lists". But the app only ever reads user docs while signed in. There is no App Check, and the Firebase config is committed, so the project id is discoverable. Split the doc into public profile fields vs private email/contactInfo. App Check hardens this further but is not a prerequisite and lands later, in M3 — do not wait for it.
  • channelPosts update — a member can overwrite another member's content, or their authorUid. Give content edits to resource.data.authorUid only, and fix isCurrentUserGymOwner in the same change so authors can delete their own posts.
  • Event startAt/endAt — createEvent writes the fields as nullable; events_service._mapDocToEvent does (d['startAt'] as Timestamp). strict-casts is off, so it compiles clean. Any event saved without a start time crashes the calendar for its owner and everyone it is shared with. The typed model needs a required startAt at the write boundary and a null-safe read, plus rule-level shape validation so bad docs can't be written at all.
  • No field validation in rules — a client can write accountType: 'gym' onto its own user doc and instantly gain channel creation and DM-anyone privileges. sentAt/createdAt are Timestamp.now() from the device, so ordering is spoofable. Validate users, events, channelPosts and messages; make accountType immutable after create; validate createdAt == request.time.
  • Storage caps and CORS — storage-cors.json exposes Authorization to every origin. Add request.resource.size < 5 * 1024 * 1024 and a contentType.matches('image/.*') check, and narrow CORS to the app origins that actually need it.
  • Calendar listeners — events_service._mergeEventStreams is a hand-rolled merger that fans out two snapshot listeners per friend and two per joined gym, deduping and sorting in Dart. getNextWorkoutEventForUser builds the entire 60-day range stream just to take .first. If one collection-group query can't satisfy the visibility rules, cap concurrent listeners and page the rest.
  • N+1 sequential fetches — friends_service.getFriendIdsWithNames, gyms_service member profiles, and profile_page's friends/gyms lists all loop .get() one doc at a time. getIncomingFriendRequestsStream runs an asyncMap with one .get() per thread on every snapshot. social_page still queries every joined gym for a tab that was deleted — delete the dead _loadMessagesList call outright, that one is free.
  • Search — search_service reads the first 100 user docs Firestore happens to return and filters in Dart: no query, no index, no ordering, no pagination. Users beyond that window are unfindable, with no error. displayNameLower is written at signup precisely for this and never queried, so the prefix range query (>= q, < q + '') is a small change — and it is invisible until the day it isn't.
  • No abstraction over Firestore — 14 of 15 services are top-level free functions calling FirebaseAuth.instance.currentUser and FirestoreRefs directly, so there is nothing to substitute in a test. Not a rewrite: as each service is next touched, give its Firestore handle a default parameter so a test can pass a fake.
  • Two repetition mechanisms — events_service._expandDocToEventsForRange renders N occurrences from one stored doc; plans_service writes N actual event documents, capped at 250 on create and 180 on update. Trigger: the first bug report where a recurring event and a plan instance both appear on the same day.
  • DM rule get() cost — dmAllowedBetween() reads the thread, both user docs, and sometimes a membership array. Each is a billed read and counts against Firestore's 10-get()-per-evaluation ceiling; it is close to the limit already. Denormalising at thread-creation time makes the rule read one document instead of four.
  • Message read without a thread doc — threads are delete: if false, which narrows the window, but the clause is a hole by construction. If thread creation genuinely races message creation, fix it with a batched write instead of a rule exemption.

What we are deliberately NOT building

Solo developer, free tier, boring tools. Each of these is a real architecture that a bigger team would want, and each has a named trigger — none is silently dropped.

Not buildingOne lineTrigger that would change it
A backend service of our own The client talks to Firebase directly and will keep doing so A non-Flutter client, or Firestore reads past $25/mo (D1)
Microservices There is no service to split — one app, one Firebase project Never, at this size
A caching layer Firestore's SDK already caches locally A measured read-cost problem that query fixes did not solve
An offline-first sync engine Firestore's default offline persistence is the whole strategy Beta feedback showing users lose work in dead zones
  • A backend service of our own — there is no server to write, deploy, or page someone about. Cloud Functions specifically also requires the Blaze plan, i.e. a card on file.
  • Microservices — if the backend above ever gets built, it starts as one process.
  • A caching layer — the three hand-rolled avatar caches in profile_avatar_service are the maximum caching this app gets. Measure first: the N+1 loops are the actual cost, not the absence of a cache.
  • An offline-first sync engine — we are not writing conflict resolution, an outbox, or a mutation queue. Until the trigger fires the gap is a UI gap — deliberate offline/empty/error states — not a sync-engine gap.
