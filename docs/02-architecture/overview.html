Architecture Overview

What this is: the shape of the system as it actually exists in forge_senior_project_version/lib — every directory, what runs where, what the notes recommended and we are not doing, and the architectural risks that will bite. Read this before opening data-model.html.

The 21 empty files

21 of 58 .dart files are 0 bytes. A full grep for TODO/FIXME/HACK across lib/ returns exactly 2 hits, both in dead code. The incompleteness is invisible to tooling — anyone who greps will conclude the app is finished. It is not.

core/constants/ colors.dart, icons.dart, strings.dart The brand blue is copy-pasted into 6+ files. One theme change is a 6-file edit. DECIDED Fill colors.dart. Leave strings.dart and icons.dart empty — no i18n is planned.
core/firebase/converters.dart 1 No withConverter, so every read is an untyped map. DECIDED Fill alongside the first typed model (Event).
app/di_providers.dart 1 No dependency injection at all. DECIDED Delete it. Per D5 we are not adding DI; the file is a promise nobody is keeping.

Architecture as-is vs as-intended

ARCHITECTURE_ANALYSIS.md and PROJECT_STATUS.md made a set of architectural recommendations in February. Six months and ~16,000 lines later, none of the three headline recommendations were adopted. That is not a failure — a working app got built instead. But the docs still claim the intent, so here is the honest ledger.

RecommendationSourceAdopted?Our call
Adopt Riverpod for state management ARCHITECTURE_ANALYSIS.md ("Riverpod recommended") and again in PROJECT_STATUS.md No — no state package in pubspec.yaml at all PROPOSED D5 — do not migrate. Keep setState + StreamBuilder. Recommended twice, adopted zero times, and the app works. Introduce Riverpod only where state genuinely crosses screens. This is the most reversible-but-expensive call in the plan — see decisions.
Set up proper dependency injection ARCHITECTURE_ANALYSIS.md; di_providers.dart scaffolded No — the file is 0 bytes DECIDED Not doing it. AuthService already accepts optional FirebaseAuth/FirebaseFirestore — that constructor seam is the only injection we need, and it is currently unexercised. Delete di_providers.dart.
Create base classes / interfaces for repositories ARCHITECTURE_ANALYSIS.md No — services are top-level free functions calling Firebase directly DEFERRED Trigger: an actual backend migration, or a second non-Flutter client (same trigger as D1). Until then a repository interface buys one developer nothing. Cost of the debt, stated plainly: any move off Firebase touches all 15 service files and most of the UI.
Feature-based clean architecture — data/domain/presentation per feature ARCHITECTURE_ANALYSIS.md ("Excellent separation by feature", "DON'T START OVER") Partially — the folder tree exists everywhere; only presentation/view/ ever has content DECIDED Keep the feature folders (they work). Delete the empty data/, domain/, and viewmodel/ folders under feed/. One convention, honestly applied, beats two conventions where one is fictional.
Move services to lib/core/services/ ARCHITECTURE_ANALYSIS.md — raised twice in the same file, decided neither time No DECIDED Keep lib/services/. Zero functional benefit, touches every import in the app. The question is closed.
Firestore converters / typed reads core/firebase/converters.dart scaffolded at commit 1 No — 0 bytes; every read is Map<String, dynamic> DECIDED Adopt incrementally, starting with Event, because Event carries the live crash path. See data-model.
Error boundaries and proper error handling ARCHITECTURE_ANALYSIS.md ("structural improvement, not done") No — core/errors/ is two empty files DECIDED One AppException plus a rule that no catch block may be empty. Lands with M1.
Replace direct-Firebase with a frontend + API gateway Ideas for Future.docx No DEFERRED (D1). Trigger: a second client that isn't Flutter, or Firestore read cost past $25/mo. Not a rewrite anyone should start from this codebase's current test coverage.
Multi-platform targets — web, macOS, Windows, Linux Forge Proposal ("deploy to mobile, desktop and web without extra code") Scaffolds exist — firebase_options.dart configures web/macOS/Windows; Linux throws UnsupportedError DECIDED D3 — iOS + Android only. The other targets exist because Flutter generates them, not because a user asked. DEFERRED trigger: a gym admin asks to moderate from a desktop browser.
The pattern to notice: every abandoned recommendation left behind an empty file rather than a decision. That is why core/ is a directory tree of blanks. The fix is not to fill them all — it is to delete the ones we have decided against so the tree stops implying an architecture nobody is building.

Known architectural risks

Severity is about blast radius, not effort. Everything Critical or High is reachable with data the app itself writes.

RiskSeverityWhy it happensFix shapeMilestone
/users is allow read: if true — the whole user collection is world-readable, unauthenticated Critical An inline rule comment justifies it: "needed for friend lists, gym lists". But the app only ever reads user docs while signed in — the rule is wider than any code path requires. No App Check, and the Firebase config is committed, so the project id is discoverable. Require request.auth != null immediately. Then split the doc: public profile fields vs private email/contactInfo. Enable App Check in the same pass. M1
channelPosts allow update is unconstrained — any joined member can rewrite any field of any post High The rule was written to permit likes, but nothing narrows affectedKeys(). A member can overwrite another member's content — or their authorUid. Constrain the member path to hasOnly(['likeIds']). Give content edits to resource.data.authorUid only. Fix isCurrentUserGymOwner in the same change so authors can delete their own posts. M1
Event startAt/endAt: nullable on write, non-null cast on read — a live crash path High createEvent writes the fields as nullable; events_service._mapDocToEvent does (d['startAt'] as Timestamp). strict-casts is off, so it compiles clean. Any event saved without a start time crashes the calendar for its owner and everyone it is shared with. Regression test first, then a typed Event model with a required startAt at the write boundary and a null-safe read. Add rule-level shape validation so bad docs can't be written at all. M1
No field validation in any security rule; client-supplied timestamps High Not one rule checks a type, a length, or a required key. A client can write accountType: 'gym' onto its own user doc and instantly gain channel creation and DM-anyone privileges. sentAt/createdAt are Timestamp.now() from the device, so ordering is spoofable. Shape validation on users, events, channelPosts, and messages. Make accountType immutable after create. Validate createdAt == request.time. M1
Storage has no size or MIME cap; CORS is origin: ["*"] Medium storage.rules allows any owner write of any size. storage-cors.json exposes Authorization to every origin. Add request.resource.size < 5 * 1024 * 1024 and a contentType.matches('image/.*') check. Narrow CORS to the app origins that actually need it. M1
Calendar opens 2×(friends + gyms) + 1 live listeners Medium events_service._mergeEventStreams is a hand-rolled merger that fans out two snapshot listeners per friend and two per joined gym, deduping and sorting in Dart. getNextWorkoutEventForUser builds the entire 60-day range stream just to take .first. Replace the fan-out with one collection-group query over events windowed by date. If that can't satisfy the visibility rules, cap concurrent listeners and page the rest. M6 — threshold: a user with >15 friends+gyms, or Firestore reads past 50k/day
N+1 sequential fetches throughout Medium friends_service.getFriendIdsWithNames, gyms_service member profiles, and profile_page's friends/gyms lists all loop .get() one doc at a time. getIncomingFriendRequestsStream runs an asyncMap with one .get() per thread on every snapshot. social_page still queries every joined gym for a tab that was deleted. Batch with whereIn chunks. Lean on the names already denormalised onto the docs instead of re-fetching. Delete the dead _loadMessagesList call outright — that one is free. M6 — except the dead query, which goes in M2
Search is limit(100) + in-memory contains() — silently breaks past 100 users Medium search_service reads the first 100 user docs Firestore happens to return and filters in Dart. No query, no index, no ordering, no pagination. Users beyond that window are unfindable, with no error. displayNameLower is written at signup precisely for this and never queried. Prefix range query on displayNameLower (>= q, < q + '') with a real limit and pagination. The field already exists — this is a small change, and it is invisible until the day it isn't. M3 — before the beta cohort can exceed 100 accounts
No abstraction over Firestore anywhere — no seam for tests or backend swap Medium 14 of 15 services are top-level free functions calling FirebaseAuth.instance.currentUser and FirestoreRefs directly. There is nothing to substitute in a test. Not a rewrite. As each service is next touched, give its Firestore handle a default parameter so a test can pass a fake. Incremental, one file at a time. M2 onward, opportunistically
Two competing repetition mechanisms — events expand recurrence client-side, Plans materialise real docs Medium events_service._expandDocToEventsForRange renders N occurrences from one stored doc. plans_service writes N actual event documents, capped at 250 on create and 180 on update. Nothing reconciles them; an event can be both recurring and plan-generated. Pick one. DEFERRED — trigger: the first bug report where a recurring event and a plan instance both appear on the same day. M6
DM rules make 3–4 get() calls per message write Medium dmAllowedBetween() reads the thread, both user docs, and sometimes a membership array. Each is a billed read and counts against Firestore's 10-get()-per-evaluation ceiling. It is close to the limit already. Denormalise the permission answer onto the thread doc at creation time, so the rule reads one document instead of four. M6 — threshold: the first resource-exhausted rule error
Message read is allowed when the thread doc does not exist Medium A race-condition escape hatch at firestore.rules line 161. Threads are delete: if false, which narrows the window, but the clause is a hole by construction. Remove the !exists(...) branch. If thread creation genuinely races message creation, fix it with a batched write instead of a rule exemption. M1

What we are deliberately NOT building

Solo developer, free tier, boring tools. Each of these is a real architecture that a bigger team would want, and each has a named trigger — none is silently dropped.

Not buildingOne lineTrigger that would change it
A backend service of our own The Flutter client talks to Firebase directly and will keep doing so; there is no server to write, deploy, or page someone about. A second client that isn't Flutter, or Firestore read cost past $25/mo (D1). Cloud Functions specifically also requires the Blaze plan, i.e. a card on file.
Microservices There is no service to split. One app, one Firebase project. Never, at this size. If the backend above ever gets built, it starts as one process.
A caching layer Firestore's SDK already caches locally; the three hand-rolled avatar caches in profile_avatar_service are the maximum caching this app gets. A measured read-cost problem that batching and query fixes did not solve. Measure first — the N+1 loops are the actual cost, not the absence of a cache.
An offline-first sync engine Firestore's default offline persistence is on and that is the whole strategy. We are not writing conflict resolution, an outbox, or a mutation queue. Beta feedback showing users actually lose work in the gym's dead zones. Until then the gap is a UI gap — deliberate offline/empty/error states — not a sync-engine gap.
