Architecture Overview

What this is: the shape of Forge as it actually exists today — client, backend surface, feature areas, and the one pattern that holds all of it together — not an idealized redesign.

System diagram

One Flutter codebase, three build targets with real Firebase registration, one Firebase project as the entire backend. There is no server tier — the client talks to Firebase directly.

Major components

Six feature areas make up the app. All are working end-to-end against live Firestore; line counts are the primary view file only, not the whole feature folder.

The real architecture pattern

Every screen is a StatefulWidget that calls a free function in lib/services/*.dart directly from build(), usually through a StreamBuilder or FutureBuilder. The service function talks to Firestore. That is the entire stack.

LayerWhat's thereWhat's not there
ViewStatefulWidget + setState, or StreamBuilder/FutureBuilder wired to a service call.No ViewModel, no Bloc, no Provider.
ServiceFree functions in lib/services/*.dart — the de facto data layer for every feature.No repository interfaces, no DI container.
DataRaw Map<String, dynamic> almost everywhere; Goal and the Plan* classes are the only typed exceptions.No DTOs, no converters layer.
State managementNone — no Riverpod, Bloc, Provider, or get_it anywhere in pubspec.yaml or code.ARCHITECTURE_ANALYSIS.md recommended Riverpod; never adopted.
DECIDED Keep this pattern.

Per brief §7: "The dead clean-architecture scaffold was never used. Adopting it now is a rewrite with no payoff." View → free-function service → Firestore is the deliberate, permanent shape of this app, not a temporary state on the way to something else.

Routing

Navigation runs on go_router, defined in app/router.dart. A top-level redirect gates every route on FirebaseAuth.instance.currentUser — logged out goes to login/register, logged in enters a ShellRoute with a persistent bottom nav.

DetailNotes
Auth gateTop-level redirect checks FirebaseAuth.instance.currentUser; unauthenticated users cannot reach any route inside the shell.
ShellShellRoute wraps Feed, Calendar, Social, Profile behind one persistent bottom nav bar.
TransitionsCustom slide-transition logic keyed off a hand-maintained route-order map.
Deep linksQuery params drive calendar focus (focusOwner, focusEvent) and event edit (edit).

Known duplication worth knowing

_mergeEventStreams (events_service.dart:450-497) and _mergeUpdateStreams (updates_service.dart:50-82) are near-identical hand-rolled multi-stream mergers — each subscribes N per-friend/per-gym Firestore streams, buffers the latest value per index, and re-sorts client-side on every emission.

They were written twice, not shared. A bug fix to one (say, a subscription leak on cancel) has to be applied to the other by hand or it drifts. See conventions.html for how to treat this pattern going forward.
