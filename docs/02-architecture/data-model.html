Data Model

What this is: the Firestore/Storage shape Forge's code actually reads and writes today, field by field — a reference page, not a proposal. Firestore is schemaless; this is inferred from firestore_refs.dart, the service files, and firestore.rules.

Dead collection: user_preferences/{userId}

Rules exist, code doesn't.

firestore.rules:191-204 defines access rules for user_preferences/{userId}. Nothing in lib/ reads or writes this collection — it is referenced only in the rules file and two stale markdown docs. Treat it as a cleanup item, not a feature to build toward.

Relationships

Two structural choices explain most of the shape above. Both are honest trade-offs, not mistakes, and both are locked in by brief §7 ("do not change the existing Firestore data model").

ChoiceConsequence
One users collection models both people and gyms, discriminated by accountType. A gym is a user doc that additionally carries memberUserIds/channelNames.Simple to query (one collection, one set of security rules to reason about) but means gym-specific fields sit unused on every person doc's schema, and vice versa. There is no schema-level guarantee a "gym" doc doesn't also have friendIds set.
Friendships and gym membership are denormalized uid arrays (friendIds, joinedGymIds, memberUserIds) directly on the user/gym doc, not a separate join collection.Reading "who are my friends" is one document read, not a query — fast and cheap on the free tier. It also means the array shares the document's 1 MiB Firestore size limit with every other field on that doc, so it does not scale to a large friend or member count, and any single friend/member read still means loading the whole array even to check one relationship.

Storage choices

ChoiceDetail
Firestore for structured dataEvery collection above. Primary datastore for the whole app.
Firebase Storage for avatars onlyPath convention avatars/{uid}/profile, bucket forge-by-alpfit.firebasestorage.app. No other file uploads exist in the app.
Enums as stringsaccountType, eventType, resetPeriod, status, messageKind are all stored as plain strings, not Firestore's native enum-adjacent types.
DateTime ⇄ TimestampConversion happens at the service boundary — services accept/return Dart DateTime, Firestore stores Timestamp. No shared converter utility (core/firebase/converters.dart is 0 bytes) — each service does this inline.
