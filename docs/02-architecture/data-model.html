Forge docs / Architecture

Data Model

What this is: the reference doc for every Firestore entity Forge actually writes — path, every field with its type, who can read and write it under the current rules, and whether it has a typed Dart class. Read it with overview.html risks open; several rows here are the same finding seen from the data side.

The headline finding

Only Goal is a real typed model class. lib/models/ contains exactly one file, goal.dart. Every other entity in the system — User, Event, ChannelPost, Comment, DirectThread, DirectMessage — is an untyped Map<String, dynamic> passed hand-to-hand between services and widgets. Plan is the halfway case: it has read-side DTO classes declared inside its service file, but its writes are still raw maps.

This is the single biggest data-layer finding, and it is not a style complaint. Three concrete consequences:

  • No compiler help. A field renamed in one service and not the other fails silently at runtime. Nothing catches d['startAt'] vs d['start_at'].
  • Unchecked casts everywhere. Reading an untyped map means writing as Timestamp and as List<String>. With strict-casts off (see conventions) these compile clean and crash at runtime.
  • Schemas that don't round-trip. The event creator writes exercises as setDetails: [{reps, weight}]. events_service._mapDocToEvent reads a top-level weight key that is never written. The calendar therefore renders every exercise weight blank, and nothing anywhere reports an error.
DECIDED Add typed models incrementally, starting with Event. Not a big-bang model layer, and not a code-generation package. One hand-written class per entity with fromDoc / toMap, added when that entity is next touched.

Why Event first: it is the only entity with a live crash path. createEvent writes startAt/endAt as nullable; _mapDocToEvent reads them with a non-null cast. A typed Event with a required startAt at the write boundary and a null-safe read closes the crash and the schema drift in one change. Order after that: User (because the rules rewrite in M1 needs a fixed shape to validate against), then ChannelPost, then the DM pair.

user_preferences Dead ruleset

This collection is referenced nowhere in lib/. No service reads it, no service writes it, no document has ever been created. It is also the only collection FIRESTORE_RULES_SETUP.md documents in detail — a doc describing the one collection the app never uses.

Security rules

firestore.rules, 206 lines. Read it as the real access-control spec — FIRESTORE_RULES_SETUP.md has drifted and is missing six of the nine collections.

/users/{userId} is allow read: if true. Not "any signed-in user" — anyone, with no authentication at all. Anyone who knows the Firebase project id can enumerate every user document and read email, displayName, contactInfo, avatarUrl, friendIds, joinedGymIds, and memberUserIds.

The project id is discoverable: Firebase client config is committed and git-tracked, which is normal and acceptable for Firebase — the security model puts enforcement in the rules. The problem is not the committed keys. The problem is that the rules do not enforce anything on this collection, and App Check is not enabled. Fix the rule; do not go rotate keys.

The inline comment justifies the rule as "needed for friend lists, gym lists". The app only ever reads user docs while signed in, so request.auth != null breaks nothing. This is the highest-severity item in the entire project.
CollectionReadWriteProblem?
users/{userId} if true — public, unauthenticated Create: self only. Update: self, or one of four diff-guarded cross-user mutations (friend-accept adds only self to friendIds; join/leave gym adds/removes only self from a gym's memberUserIds; a gym removes only itself from a member's joinedGymIds). Delete: if false. Critical — full PII leak. Also: no shape validation, so a client can write accountType: 'gym' on its own doc and gain channel-creation and DM-anyone privileges, or a 1 MB displayName. And delete: if false means account deletion is explicitly denied — an App Store 5.1.1(v) blocker.
users/{u}/events/{e} Owner, invitee, or isPublic AND owner ∈ reader's friendIds or joinedGymIds Owner only Medium — the read logic is sound. But owner-only write makes the "invite friends to edit a workout" requirement architecturally impossible. No field validation, so the nullable startAt crash path can be written by any client.
users/{u}/goals/{g} Owner only Owner only OK — apart from the client-supplied createdAt.
users/{u}/plans/{p} Owner only Owner only OK — same timestamp caveat.
users/{gym}/channelPosts/{p} Gym or joined member Create: gym or joined member. Update: gym or joined member, unconstrained. Delete: gym or authorUid. High — the update rule was written for likes but restricts nothing. Any joined member can overwrite any post's content or authorUid. Needs affectedKeys().hasOnly(['likeIds']).
…/channelPosts/{p}/comments/{c} Gym or joined member Create: gym or joined member. Delete: gym or author. Update: if false. Medium — create has no rate limit and no content constraint. Immutability is fine; unbounded creation is not.
directThreads/{t} Participant Create/update: participant, participants.size() == 2. Delete: if false. Medium — update lets a participant rewrite the other party's unreadCounts and set lastMessage to arbitrary text.
…/{t}/messages/{m} Participant, or if the thread doc does not exist Create: participant + senderUid == auth.uid + (a friend_request addressed to the other participant, OR dmAllowedBetween()). Delete: only a received friend_request. Update: if false. Medium — the !exists() read branch is a hole by construction. Separately, dmAllowedBetween() performs 3–4 get() calls per message write: each is billed, and it is close to Firestore's 10-get()-per-evaluation ceiling.
user_preferences/{userId} Self Self; delete never Dead — no code path touches this collection. Delete the block.
Storage: avatars/{userId}/** if true — public, unauthenticated request.auth.uid == userId Medium — no file-size limit and no content-type restriction. A user can upload a 5 GB file to their own avatar path. Everything outside /avatars/** is implicitly denied, which is correct. storage-cors.json is origin: ["*"] with Authorization in responseHeader.

Cross-cutting: not one rule in the file validates a field type, a string length, or a required key. Every timestamp on goals, plans, and DMs is client-supplied Timestamp.now(), with no request.time check anywhere. See the Firebase runbook for the deploy command and M1 for the fix order.

Composite indexes

From firestore.indexes.json — 7 indexes, fieldOverrides: [].

2eventsCOLLECTION_GROUPinviteeIds CONTAINS, startAt ASC"Events I was invited to."
3channelPostsCOLLECTION_GROUPchannelName ASC, createdAt DESCChannel feed, newest first.
4eventsCOLLECTION_GROUPplanId ASC, startAt ASCFinding and regenerating a plan's materialised instances.
5goalsCOLLECTIONstatus ASC, createdAt DESCgetActiveGoalsStream. Correctly scoped.

7messagesCOLLECTION_GROUPmessageKind ASC, senderUid ASCOutgoing friend requests / pending state.
Two index notes worth acting on.
• Indexes 1, 2 and 4 are declared COLLECTION_GROUP, but every query in the code is a direct subcollection query on users/{uid}/events. A collection-group index does satisfy those, so this is harmless today — and it is exactly the index you would need if the calendar listener fan-out is replaced with a single collection-group query.
• Nothing indexes plans on name + updatedAt, which findPlanByNameForCurrentUser requires. Firestore will demand it at runtime — and channel_page.dart currently handles that class of error by rendering Firebase CLI instructions to the end user, telling a gym member to run firebase login --reauth and firebase deploy. Add the index; delete the developer error screen.

Missing from the model

Things the requirements need that no entity supports. "Priority" is when the absence starts costing something, not how hard it is.

Missing entity / fieldNeeded forPriority
User groups — no entity, no collection, no rules, no UI "Create and join groups of other users to interact with" is an explicit Social page requirement in the Initial Requirements; the Final Specs demotes it to a stretch ("create groups of friends to share events and posts with"). Nothing anywhere implements it. Optional — the demotion is the later signal. See features → groups.
Friend request as a first-class entity — currently a DirectMessage with messageKind: 'friend_request' A request has a lifecycle — pending, accepted, declined, withdrawn, blocked — and none of it is representable. Consequences today: the other-user profile shows "Add Friend" with no pending state, so users fire duplicate requests until the service throws; declining pops the whole chat page while accepting does not; and there is no unfriend-then-reblock story. Important — the duplicate-request bug is user-visible now.
Gym membership approval state — addGym joins instantly; only the kick half exists "Remove from or accept users into managed community" is a must-have requirement. Membership is currently two arrays with no pending value and no request record. There is no way for a gym to gate who joins. Important — a rec-center beta means a real gym expects this.
Moderation / report records — moderation_service.dart is 0 bytes Report, block, hide, takedown, appeal. App Store guideline 1.2 requires a report/block mechanism for any UGC app; Forge has gym channels and DMs. There is no reports collection, no blockedUserIds field, no hidden-content flag. Must — hard iOS submission blocker, and D6 puts real external users in scope.
Notification tokens — no fcmTokens field, no notificationPreferences Push. push_service.dart is empty, so invites, DMs, and event changes are all silent — you learn about them by opening the app. Even deferring push, the token storage shape needs deciding before it is retrofitted onto a live user table. Optional — DEFERRED to M5, trigger: retention becomes the problem worth solving.
Account-deletion tombstones — allow delete: if false on users, no UI Apple guideline 5.1.1(v) requires in-app account deletion. Deleting a user also orphans their events, goals, plans, channel posts, comments, DM threads, avatar blob, and their uid inside every friend's friendIds and every gym's memberUserIds. A tombstone or a soft-delete flag is needed so surviving references render as "Deleted user" instead of crashing. Must — hard iOS blocker, and the cascade is the real work.
Recurring-event exceptions — recurrence has no exception list "Skip this one occurrence" and "edit just this occurrence" are unrepresentable. Client-side expansion means every occurrence is derived; there is nowhere to record that one of them moved or was cancelled. Plans dodge this by materialising real docs — which is why two mechanisms exist. Important — the first user who cancels one week of a recurring workout hits it.
Timezones — every timestamp is naive; the goal period engine does flat date arithmetic A calendar app and a period-based goal engine both depend on "what day is it for this user". ResetPeriod.monthly is a flat 30-day add; the day grid starts at a hardcoded 4 AM and renders anything earlier at a negative offset, off-grid. No document in the corpus addresses timezones at all. Important — silent wrong-day bugs, and they get worse with travel and DST.
Channel as an entity — currently a string in the gym doc's channelNames array Per-channel write permissions ("users can post on certain channels"), channel descriptions, ordering, archiving, and the "subpages" requirement. A string array supports none of it, and renaming a channel orphans every post that carries the old channelName. Important — the rename-orphans-posts bug is one gym admin away.
Personal posts — no post entity outside gym channels "View updates from friends" in the Feed requirement. Today that resolves to "your friend scheduled a public event" — friends have no posting surface at all. The requirement is met in name only. Optional — the Final Specs lists friend-directed posts as stretch.
Exercise / movement catalog — exercises are free-text maps inside each event Every requirements doc names an exercise database as a needed resource ("I will create this or find a free API"), and it was never specified or built. Without it there is no autocomplete, no dedupe, and no way to answer "when did I last do this movement". Optional — and note the anti-scope: Forge does not compete on workout programming. Fix the setDetails round-trip bug first; that is the real defect.
Event RSVP state — no attendeeStatus map on the event The Attend/Decline chips already exist in the DM UI and animate convincingly. They write nothing. A {uid: 'going'|'declined'} map on the event doc is the missing half. Important — this is fake UI shipping today, not a future feature.

What To Do Next

  1. Write a failing test for the Event.startAt null crash, then add the typed Event model. It is the first entry in the typed-model rollout and it closes a live crash path, the setDetails round-trip bug, and the missing endAt > startAt validation in one pass.
  2. Change allow read: if true to allow read: if request.auth != null on /users. One line. Nothing in the app breaks. It is the highest-severity item in the project and it is a five-minute fix followed by a careful test. M1.
  3. Take the "Missing from the model" rows marked Must — moderation records and account-deletion tombstones — into M3 scoping. Both are store blockers with real data-model design behind them, not paperwork.
