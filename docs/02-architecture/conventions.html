Firestore naming & the subcollection-under-user pattern

Everything a user owns lives under users/{uid}/. A gym is a user, so gym content lives under users/{gymUid}/ too. The only top-level collection besides users is directThreads — because a thread is owned by two people at once.
RuleDetailExample
Collection nameslowerCamelCase, pluralevents, goals, plans, channelPosts, directThreads, messages, comments
The one exceptionuser_preferences is snake_case DECIDED delete it—
OwnershipOwned data is a subcollection of the owner's user docusers/{uid}/events/{eventId}
Document idsFirestore auto-ids, with two deliberate exceptionsabc123__xyz789
Field nameslowerCamelCase, with typed suffixesinviteeIds, lastMessageAt, displayNameLower, isPublic
DenormalisationExpected and correct for FirestoreauthorName, inviteeNames, locationGymName
TimestampsInconsistent today DECIDED serverTimestamp() everywhere—
Adding a collectionThree things, always together: ref, rule, indexSee the missing plans index.
  • The one exception — user_preferences is also the one collection the app never touches, so delete it rather than rename it.
  • Ownership — no ownerUid filter needed; the path is the ownership, and the security rules key off the path parameter.
  • Document ids — users/{uid} uses the Firebase Auth uid, and directThreads/{id} uses sorted(uidA, uidB).join('__') so a thread can be addressed without a lookup query.
  • Field names — *Ids for arrays of uids, *At for timestamps, *Lower for search-normalised copies, is* for bools.
  • Denormalisation — names are copied onto the referencing doc so a list render is one query, not N.
  • Timestamps — serverTimestamp() on user docs, event creates, and channel posts; raw Timestamp.now() on goals, plans, plan-generated events, and DMs. The decided target is serverTimestamp() everywhere, enforced in the rules.
  • Adding a collection — the ref in firestore_refs.dart, a rule block in firestore.rules, and any composite index in firestore.indexes.json. Missing the third ships a runtime error to the user — that has already happened once.
The trade-off this pattern makes, stated once. Path-as-ownership gives simple rules and cheap owner queries. It costs you cross-user queries: "all public events this week" needs a collection-group query and an index, which is why three of the seven indexes are COLLECTION_GROUP. It also means anything owned by two people has no home — which is exactly why collaborative event editing is impossible and why friend requests ended up as DM messages. Keep the pattern; know the edge.

  • A widget used by exactly one screen — a private class is the existing habit and it is fine.
  • A widget used by two or more features — lib/widgets/ is currently home to just storage_avatar.dart.
  • A Firestore read or write — as a top-level function. Never call Firestore from a widget.
  • A new collection path — plus rules and indexes, see above.
  • A typed model — hand-written; no code generation. Event is first in the queue.
  • A shared colour, spacing value, or text style — colors.dart (empty, fill it) or app_text_styles.dart (already real).
  • A validator — you'll be the first.
  • An error type — one class. Not a Result/Either hierarchy.
  • A route — auth-gated routes go inside the ShellRoute; /login and /register stay outside it so the bottom nav doesn't render.
  • A test — the directory does not exist yet; see testing.
  • Feed-MVVM-shaped code — those seven empty files are being deleted, not filled. Per D5 we are not adopting that layering.
  • State on one screen — this is the house pattern and it is deliberate (D5).
  • State that crosses screens — today the answer is a hand-rolled ChangeNotifier singleton (AuthStateNotifier, AvatarHeaderRefreshNotifier). A third one is the trigger to reopen the Riverpod question — see PROPOSED D5.

Git

The current commit log is unsearchable. Eleven commits, and the messages are "a lot", "a lot of stuff", "lots of stuff got done", "moippre stuff", "added ealeier deisgn ideas", and "asdgfasfdgarewgqrgv". git log --oneline currently tells you nothing about what changed, which means git bisect, git blame, and "when did this break" are all unavailable. That is a real cost the moment there is a bug worth tracing.

Branch names DECIDED — <type>/<linear-id>-<slug>, e.g. fix/FOR-12-users-read-rule. Type is one of feat, fix, chore. Linear is where the work lives (D10), so the issue id belongs in the branch name.

Commit messages PROPOSED — <area>: <what changed>, one line, present tense, under 72 characters. Area is a lib/ folder name or one of rules, indexes, docs, android, ios. That's the whole policy — no body required, no type taxonomy, no footer template. Examples: rules: require auth to read /users, services: fix null startAt crash in event mapper, docs: add architecture pages.

Not adopting: Conventional Commits, changelog generation, commit signing, squash policy, or PR templates. One developer, one branch at a time — the only thing worth buying here is a searchable log.

Lint & type safety

analysis_options.yaml is currently one line:

include: package:flutter_lints/flutter.yaml
SettingNowConsequence
strict-castsOffThis is the one that matters. (d['startAt'] as Timestamp) on a nullable field, as List<String>, as List<Map<String, String>> — all compile clean and crash at runtime. Every unchecked cast in the app exists because this is off.
strict-raw-typesOffBare List and Map pass silently — which is the whole untyped-Firestore problem written in the type system.
strict-inferenceOffImplicit dynamic from unannotated returns.
Extra lint rulesNoneflutter_lints is the permissive default set. No always_declare_return_types, no avoid_dynamic_calls, no unawaited_futures.
errors: severity overrides / exclude:NoneNothing is promoted to an error, nothing is suppressed.
Never cite "flutter analyze is clean" as evidence of anything. PROJECT_STATUS.md claims "Flutter analyze: No issues found!" — and it is probably true. It measures the lint configuration, not the code. The analyzer is set up to find nothing, and it is finding nothing.
DECIDED Enable strict-casts and strict-raw-types — as a milestone, not a drive-by.

Target file:

include: package:flutter_lints/flutter.yaml
analyzer:
  language:
    strict-casts: true
    strict-raw-types: true

This will surface real errors, not warnings to ignore. Every unchecked Firestore cast becomes a compile failure, and several of them are latent crashes we already know about. That is the point — but it is a day of work with no test suite behind it, so it gets its own scope rather than being tacked onto an unrelated change. Pair it with the first typed models so the fixes have somewhere to land.

Testing

There are zero tests. No test/ directory exists anywhere in the project. flutter_test sits in dev_dependencies unused. There is no CI, no golden tests, and the default test/widget_test.dart that flutter create generates has been deleted. Coverage is 0%, and there is no safety net under any refactor on this page.

The minimum bar. Five rules, no coverage target — a percentage would just invent busywork for a solo developer.

  1. Every service file gets a widget-free unit test before it is next modified. Not all eleven at once — the one you're about to touch. Services are pure logic over Firestore, so they are the cheapest thing in the app to test and the most expensive thing to get wrong.
  2. Every crash path found gets a failing regression test first, then the fix. The test proves the crash is real and proves the fix works. Start with events_service._mapDocToEvent and a document whose startAt is null.
  3. Test files mirror the lib/ path. lib/services/goals_service.dart → test/services/goals_service_test.dart. No other structure.
  4. Add the seam as you go, don't build one up front. When you test a service, give its Firestore and Auth handles optional parameters that default to the real instances. AuthService already has exactly this constructor seam and has never used it — copy that shape into the free-function services one file at a time.
  5. No widget tests to start. They are slower to write, more brittle, and the screens are the part most likely to change. Revisit once the services have coverage.

Open question, deliberately not answered here: the test-double approach — fake_cloud_firestore vs hand-rolled fakes — is not yet determined. It needs a package decision, which belongs on the services page, not in a conventions doc. Pick it when writing the first test, not before.

Patterns to avoid

Every row is a real pattern in the current code, with the file that has it. These are the things to catch in your own diff.

  • catch (_) {} — a profile save can fail silently and the user is told it worked. This is worse than a crash; a crash you find out about. Catch, surface it to the user, and rethrow or log. Once core/errors/app_exception.dart exists, wrap it.
  • try { } finally { } — a failed plan load shows an empty edit form as if the plan had no data. If there is genuinely nothing to do in the catch, say so in a comment — but there usually is.
  • Non-null casts — not hypothetical: createEvent writes the nullable field that _mapDocToEvent casts. A typed model does the null-check once. Turning on strict-casts makes the compiler find these for you.
  • const [] placeholders — it reads as "no data yet" forever, to you and to a reviewer. If the source is planned, leave the section out and put it in Linear.
  • Fake UI — calendar_page.dart hardcodes 'Friend 1', 'Ethan', 'Gym 1' and _filterStates is never read by any query; direct_message_page.dart line 147 is an RSVP that only calls setState; feed_page.dart line 779 is a comment sheet whose "Done" discards the input. It animates convincingly, so a demo viewer and a future you both believe the feature exists — this is why the app looks more finished than it is. A missing feature is honest; a fake one is a trap you set for yourself.
  • Redeclared constants — the theme's actual seed colour (deepPurple) is never seen because every screen overrides it, so the MaterialApp theme is decorative. Delete the copies as you touch each file.
  • setState after await — intermittent, hard to reproduce, and invisible without crash reporting. Guard every await that precedes a setState.
  • Developer instructions as UI — channel_page.dart tells the user to run firebase login --reauth and firebase deploy --only firestore:indexes, with a copy-to-clipboard console URL, which also leaks the Firebase console URL for the project. Fix the missing index instead — see indexes.
  • Dead code — the three unreachable builders in social_page.dart hold the repo's only two TODOs. Plus _loadMessagesList, which still runs a query per joined gym for a tab that was deleted. It costs reads, it costs reading time, and it hides those TODOs where nobody will find them.
  • N+1 .get() — each failure is individually swallowed. Use the name already denormalised on the doc you're holding.

What To Do Next
