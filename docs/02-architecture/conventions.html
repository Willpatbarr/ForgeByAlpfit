Conventions

What this is: naming, folder layout, and coding patterns actually in force in this codebase today — what to copy when adding a feature, and what existing debt not to add more of.

Folder layout

Top level of lib/: app, core, features, models, services, widgets. Every feature lives under features/<name>/presentation/view/.

FolderHolds
lib/app/Router (router.dart), auth state, the empty di_providers.dart.
lib/core/firebase/firestore_refs.dart (real, 49 lines) and constants/app_text_styles.dart (real, 81 lines). Everything else under core/errors, core/util, most of core/constants is 0 bytes.
lib/features/<name>/presentation/view/The screens themselves — one flat folder per feature, no data/domain split.
lib/models/The two real typed models: Goal, and the Plan* classes.
lib/services/Free-function service files — the de facto data layer for every feature.
lib/widgets/Shared UI widgets used across features.
Only feed/ ever got the deeper layering, and it is empty.

features/feed/data/, features/feed/domain/, and features/feed/presentation/viewmodel/ exist as folders with 0-byte files inside. Every other feature — auth, calendar, event_creator, social, profile — only ever had a flat presentation/view/ folder. The flat layout is the real convention; the deeper folders are fossil, not a pattern to extend. See overview.html for the full dead-scaffold list.

Patterns to follow

  • StreamBuilder wired directly to a service stream function (e.g. getEventsForDayStream) — the standard way a screen gets live data.
  • Services throw plain Exception(humanReadableMessage) — no typed error/Result layer exists, and none should be added ad hoc.
  • Views catch FirebaseException / FirebaseAuthException / generic Exception and surface it with a SnackBar.
  • Firestore document/collection references are centralized in core/firebase/firestore_refs.dart — do not hand-build a Firestore path inline in a service or view.
  • Multi-stream merges (own + friends' + gyms' events) go through a hand-rolled merger function local to the service file — see the duplication note below before writing a third one.

Patterns NOT to copy

This is existing debt. The brief is explicit: fix it feature-by-feature when a bug makes the case, not in a batch rewrite.

Debt patternWhere it shows upWhat to do instead
Map<String, dynamic> as the de facto model typeEvents, search results, gym members, feed updates, friend lists — almost everything except Goal and the Plan* classes.Do not retrofit typed models across the board. Add a typed model for a feature only when a bug there makes the case for it (brief §7).
Business logic living inside 1,300–2,100 line view filesevent_creator_page.dart (2,141), social_page.dart (1,963), calendar_page.dart (1,489), feed_page.dart (1,333).Don't grow a new screen to this size by habit. It's tolerated debt in the existing screens, not a target to replicate in a new one.
Duplicated hand-rolled stream mergers_mergeEventStreams (events_service.dart:450-497) and _mergeUpdateStreams (updates_service.dart:50-82) — same shape, copy-pasted.If a third merge is needed, extract a shared mergeSortedStreams<T> helper in core/ instead of writing a third copy.
Frame as "don't add more of it," not "rewrite now."

Brief §7: "Typed models only where they pay... do not retrofit Map<String,dynamic> everywhere. Add types feature-by-feature when a bug makes the case." The same restraint applies to view-file size and the stream mergers — these are accepted debt, tracked on out/05-debt.md, not blockers.

Adding a new feature

  1. Create lib/features/<name>/presentation/view/<name>_page.dart — flat, no data/ or domain/ subfolders. That is the real convention; see Folder layout above.
  2. Add a service file lib/services/<name>_service.dart exporting free functions that talk to Firestore, following the naming convention above.
  3. Centralize any new Firestore paths in core/firebase/firestore_refs.dart rather than inlining them in the service.
  4. Wire the screen's live data through a StreamBuilder calling the new service function, matching the pattern used everywhere else.
  5. Register the screen in app/router.dart — inside the ShellRoute if it needs the persistent bottom nav, top-level if it's auth-adjacent like login/register.
  6. Use a typed model only if the data is already typed elsewhere in this feature (e.g. extending Goal) or a specific bug requires it — default to Map<String, dynamic> otherwise, per brief §7.
  7. Verify: confirm the new screen's data persists across an app restart — the Final Requirements Spec's own bar for "done" (quoted on vision.html).

What To Do Next

  1. Before writing a new feature, skim overview.html for the dead-scaffold list so nothing gets built inside those folders by mistake.
  2. Before adding a field to any collection, check data-model.html for the existing shape and the two relationship trade-offs already accepted.
  3. If a debt pattern above starts actively causing a bug, fix that one instance — do not batch-rewrite the rest as part of an unrelated change.
