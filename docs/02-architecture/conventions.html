Firestore naming & the subcollection-under-user pattern

Everything a user owns lives under users/{uid}/. A gym is a user, so gym content lives under users/{gymUid}/ too. The only top-level collection besides users is directThreads — because a thread is owned by two people at once.
RuleDetailExample
Collection nameslowerCamelCase, pluralevents, goals, plans, channelPosts, directThreads, messages, comments
The one exceptionuser_preferences is snake_case — and it is the one collection the app never touches. DECIDED delete it rather than rename it.—
OwnershipOwned data is a subcollection of the owner's user doc. No ownerUid filter needed; the path is the ownership, and the security rules key off the path parameter.users/{uid}/events/{eventId}
Document idsFirestore auto-ids by default. Two deliberate exceptions: users/{uid} uses the Firebase Auth uid, and directThreads/{id} uses sorted(uidA, uidB).join('__') so a thread can be addressed without a lookup query.abc123__xyz789
Field nameslowerCamelCase. *Ids for arrays of uids, *At for timestamps, *Lower for search-normalised copies, is* for bools.inviteeIds, lastMessageAt, displayNameLower, isPublic
DenormalisationExpected and correct for Firestore. Names are copied onto the referencing doc so a list render is one query, not N.authorName, inviteeNames, locationGymName
TimestampsInconsistent today — serverTimestamp() on user docs, event creates, and channel posts; raw Timestamp.now() on goals, plans, plan-generated events, and DMs. DECIDED serverTimestamp() everywhere, enforced in the rules.—
Adding a collectionThree things, always together: the ref in firestore_refs.dart, a rule block in firestore.rules, and any composite index in firestore.indexes.json. Missing the third ships a runtime error to the user — that has already happened once.See the missing plans index.
The trade-off this pattern makes, stated once. Path-as-ownership gives simple rules and cheap owner queries. It costs you cross-user queries: "all public events this week" needs a collection-group query and an index, which is why three of the seven indexes are COLLECTION_GROUP. It also means anything owned by two people has no home — which is exactly why collaborative event editing is impossible and why friend requests ended up as DM messages. Keep the pattern; know the edge.

Lint & type safety

analysis_options.yaml is currently one line:

include: package:flutter_lints/flutter.yaml
SettingNowConsequence
strict-castsOffThis is the one that matters. (d['startAt'] as Timestamp) on a nullable field, as List<String>, as List<Map<String, String>> — all compile clean and crash at runtime. Every unchecked cast in the app exists because this is off.
strict-raw-typesOffBare List and Map pass silently — which is the whole untyped-Firestore problem written in the type system.
strict-inferenceOffImplicit dynamic from unannotated returns.
Extra lint rulesNoneflutter_lints is the permissive default set. No always_declare_return_types, no avoid_dynamic_calls, no unawaited_futures.
errors: severity overrides / exclude:NoneNothing is promoted to an error, nothing is suppressed.
Never cite "flutter analyze is clean" as evidence of anything. PROJECT_STATUS.md claims "Flutter analyze: No issues found!" — and it is probably true. It measures the lint configuration, not the code. The analyzer is set up to find nothing, and it is finding nothing.
DECIDED Enable strict-casts and strict-raw-types — as a milestone, not a drive-by.

Target file:

include: package:flutter_lints/flutter.yaml

    strict-casts: true

That is the point — but it is a day of work with no test suite behind it, so it gets its own scope rather than being tacked onto an unrelated change. Testing

There are zero tests. No test/ directory exists anywhere in the project. flutter_test sits in dev_dependencies unused. There is no CI, no golden tests, and the default test/widget_test.dart that flutter create generates has been deleted. Coverage is 0%, and there is no safety net under any refactor on this page.

The minimum bar. Five rules, no coverage target — a percentage would just invent busywork for a solo developer.

  1. Every service file gets a widget-free unit test before it is next modified. Not all eleven at once — the one you're about to touch. Services are pure logic over Firestore, so they are the cheapest thing in the app to test and the most expensive thing to get wrong.
  2. Every crash path found gets a failing regression test first, then the fix. The test proves the crash is real and proves the fix works. Start with events_service._mapDocToEvent and a document whose startAt is null.
  3. Test files mirror the lib/ path. lib/services/goals_service.dart → test/services/goals_service_test.dart. No other structure.
  4. Add the seam as you go, don't build one up front. When you test a service, give its Firestore and Auth handles optional parameters that default to the real instances. AuthService already has exactly this constructor seam and has never used it — copy that shape into the free-function services one file at a time.
  5. No widget tests to start. They are slower to write, more brittle, and the screens are the part most likely to change. Revisit once the services have coverage.

Open question, deliberately not answered here: the test-double approach — fake_cloud_firestore vs hand-rolled fakes — is not yet determined. It needs a package decision, which belongs on the services page, not in a conventions doc. Pick it when writing the first test, not before.

Patterns to avoid

Every row is a real pattern in the current code, with the file that has it. These are the things to catch in your own diff.

PatternWhere it isWhy it hurtsDo instead
catch (_) {} — swallowing the error entirely profile_page.dart lines 91, 374, 721, 1002; friends_service; gyms_service; plan_creator_sheet.dart line 104 The UI reports success for a write that never landed. A profile save can fail silently and the user is told it worked. This is worse than a crash — a crash you find out about. Catch, surface it to the user, and rethrow or log. Once core/errors/app_exception.dart exists, wrap it. No catch block may be empty.
try { } finally { } with no catch plan_creator_sheet.dart lines 60–93 Same failure mode, quieter. A failed plan load shows an empty edit form as if the plan had no data. Add the catch. If there is genuinely nothing to do, say so in a comment — but there usually is.
Non-null casts on nullable Firestore fields events_service._mapDocToEvent (as Timestamp); event_creator_page.dart line 1576 (setDetails); calendar_page.dart lines 1245, 1291 (attendees, exercises) Runtime crash on data the app itself can write. Not hypothetical — createEvent writes the nullable field that _mapDocToEvent casts. Null-check at the read boundary, or read through a typed model that does it once. Turning on strict-casts makes the compiler find these for you.
Hardcoded const [] placeholder lists create_page_hub.dart lines 560, 564, 595, 598 — four const <_HubItemData>[] sections A section that can never populate looks identical to an empty state. It reads as "no data yet" forever, to you and to a reviewer. Don't render the section until it has a real source. If the source is planned, leave the section out and put it in Linear.
Fake UI with unwired state calendar_page.dart lines 44–56 (hardcoded 'Friend 1', 'Ethan', 'Gym 1'; _filterStates never read by any query); direct_message_page.dart line 147 (RSVP that only calls setState); feed_page.dart line 779 (comment sheet's "Done" discards the input) The worst pattern on this list. It animates convincingly, so a demo viewer and a future you both believe the feature exists. This is why the app looks more finished than it is. Wire it or remove it. A missing feature is honest; a fake one is a trap you set for yourself.
Redeclared constants Color(0xFF4D7CFF) as a private const in 6+ files. The theme's actual seed colour (deepPurple) is never seen because every screen overrides it. One brand change becomes a six-file edit, and the MaterialApp theme is decorative. Fill core/constants/colors.dart and delete the copies as you touch each file.
setState after await with no mounted guard profile_page.dart lines 169, 208, 226, 250, 261 Exception if the user navigates away mid-request. Intermittent, hard to reproduce, and invisible without crash reporting. if (!mounted) return; immediately after every await that precedes a setState.
Developer instructions rendered as end-user UI channel_page.dart lines 205–257 — tells the user to run firebase login --reauth and firebase deploy --only firestore:indexes, with a copy-to-clipboard console URL A gym member sees a CLI tutorial. It also leaks the Firebase console URL for the project. Generic user-facing error; log the detail. Fix the missing index instead — see indexes.
Dead code left in place ~380 lines across social_page.dart (lines 544, 566, 1858 — three unreachable builders holding the repo's only two TODOs) and feed_page.dart lines 794–927. Plus _loadMessagesList, which still runs a query per joined gym for a tab that was deleted. It costs reads, it costs reading time, and it hides the two real TODOs in the repo where nobody will find them. Delete it. Git remembers.
N+1 sequential .get() in a loop friends_service.getFriendIdsWithNames; gyms_service member profiles; profile_page.dart lines 211, 235 Billed reads scale with friend count, and each failure is individually swallowed. Batch with whereIn chunks, or use the name already denormalised on the doc you're holding.
