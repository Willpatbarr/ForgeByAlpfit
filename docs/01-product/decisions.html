Decision Log

What this is: D1–D42 — every meaningful call, its tag, a one-line reason, and how hard it is to undo. Read the seven coin-flips at the top; skim the rest. If you disagree with a DECIDED row, say so and it moves — that's what the reversibility column is for.

Needs your eye — the seven coin-flips

Everything below is a genuine taste call, not a finding. The rest of this log is either forced by the notes (LOCKED) or forced by the code (DECIDED). These seven could go either way, I picked a side, and the side I picked is the one that costs a solo developer the least this quarter. This is where your editing attention belongs — everything else can be skimmed.
#The call I madeThe other side of the coinCost to flip it later
D5 Keep setState + StreamBuilder. Do not do a Riverpod migration. Riverpod was recommended twice in the old architecture notes and adopted zero times, and a working ~16,300-line app does not need rewriting for a solo dev. Introduce Riverpod only where state genuinely crosses screens. Riverpod would make the app testable in the way the empty feed MVVM folders imagined, and it would kill the two hand-rolled global singletons and the mutable module-level _currentRoute. If you were ever going to do it, doing it before 16,300 lines becomes 30,000 is cheaper. The most reversible-but-expensive call in the plan. Reversible any time; the price is weeks, and with zero tests there is no safety net for the refactor. If you flip this, write the tests first.
D7 Rename forge_senior_project_version/ to app/. The directory name is a daily reminder of a finished class, and it is baked into the Android app label and the iOS bundle name too. Cheap now, annoying later. It breaks every absolute path in your notes, your shell history, and any IDE config — for zero functional gain. Some people find renaming mid-project genuinely disorienting. Easy to do, easy to undo, but strictly cheaper the earlier it happens. Do it in the same commit as the bundle-id change (D33) so all the identity churn lands at once.
D15 Adopt five success metrics (SM1–SM5) — invented by me. The notes contain no success metric of any kind; the only definition of done in ~20 documents is "demo-able." See vision.html for the numbers. Metrics for a 30-person beta can be theatre, and a wrong target is worse than no target because it pulls the roadmap toward it. You may prefer to run the beta and then set numbers from what you see. Easy. They are words on a page until something measures them — and today nothing does.
D17 Promote the fixed 4-day "Multi" calendar view to a real 7-day week view. Two requirements docs asked for a week view; the Final Specs silently dropped it; the code shipped 4 days with no explanation. 4 days may have been a deliberate density choice — a real week on a phone is cramped, and you may have tried 7 and hated it. If so, that's a real answer, and the fix is to document 4 days rather than change it. Easy. It's a constant and a header layout.
D18 Split the audience's "new attendee" into two rows: the pre-visit prospect and the post-visit newcomer. The notes name three categories, one of which is the gym. The pre-visit case is the entire differentiator, so I gave it its own row. It's a framing invention, not something you wrote. Three types is simpler, and the prospect may just be "a new attendee on day zero" rather than a distinct person to design for. Easy — collapse two table rows in vision.html.
D19 Build the calendar source filter for real, rather than deleting it. Source attribution is an explicit requirement in the Initial Requirements, the colours already exist, and the merged stream already knows each event's owner. Deleting the fake popup takes ten minutes and removes a lie from the app immediately; building it properly takes a day. If the beta is one gym and five friends, nobody needs a filter yet. Easy either way. But leaving it as-is is not an option — H1 is a shipping screen full of a fictional person named Ethan.
D23 The first tests are Firestore rules tests and service unit tests — not widget or golden tests. The two things that can actually hurt a user are a rules hole and a silent write failure, and both are testable without a rendered frame. Widget tests would have caught H5 (the comment button that discards input) and H8 (the empty onPressed), which are exactly the class of bug this codebase is full of. A reasonable person starts there instead. Easy. Nothing about starting with rules tests prevents adding widget tests later.

#DecisionTagRationaleReversibility
D2 Goals are must-have, not a stretch goal. DECIDED CONFLICT The Final Specs call them a stretch; a full class design, a dedicated requirements doc, a shipped feed widget, and ~1,000 lines of the app's best code all say otherwise. Direction of travel wins. hard — already built and shipped
D4 The gym account type stays. The separate "gym software" and "trainer software" products are cut, not deferred. DECIDED CONFLICT It is the differentiator and it is already built. Gym-side capability lives as a lightweight account type inside Forge, not as separate software. hard — the account type is load-bearing in the data model
D6 Real external users are the target, via a BYU-I Rec Center beta. DECIDED That makes account deletion, moderation, and a privacy policy real T1 work rather than paperwork. Every store blocker in the platform table becomes a real deadline, not a hypothetical. moderate — abandoning it drops T1 scope but also drops the point
D8 Monetization is deferred. DEFERRED The only monetization signal in ~20 documents is one stretch line about a paid premium gym tier. Trigger: three separate gyms ask for something a free tier can't do. easy
D11 No workout programming. No meal planning. Exercises exist to describe a planned workout, never to prescribe one. LOCKED The author's own anti-scope, stated in the proposal and never retracted. Competing on programming means competing with funded apps on their strongest ground, for a product whose thesis is social. hard — it is the positioning
D12 "Public" means: visible to your friends, and to fellow members of gyms you belong to. There are exactly two visibility levels. DECIDED CONFLICT The notes give basic events and workout events different definitions of "private", and the Final Specs hint at "different levels of visibility, including public or private" without ever enumerating a third. The Firestore rules already implement a single coherent reading — adopt it and close the question. moderate — adding a level means a rules change and a migration
D13 The live in-progress workout session screen is deferred. DEFERRED It has a 6-bullet spec in an orphan document and appears in no requirements list — the largest unattributed scope in the corpus. It also pulls toward D11's anti-scope. Trigger: a beta tester asks to log a workout while doing it. easy
D14 No personal friend-to-friend post surface in v1. "Updates from friends" means "your friend scheduled something." DECIDED The Final Specs already demoted it to stretch, and a second user-generated-content surface doubles the moderation burden at a moment when moderation does not exist at all (moderation_service.dart is 0 bytes). easy
D15 Adopt success metrics SM1–SM5. PROPOSED Both intakes flag the same gap: no success metric exists anywhere. SM2 — the share of workout events with at least one accepted invitee — is the product thesis expressed as one number. Numbers here. easy
D16 The BYU-I Rec Center is a beta channel, not a validated design partner. DECIDED The one true stakeholder document is an ask list — what the student wanted from the gym — and contains zero gym-originated requirements. The formal proposal's stakeholder field literally reads "TBD". Treat gym-side requirements as unvalidated until a gym writes one down. easy — one real meeting changes it
D17 Promote the 4-day Multi view to a real 7-day week view. Year view stays cut. PROPOSED Week view was required by two docs and silently dropped by a third; the code shipped an unexplained 4 days. Year view was dropped too and nobody has missed it. easy
D18 Model four audiences: prospect, new attendee, consistent attendee, gym account. PROPOSED The notes name three categories (one is the gym). Splitting "new attendee" at the first-visit line gives the differentiator its own user to design for. easy
D19 Build the calendar source filter for real; do not delete it. PROPOSED It is an explicit requirement, the colours exist, and the merged stream already knows each event's owner. Leaving the fake version shipped is the only unacceptable outcome. easy

Architecture & tech

#DecisionTagRationaleReversibility
D1 Flutter + Firebase (Auth, Firestore, Storage). LOCKED ~16,300 lines already run on it. Not revisiting. The "future API gateway rewrite" one document declares is DEFERRED — trigger: a second client that isn't Flutter, or Firestore read cost past $25/mo. hard — no repository seam exists; a migration touches all 15 services and most of the UI
D5 Keep setState + StreamBuilder; no Riverpod migration. Introduce Riverpod only where state genuinely crosses screens. PROPOSED Recommended twice, adopted zero times, and the app works. A solo developer with zero tests should not rewrite a working app for architectural tidiness. Full both-sides above. moderate — reversible any time, priced in weeks
D20 Services stay as free functions in lib/services/. No repository interfaces, no DI container. DECIDED Follows directly from D5. The old architecture notes raised the services-location question and then declined to answer it, twice; di_providers.dart has been 0 bytes since day one. Abstraction nobody consumes is cost without benefit. moderate
D21 Fill core/ — errors, validators, date utils, converters, colours — before adding features. DECIDED Ten empty files are the direct cause of the recurring bugs: no error types → catch (_) {} everywhere; no validators → no email or date checking; no colour constant → "forge blue" redeclared in six files. This is the cheapest structural fix in the plan. easy
D22 Two repetition mechanisms both stay, with a documented boundary: Plans materialise real event docs for multi-week programmes; in-event recurrence handles simple repeats client-side. DECIDED Both ship and both work. Merging them is a rewrite with no user-visible payoff today. Merging is deferred — trigger: the first bug where a plan-generated event and a recurring event disagree about the same slot. moderate
D23 First tests are Firestore rules tests + service unit tests, not widget or golden tests. PROPOSED Zero tests exist and no test/ directory does either. The two failure classes that actually reach users are rules holes and silent write failures, and both are testable headlessly. Both sides above. easy

Data

#DecisionTagRationaleReversibility
D24 The Firestore layout as built is the layout: users/{uid} at root with events/goals/plans subcollections, directThreads/{id} at root, and gyms as user docs with membership in joinedGymIds. LOCKED It exists, it has indexes, and the rules encode it. Full field-by-field detail in 02-architecture/data-model.html. hard
D25 /users read stops being if true. Authenticated read at minimum; a narrower public projection if search needs one. DECIDED The single highest-severity item in the project. Today every user's email and contact info is readable unauthenticated by anyone with the project id, with no App Check. The inline comment justifies it for "friend lists, gym lists" — but the app only ever reads user docs while signed in, so the rule buys nothing and costs everything. easy — one line, plus verifying nothing anonymous depended on it
D26 Event startAt / endAt become required non-null on write. DECIDED They are nullable on write and non-null-cast on read — a guaranteed crash for any event saved without a start time, reachable with data the app itself writes. hard — needs a backfill for any existing null rows
D27 setDetails: [{reps, weight}] is the canonical exercise shape. The reader's top-level weight key is a bug, not a schema. DECIDED The creator writes setDetails; the mapper reads a weight field nobody writes, so the calendar renders blank weights for every workout ever created. Fix the reader, not the writer. easy
D28 Server timestamps replace client clocks on DMs, goals, and plans; rules validate against request.time. DECIDED Timestamp.now() from the client with no rule check means message ordering is spoofable and any clock-skewed device writes wrong history. easy
D29 Editing a goal must preserve periodHistory and current progress. DECIDED Today, renaming a goal destroys every past period and resets progress to zero — labelled in-code as "Edit behavior (v1)". No requirement ever said that was correct, and it silently deletes the only long-lived user data in the app. easy
D30 Owner-only writes stay. Inviting friends to edit a workout is therefore a data-model change, not a UI change. DECIDED CONFLICT The Initial Requirements ask for workout co-editing; the Final Specs drop it; the rules make it architectural — events live under users/{owner}/events with allow write: if request.auth.uid == userId. Anyone planning this as "add an invite button" will be wrong by an order of magnitude. It needs a location change or an invitee write scope, plus a conflict story. hard
D31 Introduce a typed Event model class. DECIDED lib/models/ contains exactly one file (goal.dart) and Goals is also the least buggy feature — that is not a coincidence. Event is the most-written entity in the app and it travels as a raw Map<String, dynamic>, which is how D26 and D27 happened. moderate
D32 Delete the user_preferences ruleset. DECIDED Full CRUD rules for a collection referenced nowhere in lib/. It is also the one collection the old rules doc bothered to document. Dead weight in a security-critical file. easy

Platform & release

#DecisionTagRationaleReversibility
D3 iOS + Android only. DECIDED CONFLICT Web, macOS, Windows and Linux targets exist because Flutter allows them, not because a user asked. Linux throws UnsupportedError today. DEFERRED — trigger: a gym admin asks to moderate from a desktop browser. easy — the scaffolds stay on disk
D9 Docs render via Cloudflare Pages. DECIDED Consistency with your other projects, even though Firebase Hosting is already configured. Firebase Hosting stays only if it is already load-bearing for the app itself. easy — static HTML, no build step
D33 Bundle identifiers move off com.example.* before anything leaves the machine. LOCKED Not a preference — Google Play and the App Store both reject com.example.* outright. The Android app label and iOS display name are placeholders too. hard — a bundle id is permanent once published, so pick carefully once
D34 Release builds get a real upload key. LOCKED Release currently uses signingConfigs.getByName("debug"). A debug-signed AAB cannot be uploaded to Play at all. hard — losing the upload key later is a genuine problem; back it up when you make it
D35 Portrait-only until a landscape layout actually exists. DECIDED iOS currently allows both landscape orientations on phone and all four on iPad, and no screen has a landscape layout. Allowing an orientation you haven't designed is a bug you ship. easy
D36 The committed Firebase client config stays committed. No key rotation. DECIDED Firebase client API keys identify the project; they do not authorise anything. Committing them is normal and acceptable. The real exposure is firestore.rules (D25), not the config file — and fixing the rules is what actually closes the hole. No cargo-culted "rotate your keys." easy
D37 Google Play is the first external channel; Apple follows. DECIDED $25 one-time versus $99/year, and it defers the Apple-specific blockers (guideline 1.2 report/block, 5.1.1(v) account deletion) by one milestone — though D6 means they all get built anyway. Matches the tiering in the service map. easy
