Decisions D1–D42, with status, rationale, and reversibility. Start with the seven open calls.

Needs your eye — the seven coin-flips

Everything below is a genuine taste call, not a finding. The rest of this log is either forced by the notes (LOCKED) or forced by the code (DECIDED). These seven could go either way, I picked a side, and the side I picked is the one that costs a solo developer the least this quarter. This is where your editing attention belongs — everything else can be skimmed.

D5 · State management PROPOSED

The call: keep setState + StreamBuilder. Do not do a Riverpod migration. It was recommended twice in the old architecture notes and adopted zero times, and a working ~16,300-line app does not need rewriting for a solo dev. Introduce Riverpod only where state genuinely crosses screens.

The other side: Riverpod would make the app testable in the way the empty feed MVVM folders imagined, and it would kill the two hand-rolled global singletons and the mutable module-level _currentRoute. If you were ever going to do it, doing it before 16,300 lines becomes 30,000 is cheaper.

Cost to flip: the most reversible-but-expensive call in the plan. Reversible any time; the price is weeks, and with zero tests there is no safety net for the refactor. If you flip this, write the tests first.

D7 · Rename the app directory PROPOSED

The call: rename forge_senior_project_version/ to app/. The directory name is a daily reminder of a finished class, and it is baked into the Android app label and the iOS bundle name too. Cheap now, annoying later.

The other side: it breaks every absolute path in your notes, your shell history, and any IDE config — for zero functional gain. Some people find renaming mid-project genuinely disorienting.

Cost to flip: easy to do, easy to undo, but strictly cheaper the earlier it happens. Do it in the same commit as the bundle-id change (D33) so all the identity churn lands at once.

D15 · Success metrics SM1–SM5 PROPOSED

The call: adopt five success metrics (SM1–SM5) — invented by me. The notes contain no success metric of any kind; the only definition of done in ~20 documents is "demo-able." See vision.html for the numbers.

The other side: metrics for a 30-person beta can be theatre, and a wrong target is worse than no target because it pulls the roadmap toward it. You may prefer to run the beta and then set numbers from what you see.

Cost to flip: easy. They are words on a page until something measures them — and today nothing does.

D17 · 7-day week view PROPOSED

The call: promote the fixed 4-day "Multi" calendar view to a real 7-day week view. Two requirements docs asked for a week view; the Final Specs silently dropped it; the code shipped 4 days with no explanation.

The other side: 4 days may have been a deliberate density choice — a real week on a phone is cramped, and you may have tried 7 and hated it. If so, that's a real answer, and the fix is to document 4 days rather than change it.

Cost to flip: easy. It's a constant and a header layout.

D18 · Split the audience PROPOSED

The call: split the audience's "new attendee" into two rows — the pre-visit prospect and the post-visit newcomer. The notes name three categories, one of which is the gym. The pre-visit case is the entire differentiator, so I gave it its own row.

The other side: it's a framing invention, not something you wrote. Three types is simpler, and the prospect may just be "a new attendee on day zero" rather than a distinct person to design for.

Cost to flip: easy — collapse two table rows in vision.html.

D19 · Calendar source filter PROPOSED

The call: build the calendar source filter for real, rather than deleting it. Source attribution is an explicit requirement in the Initial Requirements, the colours already exist, and the merged stream already knows each event's owner.

The other side: deleting the fake popup takes ten minutes and removes a lie from the app immediately; building it properly takes a day. If the beta is one gym and five friends, nobody needs a filter yet.

Cost to flip: easy either way. But leaving it as-is is not an option — H1 is a shipping screen full of a fictional person named Ethan.

D23 · Which tests come first PROPOSED

The call: the first tests are Firestore rules tests and service unit tests — not widget or golden tests. The two things that can actually hurt a user are a rules hole and a silent write failure, and both are testable without a rendered frame.

The other side: widget tests would have caught H5 (the comment button that discards input) and H8 (the empty onPressed), which are exactly the class of bug this codebase is full of. A reasonable person starts there instead.

Cost to flip: easy. Nothing about starting with rules tests prevents adding widget tests later.

  • D1 — ~16,300 lines already run on it. Not revisiting. The "future API gateway rewrite" one document declares is DEFERRED — trigger: a second client that isn't Flutter, or Firestore read cost past $25/mo. No repository seam exists, so a migration touches all 15 services and most of the UI.

The old architecture notes raised the services-location question and then declined to answer it, twice; di_providers.dart has been 0 bytes since day one.   • D21 — Fill core/ — errors, validators, date utils, converters, colours — before adding features. Ten empty files are the direct cause of the recurring bugs: no error types → catch (_) {} everywhere; no validators → no email or date checking; no colour constant → "forge blue" redeclared in six files. Both ship and both work, and merging them is a rewrite with no user-visible payoff today.   • D23 — Zero tests exist and no test/ directory does either. The two failure classes that actually reach users are rules holes and silent write failures, and both are testable headlessly. Both sides above.

  • D24 — The layout as built: users/{uid} at root with events/goals/plans subcollections, directThreads/{id} at root, and gyms as user docs with membership in joinedGymIds. It exists, it has indexes, and the rules encode it. Full field-by-field detail in 02-architecture/data-model.html.
  • D25 — Authenticated read at minimum; a narrower public projection if search needs one. Today every user's email and contact info is readable unauthenticated by anyone with the project id, with no App Check. The inline comment justifies it for "friend lists, gym lists" — but the app only ever reads user docs while signed in, so the rule buys nothing and costs everything. Easy to fix: one line, plus verifying nothing anonymous depended on it.
  • D26 — They are nullable on write and non-null-cast on read — a guaranteed crash for any event saved without a start time, reachable with data the app itself writes. Any existing null rows need a backfill.
  • D27 — The creator writes setDetails; the mapper reads a weight field nobody writes, so the calendar renders blank weights for every workout ever created. Fix the reader, not the writer.
  • D28 — Rules validate against request.time. Timestamp.now() from the client with no rule check means message ordering is spoofable and any clock-skewed device writes wrong history.
  • D29 — Today, renaming a goal destroys every past period and resets progress to zero — labelled in-code as "Edit behavior (v1)". No requirement ever said that was correct, and it silently deletes the only long-lived user data in the app.
  • D30 — Inviting friends to edit a workout is therefore a data-model change, not a UI change. The Initial Requirements ask for workout co-editing; the Final Specs drop it; the rules make it architectural — events live under users/{owner}/events with allow write: if request.auth.uid == userId. Anyone planning this as "add an invite button" will be wrong by an order of magnitude. It needs a location change or an invitee write scope, plus a conflict story.
  • D31 — lib/models/ contains exactly one file (goal.dart) and Goals is also the least buggy feature — that is not a coincidence. Event is the most-written entity in the app and it travels as a raw Map<String, dynamic>, which is how D26 and D27 happened.
  • D32 — Full CRUD rules for a collection referenced nowhere in lib/. It is also the one collection the old rules doc bothered to document. Dead weight in a security-critical file.
