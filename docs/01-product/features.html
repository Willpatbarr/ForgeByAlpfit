Looks done, isn't

These nine are the highest-value work in the entire plan. Each one renders, animates, and responds to taps. A demo viewer would touch every one of them and conclude the feature is finished. None of them are. They are more urgent than any new feature, because they are the failures a beta tester will hit in the first ten minutes and quietly decide the app is broken.

H1 · Calendar source filter

What you see: a filter popup listing "You", "Friend 1", "Ethan", "Gym 1" with colour chips and toggles that respond.

What actually happens: entirely fake. The names are hardcoded literals — "Ethan" is not a user, it is a string. _filterStates is written by the toggles and never read by any query. Toggling changes nothing.

Where: calendar_page.dart:44-56

H2 · Create-hub item detail sheet

What you see: tap an item in the Create hub, a sheet slides up.

What actually happens: the sheet says "Details for this item will open here when connected to your data." It is a literal placeholder string shipped in the app.

Where: event_creator_page.dart:289

H3 · Create hub: 4 of 12 sections

What you see: "From Your Gyms" and "From Your Friends" under both Goals and Plans — headers, layout, empty state.

What actually happens: empty by construction. All four are const <_HubItemData>[]. They can never populate, no matter how many gyms or friends you have. Separately, "Popular Workouts/Goals/Plans" are just your own items — no popularity signal exists anywhere in the app.

Where: create_page_hub.dart:560,564,595,598

H4 · DM event-invite RSVP

What you see: an event invite arrives as a chat bubble with Attend / Decline. Tapping animates convincingly.

What actually happens: 100% cosmetic. onSideTapped calls setState and nothing else. No write, no notification to the inviter, gone on navigation. The file's own header comment admits it: "Local-only RSVP chip state … (not persisted)". This is also the thing that makes SM2 unmeasurable.

Where: direct_message_page.dart:7,33,147

H5 · Feed comment "Done" button

What you see: type a comment, tap Done, the sheet closes.

What actually happens: the typed text is discarded. Only onSubmitted (the keyboard return key) actually posts. The most natural gesture is the one that loses your comment.

Where: feed_page.dart:779

H6 · Deleting your own channel post

What you see: a delete affordance on posts and comments in a gym channel.

What actually happens: permission bug. isCurrentUserGymOwner is literally uid == gymUid, so a post's own author cannot delete their own post or comment unless they are the gym. Meanwhile the Firestore rule's unconstrained allow update lets any joined member rewrite any post's content.

Where: channel_posts_service.dart:357, firestore.rules

H7 · Profile save

What you see: edit your name or contact info, tap save, get a success confirmation.

What actually happens: failures are swallowed. catch (_) {} around an optimistic write — the UI reports success for a write that never landed. Same pattern at four sites in one file, plus friends_service, gyms_service, and plan_creator_sheet.

Where: profile_page.dart:91,374,721,1002

H8 · "View in Workouts Screen"

What you see: a button on the calendar event sheet.

What actually happens: the onPressed body is a single comment. Tapping does nothing at all. (Nearby, _getEventsForDate is dead code that return [].)

Where: calendar_page.dart:1314

H9 · The core/ layer and the feed MVVM layer

What you see: a clean feature-based architecture with errors, validators, converters, date utils, and a feed repository/DTO/viewmodel/state stack.

What actually happens: 21 of 58 Dart files are 0 bytes. That includes all of core/errors, all of core/util, all of core/constants except one, core/firebase/converters.dart, di_providers.dart, and every one of the seven feed MVVM files. There are no error types, no validators, no date utils, and no converters — which is precisely why H7 exists.

Where: filesystem; see the empty-file list in the code intake

Two more that belong to the same family but are cleanup rather than repair: channel_page.dart:205-257 ships Firebase CLI instructions to end users ("run firebase login --reauth") when an index is missing, and roughly 500 lines of dead widget builders remain across feed_page, social_page, and calendar_page — one of which still runs a per-gym Firestore query on every page load for a tab that no longer exists.

Built but never specified

The risk is not that they're bad — several are the best code in the app. The risk is that nothing defines correct behavior, so nobody can say whether a given bug is a bug.

Open question: the 5×6 feed widget grid

The published grid math does not close. DEFERRED — trigger: before building any new feed widget.

The Feed Page Widget Modules doc defines a 5×6 grid (5 horizontal 0–4, 6 vertical 0–5) where position is the top-left cell a widget occupies, plus three current widgets: Next Workout p=0:0 h=3 w=4 · Goals p=0:2 h=2 w=4 · Friends p=4:0 h=4 w=1.

The row:col versus col:row convention is never stated, and under either reading these overlap or exceed the 5×6 bounds — a widget at 0:0 with height 3 collides with one at 0:2 on one reading, and runs off the edge on the other. Meanwhile the shipped feed does not use the grid at all: buildBasicFeedWidget at feed_page.dart:92 is dead code and the layout is hardcoded.

Do not resolve this by guessing. One sentence from you — "position is row:col" or "col:row" — settles it. Until then, no new widget should be built on the abstraction, because whichever convention gets assumed will silently become the convention forever.
