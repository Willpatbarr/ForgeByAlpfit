What this is: every feature the notes ever asked for, reconciled against what the Flutter code actually does — with a priority and a build state on each row. This is the page you plan from. Where the docs and the code disagree, the code wins and the doc is the contradiction.

Looks done, isn't

These nine are the highest-value work in the entire plan. Each one renders, animates, and responds to taps. A demo viewer would touch every one of them and conclude the feature is finished. None of them are. They are more urgent than any new feature, because they are the failures a beta tester will hit in the first ten minutes and quietly decide the app is broken.

Built but never specified

Eight substantial features exist in the code with no requirement, no user story, and no acceptance criterion anywhere in ~20 documents. The risk is not that they're bad — several are the best code in the app. The risk is that nothing defines correct behavior, so nobody can say whether a given bug is a bug.

FeatureWhy it's a riskAction
Goals ~1,000 lines; the app's most polished feature The only spec is an AI-generated class design doc that appears in no requirements list, and the governing Final Specs calls goals a stretch. Meanwhile updateGoalForCurrentUser wipes periodHistory on edit — is that a bug or "Edit behavior (v1)"? Nothing says. Write acceptance criteria for check-in, rollover, archive, and edit. Four sections are permanently empty (H3), "Popular" means "yours", widget.isGym is dead, and the date window is computed once in initState and never refreshed. Decide what the hub is for before fixing it. If the answer is "browse and reuse your own stuff", delete the gym/friend/popular sections rather than filling them.
Recurrence engine weekly / monthly / every-other-day / custom-weekly Undocumented, and it competes with Plans: recurrence expands one stored doc into N rendered occurrences client-side, while Plans materialize real event docs. Two repetition mechanisms with no stated boundary. No timezone handling in either. Document both, state which is used when (D22), and defer merging them until they visibly disagree.
Friend-request-as-DM The entire friendship handshake runs through directThreads with a messageKind: 'friend_request', and the Firestore rules encode the protocol. No doc mentions it. There is no pending state in the UI, so users fire duplicate requests until the service throws. Document the state machine (request → accept/decline → friends), then add the pending state.
Event-invite deep links Invites arrive as DMs carrying eventId + eventOwnerUid and deep-link into the calendar via router query params. Undocumented, and the RSVP at the other end is fake (H4). Spec the invite lifecycle end to end. This is the thesis feature — it deserves the only sequence diagram in the project.
Unread badging Live unread counts on the bottom nav and gym rows, driven by an unreadCounts map that either participant can rewrite (the rules allow it). No spec for when a thread is "read." Define read semantics; constrain the rule so a participant can only decrement their own count.
Avatar pipeline Storage upload + a three-layer cache + an http.get fallback for Flutter web CORS. Genuinely clever and completely undocumented. avatarUrl is written to the user doc and never read — every avatar re-resolves from Storage by uid. No upload size or MIME cap. Document it, then either use avatarUrl or stop writing it. Add a size cap — there is currently none.

Open question: the 5×6 feed widget grid

The published grid math does not close. DEFERRED — trigger: before building any new feed widget.

The Feed Page Widget Modules doc defines a 5×6 grid (5 horizontal 0–4, 6 vertical 0–5) where position is the top-left cell a widget occupies, plus three current widgets: Next Workout p=0:0 h=3 w=4 · Goals p=0:2 h=2 w=4 · Friends p=4:0 h=4 w=1.

The row:col versus col:row convention is never stated, and under either reading these overlap or exceed the 5×6 bounds — a widget at 0:0 with height 3 collides with one at 0:2 on one reading, and runs off the edge on the other. Meanwhile the shipped feed does not use the grid at all: buildBasicFeedWidget at feed_page.dart:92 is dead code and the layout is hardcoded.

Do not resolve this by guessing. One sentence from you — "position is row:col" or "col:row" — settles it. Until then, no new widget should be built on the abstraction, because whichever convention gets assumed will silently become the convention forever.
