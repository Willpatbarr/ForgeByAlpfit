GitHub DECIDED T0 Now

What this is: the runbook for the code host — the private repo (already exists) and GitHub Actions for build + test (does not exist yet). The one urgent item here is confirming the repo is actually private, because the committed Firebase config plus allow read: if true means a public repo is a live data exposure.

1. What & why

GitHub stores the only copy of Forge's source that isn't on his laptop, at github.com/Willpatbarr/ForgeByAlpfit. Later it runs the CI that answers the only two questions worth automating for a solo developer: does it build and do the tests pass.

Alternative consideredOne-line reason it lost
GitLabMore CI minutes on the free tier, but he already has a GitHub account and the repo already lives there — moving buys nothing.
Codemagic / Bitrise (Flutter-specialist CI)Genuinely better at Flutter mobile builds, but a second vendor and a second config file for a project that doesn't yet have one test to run.
No CI at all, just pushViable today and honestly close to correct — but the moment a build breaks on a tester's device instead of his, "it built on my machine" stops being an answer.

Why GitHub wins: the repo is already there, Actions is in the same box with nothing extra to sign up for, and the free private-repo tier is genuinely unlimited.

4. Setup steps

  1. GitHub account exists; repo exists at Willpatbarr/ForgeByAlpfit. Done
  2. Confirm the repo is Private. Settings → General → scroll to Danger Zone → "Change repository visibility". Verify today — see the callout below. Nothing else on this page matters until this is answered.
  3. Fix .gitignore. It is the stock Flutter template. It correctly ignores build output; it does not ignore .env, *.jks, *.keystore, *.p8, *.p12, or *-service-account*.json. Add those lines before the signing keys from Google Play and Apple ever land on disk. The Firebase config files stay tracked on purpose — see why.
  4. Create .github/workflows/ci.yml — the directory does not exist yet. One job, ubuntu-latest, triggered on push and pull_request:
    subosito/flutter-action (pin the channel to stable) → flutter pub get → flutter analyze → flutter test → flutter build apk --debug.
    Set working-directory: forge_senior_project_version — the Flutter project is not at the repo root. Note if D7 (rename to app/) is accepted, this path changes with it.
  5. Stay on Linux runners. Do not add a macos-latest job. See the rate table above.
  6. Tighten the analyzer so CI means something. analysis_options.yaml is one line. Add analyzer: language: strict-casts: true. Without it, flutter analyze passes on the unchecked as Timestamp / as List<String> casts that are known crash paths — a green CI badge that proves nothing is worse than no badge.
  7. Add secrets only when needed at Settings → Secrets and variables → Actions. None are needed for a build-and-test workflow. See Secrets & config.
  8. Verify: deliberately push a commit with a syntax error on a branch and confirm the Actions run goes red. Then revert and confirm it goes green. A workflow that has only ever passed has not been tested.
Painful to change later / urgent: if Willpatbarr/ForgeByAlpfit is public right now, then the committed google-services.json plus firestore.rules' allow read: if true on /users means anyone who found the repo can dump every user's email and contact info. The config files are not the problem and rotating them is not the fix — fix the rule (M1) and flip the repo private. Also note: making a repo private does not retract forks or clones that already exist.
Also painful to change later: the repo name and owner appear in every clone URL, in the Cloudflare Pages build connection, and in any Linear/GitHub link. Renaming works (GitHub redirects) but re-breaks the Pages connection.

Actions secrets are write-only once saved — GitHub masks them in logs, but a workflow can still echo a secret out if you write it that way. Never echo a secret, and never let a fork-triggered workflow read one.

6. Escape hatch

Lock-in: LOW

QuestionAnswer
What data lives only here?Almost nothing. Git history is fully distributed — every clone is a complete copy. The GitHub-only data is Issues, PR discussion, Releases, and Actions run history. Forge uses Linear for issues, so GitHub-only data is close to zero.
How do I export?git clone --mirror gets everything that matters. Settings → Migrations, or the REST API, exports issues/PRs if they ever get used.
What does migrating cost?An afternoon. Push the mirror to GitLab/Codeberg, rewrite one workflow file into their CI syntax, reconnect Cloudflare Pages. Nothing in the Flutter code knows GitHub exists.
Sticky bitsActions YAML is GitHub-specific (rewrite, not port). The Cloudflare Pages build connection is tied to the GitHub repo and has to be re-made.

7. Cost & scale checkpoints

GitHub costs scale with developers and CI activity, not with app users. The user-count columns are here for consistency, and the honest answer in all three is "unchanged".

~10 users$0Nothing. Perhaps 20–40 CI runs/month at ~5 min each on Linux ≈ 200 min, i.e. 10% of the free budget.
~100 users (beta)$0Nothing from users. The pressure comes from release cadence: if beta feedback drives daily builds, 2,000 Linux minutes is still comfortable — roughly 400 five-minute runs.
~1,000 users$0, unless macOS CI is addedStill nothing from user count. The only realistic way to blow the budget is adding a macos-latest iOS build job: at ~$0.062/min that is ~194 minutes of headroom, i.e. roughly a dozen iOS builds before the hard stop. If that becomes the bottleneck, GitHub Pro at $4/mo (3,000 min) is the cheapest fix — or keep iOS builds local.

8. Teammate delta

QuestionAnswer
Extra seat cost$0. Collaborators on a personal-account repo are free; GitHub Free's private repos are listed as unlimited-collaborator.
Does the free tier allow another member?Yes. Settings → Collaborators → Add people. No org, no billing, no seat count.
Permission modelPersonal repos give collaborators a single level: write access to everything. There is no Read/Triage/Maintain gradation without moving to an Organization (also free). If a teammate should not be able to force-push main, that is the reason to create a free org.
What actually changesTwo things stop being optional: (1) branch protection on main — a GitHub Free feature for public repos, requiring an org or Pro for private ones, so verify before promising it; (2) the CI workflow, which stops being a nicety and becomes the shared definition of "not broken".
Actions minutesStill 2,000/month — the budget is per account owner, not per person. Two developers pushing means the same pool drains twice as fast.
