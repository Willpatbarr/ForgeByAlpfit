Forge docs / Services / Cloudflare Pages

Cloudflare Pages DECIDED T1 Before first real user

What this is: the runbook for the static host that renders this docs/ folder and — the part that makes it T1 rather than cosmetic — hosts the privacy policy and the account-deletion request page that both app stores require by URL. Without those two pages, neither store accepts the app.

1. What & why

Cloudflare Pages serves static files straight from a Git branch, so pushing to docs/ publishes the plan you're reading. Its second job is the one with a deadline attached: Apple requires a privacy policy URL for every app, and Google Play requires both a privacy policy URL and a separate publicly-reachable web page where a user can request account deletion. Forge has no privacy policy anywhere in the repo or the UI. Those pages need somewhere to live, and it is the same somewhere.

Alternatives considered, and why each lost:

  • Firebase Hosting (already configured!) — the genuinely tempting option: firebase.json already has a hosting block and it has been deployed at least once. It loses to D9, which puts docs on Cloudflare for consistency with his other projects. Worth noting the configured block points at build/web, the Flutter web build, and D3 cut web as a target — so Firebase Hosting is currently pointed at something nobody ships. It is not load-bearing and can be left dormant.
  • GitHub Pages — free and about as simple; loses on D9 consistency and on custom-domain/edge flexibility.
  • Netlify / Vercel — equivalent for a static folder, but another vendor for no gain.
  • A page inside the Flutter app — doesn't work: the store forms require a URL reachable before install, by a reviewer who hasn't downloaded anything.

Why Cloudflare Pages wins: D9 DECIDED for consistency, and the free tier has no bandwidth or request charges at all — which for a public privacy-policy URL means no surprise anything.

2. Adoption trigger

Docs rendering — T1 (could be T0 — it costs 15 minutes)

Trigger: whenever he wants to read this plan on a phone instead of opening local files. No urgency, no cost, no risk.

Privacy policy + account-deletion page — T1 Before first real user MUST

Trigger: hard-required by both stores before submission — part of M4, Beta-ready. Not paperwork: with D6 putting real external users in the beta, these are the documents that make collecting their emails legitimate.

When NOT to do more: no Cloudflare Workers, no KV, no D1, no Access rules, no Zero Trust, no analytics beyond what Pages gives free. Pages here is a file server. The moment it starts running code, it stops being the zero-maintenance choice that made it worth adopting.
One honest sequencing note: hosting is the easy half. Writing a privacy policy that accurately describes what Forge collects — emails, display names, contact info, avatars, DMs, channel posts, crash data — is the actual work, and it has to match the Apple App Privacy questionnaire and the Play Data safety form or the mismatch is itself a rejection reason. Budget for the writing, not the deploy.

Platform-direction caveat, stated once. Cloudflare has publicly confirmed that Pages and Workers are converging into a single platform, with a migration guide from Pages to Workers Static Assets. There is no deprecation notice for Pages in current docs, and Cloudflare says existing projects keep working without users lifting a finger. PROPOSED stay on Pages — it is the simpler product, D9 named it, and the migration path is documented. Revisit if Cloudflare publishes an actual deprecation date. Verify at the Cloudflare convergence post.

4. Setup steps

Nothing here is done. No Cloudflare project exists and there is no privacy policy in the repo.

  1. Create a free Cloudflare account at dash.cloudflare.com/sign-up. No card required, no domain required to start.
  2. Workers & Pages → Create → Pages → Connect to Git, authorise GitHub, and select Willpatbarr/ForgeByAlpfit. Note if the repo is private this is the one external service granted read access to the source — a reason to scope the GitHub App to that single repository rather than all repos.
  3. Configure the build as "no build". Framework preset: None. Build command: empty. Build output directory: docs. Production branch: whichever branch is authoritative. This site is hand-written HTML plus one CSS file — do not add a static site generator, and note that an empty build command uses fewer of the 500 monthly builds' wall-time.
  4. Deploy and confirm the *.pages.dev URL renders docs/index.html with assets/forge.css applied. The relative paths in these pages (../assets/forge.css) only work if the output directory is docs, not the repo root — this is the step that usually goes wrong.
  5. Decide the domain. Not yet determined — needs a decision. No domain is named anywhere in the intake. Options: use the free *.pages.dev subdomain (legitimate for a store submission, just less polished), or register something like alpfit.app. A custom domain is the one line item on this page that could cost money — typically $10–15/year for a domain, and $0 for Cloudflare itself. Flag for William.
  6. Write the privacy policy at docs/legal/privacy.html. It must honestly describe what Forge collects: email and display name (Auth + users doc), optional contact info, avatar images (Storage), workout events, goals, plans, channel posts, direct messages, and — once Crashlytics lands — crash diagnostics. Include a contact address; Apple's guideline 1.2 requires published contact information for UGC apps anyway.
  7. Write the account-deletion request page at docs/legal/delete-account.html. Google Play requires a web URL where deletion can be requested, in addition to the in-app path. State what gets deleted, what is retained and for how long, and give a working contact route. This page is a Play submission field, not a nicety.
  8. Write terms of use at docs/legal/terms.html — Play's UGC policy requires users to accept terms that define objectionable content. Registration currently has no ToS or consent step at all.
  9. Paste the resulting URLs into App Store Connect (privacy policy URL) and Play Console App content (privacy policy URL + deletion request URL).
  10. Verify — three checks:
    (a) Push a trivial docs change and confirm the live site updates within a couple of minutes.
    (b) Open the privacy policy URL in a private window on a phone — that is exactly how a store reviewer will open it, and a URL that 404s or requires login is a rejection.
    (c) Confirm the deletion-request page is reachable without installing the app.
Painful to change later: the custom domain, once it is published in two store listings and a privacy policy that users have agreed to — changing it means updating both store submissions. The *.pages.dev subdomain is derived from the project name, so name the Pages project deliberately (forge-docs, not forgebyalpfit-2). Everything else here is cheap to redo.

The real risk on this page is the opposite of a leaked key: it is publishing something you meant to keep internal. Cloudflare Pages makes the entire docs/ tree world-readable. This documentation set currently contains a detailed, itemised description of unpatched security holes in a live Firebase project — including the exact rule that leaves /users world-readable. Do not deploy docs/ publicly until M1 is closed, or exclude the security-detail pages, or put Cloudflare Access in front of the site. Publishing the map to an unlocked door is worse than leaving it in a local folder.

6. Escape hatch

Lock-in: LOW — the lowest on the entire service map.

  • What data lives only here — nothing. Every byte Pages serves is a file in the Git repo. Cloudflare holds deployment history and traffic analytics, which are diagnostics.
  • How to export — you already have it. git clone is the export.
  • What migrating costs — ten minutes. Point GitHub Pages, Netlify, or Firebase Hosting at the same docs/ folder. No build step to port, no config to translate. Nothing in lib/ knows Cloudflare exists.
  • The only sticky thing — the published URL, because it appears in two store listings and in a privacy policy users have agreed to. Owning a custom domain (rather than using *.pages.dev) makes even that portable: point the DNS elsewhere and the URL survives the move. That is a decent argument for buying the domain.

  • ~10 users — traffic is him.
  • ~100 users — requests and bandwidth are unmetered on Free, so even if every beta tester reads the privacy policy the cost line does not move. The deletion-request page starts receiving real requests, and someone has to act on them within a reasonable time.
  • ~1,000 users — this is the only service on the map that is genuinely free at every scale, because static-asset serving has no metered egress. The 500-builds/month cap remains the sole theoretical limit and it scales with his commit rate, not with users. Compare Firestore at ~$25–40/mo for the same user count.

8. Teammate delta

Extra seat cost$0 — dashboard membership is never per-seat billed

What actually changesAlmost nothing, which is the point
  • Extra seat cost — Cloudflare's own docs: a Pages site "can be managed by an unlimited number of users via the Cloudflare dashboard".
  • Does the free tier allow another member — do not confuse this with the widely-quoted "50 free users" figure; that is Cloudflare Zero Trust seats, a different product.
  • Permission model — in practice a teammate usually needs no Cloudflare access at all: they push to GitHub and the site rebuilds. Grant dashboard access only to whoever manages the domain.
  • What actually changes — the only shared-state gotcha is the 500 builds/month account-wide budget. Two people pushing docs changes drains a shared pool, and if the account also hosts other projects that pool is smaller than it looks.

What to do next

Write the privacy policy — not the deploy. Hosting takes fifteen minutes and can happen any time; the policy is a real document that has to match what the app actually collects, and both stores block on it.
  1. Before deploying docs/ publicly, close M1 — this documentation describes an unpatched, exploitable rule in a live project, and Pages makes the whole folder world-readable.
  2. Then connect the repo with build output docs and an empty build command, and confirm the CSS resolves on the *.pages.dev URL.
  3. Decide the domain question (*.pages.dev vs a bought domain) before the URL goes into two store listings — flag for William.
  4. Add docs/legal/delete-account.html; it is a required Play Console field, not an optional page.
