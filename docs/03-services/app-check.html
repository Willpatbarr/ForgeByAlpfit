Firebase App Check

What this is: the setup, rollout order, and stakes for App Check — the toggle that closes Forge's open user-directory scraping hole before real users arrive.

What & why

App Check attests that a request hitting Firestore or Storage came from a genuine, unmodified build of the Forge app, not from a script holding a copied API key. For this app specifically, it closes a hole that exists right now: the web API key lives in lib/firebase_options.dart, is committed to the repo, and is extractable from the deployed web bundle — combined with the fully-open users read rule, anyone with that key can scrape the entire user directory (names, emails, contact info) today.

Alternative consideredWhy it lost
Do nothing, rely on key secrecyThe key isn't secret by design — access is meant to be governed by rules, not by hiding it. The as-built audit confirms the open users read rule plus the committed key is a real scraping vector today.
Custom server-side request validationWould require standing up Cloud Functions, forcing the Blaze pay-as-you-go plan. The plan deliberately avoids Functions.

Why App Check wins: it's the only fix that closes the hole without standing up a server.

Setup steps

  1. In the Firebase console, open App Check and register each app — Android, iOS, web — against an attestation provider.
  2. Android: Play Integrity API as the provider.
  3. iOS: DeviceCheck / App Attest as the provider.
  4. Web: create a reCAPTCHA Enterprise site key and wire it into the App Check web initialization.
  5. Enable the debug provider for local development and generate a debug token. This is the step that trips people up — without it, a local or emulator build cannot reach Firestore at all once App Check is anything but fully open.
  6. Add each developer's debug token to the App Check allow-list in the console; a token is per machine, not shared.
  7. Deploy Firestore + Storage enforcement in monitoring/unenforced mode first — requests are scored but never blocked.
  8. Verify: open the App Check metrics tab, confirm the real app's requests show as verified, then only after that flip Firestore + Storage enforcement on.
Rollout order matters: register apps → run in monitoring/unenforced mode → check the metrics tab → only then enforce. Enforcing before monitoring can lock William out of his own app, with no warning it was about to happen.

Play Integrity / DeviceCheck credentialsManaged by Google Play Console / Apple Developer accounts, not app-side valuesN/AN/A

App Check itself introduces no server secret — it is a console configuration plus a client SDK call, not a custom backend. The one value that must stay out of any committed file is the debug token: a leaked debug token would let anyone bypass enforcement entirely, defeating the point. If it needs a placeholder anywhere, .env.example should show the variable name only, never a real token.

What To Do Next

  1. Register all three app platforms in App Check and turn on monitoring mode before anyone else touches the app.
  2. Check the metrics tab and confirm real traffic verifies before flipping enforcement on.
  3. Once enforced, re-test the login and feed flows described in firebase.html to confirm normal app use still works end to end.
