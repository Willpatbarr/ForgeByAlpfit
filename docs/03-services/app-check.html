Firebase App Check DECIDED T1 Before first real user

Runbook for verifying genuine Forge clients with Firebase App Check.

1. What & why

App Check attests that a request to Firestore or Storage came from an unmodified build of Forge on a genuine device — using Apple's App Attest on iOS and Google's Play Integrity on Android — and lets the backend reject everything else. For Forge specifically it closes the "someone read the project ID out of the app binary and started scripting against my database" hole, which matters because Forge's Firestore is directly client-facing with no server in front of it.

Alternatives considered, and why each lost:

  • Security rules alone — not actually an alternative; it is the layer underneath and it is mandatory either way. Rules answer "is this user allowed?"; App Check answers "is this even the app?" You need both, and rules come first.
  • An API gateway in front of Firestore — would work, and would also mean writing and hosting a server, the exact rewrite D1 defers. App Check buys most of the benefit for an afternoon of work and $0.
  • Obfuscating the API key — doesn't work. Firebase client config is extractable from any shipped binary by design; hiding it is theatre.

Why App Check wins: it is free, it is first-party, and it is the only thing on the list that reduces attack surface without adding a server.

2. Adoption trigger

Tier: T1 Before first real user

Trigger: before anyone who isn't him has the app on their phone — i.e. before M3, Ship to a device that isn't his, and hard-required by M4, Beta-ready.

Why this tier and not another: the moment real people's emails and messages are in the database, "anyone with the project ID can script against it" stops being a theoretical finding. It is T1 rather than T0 only because it requires real bundle IDs and store registrations that don't exist yet.

App Check depends on the final Android package name and iOS bundle ID. Order: fix the rules (M1) → fix the bundle IDs (M2/M3) → configure App Check.
The trap this page exists to prevent. App Check does not fix allow read: if true on /users. A rule that permits unauthenticated reads still permits them from an attested app — and getting an attested token is a matter of running the real app. App Check narrows who can knock. Rules decide what opens. Forge's door is currently unlocked, and App Check is a doorman, not a lock. Fix the rule first. If only one of the two ever gets done, it must be the rule.

First paid tierThere isn't one for App Check—
  • App Check itself — one of Firebase's always-free products, and it does not force a Blaze upgrade. There is no App Check meter to exceed.
  • Play Integrity API — the default quota is 10,000 token requests/day plus 10,000 server-side token decryptions/day. Classic requests and standard token preparations share one pool; they are not separate allowances. Once the quota is gone, attestation starts failing, and with enforcement on that means Android users get denied. Quota increases require linking a Google Cloud project in Play Console and can take up to a week to approve, so request headroom before you need it.
  • First paid tier — Play Integrity's docs state no pricing at all; whether standard vs classic requests differ in cost is unverified. Verify at developer.android.com/google/play/integrity/setup.
No surprise-bill risk. App Check cannot generate a bill. The failure mode is the opposite: a quota stop that locks out real users. 10,000 Play Integrity requests/day is generous for a beta but it is a real ceiling, and unlike a bill it fails closed. Note also that App Check token TTL is a lever — shorter TTLs mean more re-attestation and faster quota burn. Leave the default alone.

4. Setup steps

Nothing here is done. Prerequisites: real bundle IDs on both platforms, an Apple Developer Program membership (App Attest needs a real App ID), and a Play Console app entry (Play Integrity is linked through it). That dependency chain is why this is T1, not T0.

  1. Fix the security rules first. allow read: if true on /users, unconstrained channelPosts update, no field validation. Do not start this runbook until M1 is closed. App Check on top of open rules is a false sense of safety.
  2. Set real bundle IDs — Android applicationId and iOS bundle identifier, replacing com.example.*. Re-register both apps in the Firebase console and regenerate google-services.json, GoogleService-Info.plist, and firebase_options.dart with flutterfire configure.
  3. Add the package: flutter pub add firebase_app_check. This is a new dependency — the pubspec currently has 8 direct runtime deps and none of them is this.
  4. Android — enable Play Integrity. Firebase console → App Check → register the Android app with the Play Integrity provider. The app must exist in Play Console and be linked to the Firebase project. Add the SHA-256 signing certificate fingerprint of the upload/release key to the Firebase Android app — this will not work with the debug key the release build is currently signed with, so the Play signing work has to land first.
  5. iOS — enable App Attest. Firebase console → App Check → register the iOS app with the App Attest provider. In Xcode, add the App Attest capability to the Runner target. Requires iOS 14+ and a real provisioning profile from a paid Apple Developer account.
  6. Initialise in Dart, immediately after Firebase.initializeApp() in main.dart and before any Firestore call: FirebaseAppCheck.instance.activate(appleProvider: AppleProvider.appAttest, androidProvider: AndroidProvider.playIntegrity). Ordering matters — a Firestore call that fires before activation goes out unattested.
  7. Register debug tokens for local development. In debug builds use AppleProvider.debug / AndroidProvider.debug, read the token the SDK prints to the console, and paste it into Firebase console → App Check → the app → Manage debug tokens. Without this, enforcing App Check locks him out of his own simulator.
  8. Run in monitoring mode for at least a week. Firebase console → App Check → APIs tab shows the ratio of verified vs unverified requests per API. Do not enforce until that number is near 100% verified.
  9. Enforce, one API at a time: Cloud Firestore first, then Cloud Storage. Enforcement is per-API and reversible.
  10. Verify — three checks, not one:
    (a) Positive: the real app on a real device still reads the feed and uploads an avatar after enforcement is on.
    (b) Negative: hit the Firestore REST endpoint for users/{uid} with curl and the project's web API key, from outside the app, and confirm it is now rejected. This is the whole point of the feature; if this call still succeeds, App Check is not doing anything.
    (c) Console: the App Check metrics page shows unverified requests being denied rather than merely counted.
Painful to change later: the SHA-256 signing fingerprint registered for Play Integrity is tied to the signing key. If the upload keystore is ever lost or rotated, App Check on Android breaks until the new fingerprint is registered — one more reason the Android keystore backup matters. Also: enforcing before older installed builds are updated locks those users out. With no users yet, now is the cheapest possible moment to turn it on; after the beta it becomes a coordinated rollout.

App Attest / Play Integrity keysNot yours to hold — no file to leak——n/a
  • App Check debug tokens — a debug token bypasses attestation entirely, so anyone holding one can make requests that look like the genuine app. Keep it never in the repo and never in a commit message or screenshot. Debug providers must not ship in a release build.
  • SHA-256 signing fingerprint — the keystore it derives from is very much a secret.
  • App Attest / Play Integrity keys — managed by Apple and Google.

Never commit a real secret. App Check adds exactly one to the project — the debug token — and it is easy to leak precisely because it looks like harmless developer noise printed to a console log. Treat a leaked debug token as an incident: delete it in the Firebase console, which revokes it immediately.

Reminder from the Firebase runbook: firebase_options.dart, google-services.json, and GoogleService-Info.plist are client config, not secrets. App Check is precisely the mechanism that makes shipping them safe.

6. Escape hatch

Lock-in: LOW

  • What data lives only here — none. App Check stores no application data; it emits verification metrics, which are diagnostics, not records.
  • How to export — nothing to export.
  • What leaving costs — minutes. Turn enforcement off in the console (instant, reversible), remove one activate() call, drop one dependency. No data migration, no user impact.
  • The honest caveat — App Check's lock-in is low because it is inside Firebase, and Firebase is high lock-in. Leaving Firebase makes App Check irrelevant rather than expensive; the cost shows up on Firebase's bill, not this one.

7. Cost & scale checkpoints

ScaleCostWhat breaks
~10 users$0Nothing — trivially inside the 10,000/day quota
~100 users (Rec Center beta)$0Still fine; the risk is operational, not quota
~1,000 users$0The 10,000/day shared pool becomes worth watching
  • ~10 users — this is the cheapest moment to turn enforcement on, because locking out a stale build affects nobody.
  • ~100 users — App Check tokens are cached and refreshed on a TTL, not minted per request, so 100 users is on the order of a few hundred attestations a day against a 10,000 ceiling. The real risk at this scale is operational: enforcing mid-beta while testers are on an older build locks them out and looks like an outage.
  • ~1,000 users — roughly 10 attestations per user per day is the budget, which is comfortable but no longer enormous. Request a quota increase before you need it, since approval can take a week. App Check adds no Firestore reads and therefore no Firestore cost; it is one of the few things on this map that gets safer as it scales rather than more expensive.

8. Teammate delta

Extra seat cost$0, no seats — inherits Firebase project IAM
Permission modelEditor or Owner on forge-by-alpfit can toggle enforcement
Does the free tier allow another member?Yes, with no limit — same as Firebase
What actually changesEvery developer needs their own debug token
  • Permission model — toggling enforcement is a production-affecting action, and managing debug tokens comes with it. Worth keeping to one person even though the console won't stop the other.
  • What actually changes — debug tokens are registered per machine and per simulator. This is the single most common way App Check ruins a new teammate's first day: they clone the repo, run the app, and every Firestore call is denied with an unhelpful error. Put "register your App Check debug token" in the onboarding steps, and note that debug tokens are individual secrets — do not share one between people.

What to do next

Complete M1 before configuring App Check.
  1. Then fix the com.example.* bundle IDs (M2/M3) — App Check cannot be configured correctly before they are real.
  2. Then work this runbook top to bottom, and stay in monitoring mode for a week before enforcing.
  3. Register a debug token on day one of the work, so enforcement never locks him out of his own simulator.
