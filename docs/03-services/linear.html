Linear LOCKED T0 Now

What this is: the runbook for the work tracker. Linear's ForgeAlt team is where every issue in this plan lives. The one number to remember: the free plan stops you creating issues at 250, and this plan will generate a lot of issues.

1. What & why

Linear holds the project, milestones, documents, and issues for Forge in the ForgeAlt team — so that "what am I doing next" has exactly one answer that isn't a markdown file going stale. That last part is not hypothetical: this repo already contains four status documents that all describe a version of the app that stopped existing months ago.

Alternative consideredOne-line reason it lost
GitHub Issues (free, already in the repo)Genuinely the frugal answer, and it loses only because D10 is LOCKED — Linear is where his work already lives, and splitting a solo developer's attention across two trackers is how both go stale.
JiraCeremony built for teams of thirty, aimed at a team of one.
Notion / a markdown TODO fileThis project has already run the experiment. Four stale status files is the result.

Why Linear wins: it is already the place he works, it is free at this size, and keyboard-first triage suits someone who will abandon a tracker that costs friction.

2. Adoption trigger

TierWhenWhy
T0 Now Already adopted — workspace and ForgeAlt team exist D10 LOCKED. The plan in 04-plan is only useful if its items live somewhere he actually looks.
When NOT to add more Linear: no Cycles, no estimates, no velocity, no triage rotation, no automations, no roadmap views. All of that is instrumentation for coordinating people, and there is one person. Projects + milestones + issues + three statuses is the entire T0 surface. Adding sprint ceremony to a solo project is the fastest way to make the tracker feel like homework and get abandoned.

No surprise-bill risk — but a surprise wall. Linear Free cannot charge you. What it can do is refuse a new issue at the exact moment you are trying to write down a bug you just found. The intake report alone lists ~20 ship blockers, ~14 named stubs, and 21 empty files; a fully decomposed plan for this app plausibly runs 150–250 issues. Budget the 250, don't discover it.

How to stay under 250 without paying: write issues at milestone granularity, not at line-of-code granularity — "Fix the four hollow calendar surfaces" is one issue with a checklist, not four. Archive aggressively; verify whether archived issues still count toward the 250, because Linear's pricing page doesn't say and that single fact decides whether archiving is a real escape valve. If the answer is no, $10/user/month billed yearly is the cheapest unblock in this entire plan.

4. Setup steps

Steps 1–3 are already done. The rest is the shape the plan expects.

  1. Linear account and workspace exist. Done
  2. ForgeAlt team created. Done Sticky — the team key (the FOR-123 prefix on every issue) is what shows up in every branch name, commit message, and link. Changing it later re-labels everything.
  3. Confirm the team count is 2 or fewer — Free allows two teams, and it is easy to spend the second one on an experiment.
  4. Create the Forge project inside ForgeAlt, with milestones matching 04-plan: M1 Lock the doors · M2 Make "done" true · M3 Ship to a device that isn't his · M4 Beta-ready · M5 The Rec Center beta · M6 When it hurts. Per D10 the main agent does this, not the doc set.
  5. Keep the workflow to three states — Todo / In Progress / Done. Delete or ignore the rest. Every extra state is a decision he has to make on every issue forever.
  6. Add labels that map to this plan's vocabulary, and no others: T0 / T1 / T2 for tier, and security / store-blocker / stub / cost for kind. Four label groups is plenty.
  7. Connect GitHub (Settings → Integrations → GitHub) so FOR-123 in a branch or PR title auto-links. This is the one integration worth the two minutes; it is also the only one.
  8. Turn off email notifications you won't read. A solo tracker that emails you about your own actions trains you to ignore it.
  9. Verify: create a throwaway issue, put its ID in a git branch name, push, and confirm the branch shows up linked on the Linear issue. Then check the issue count in the team settings so you know how much of the 250 is already spent. Both of those, not just "the issue saved".
Painful to change later: the workspace URL slug and the ForgeAlt team key. Both appear in every issue ID and every shared link. Everything else in Linear is cheap to rearrange.

Never commit a real secret. Linear contributes nothing to the Flutter app's build — no Linear key belongs anywhere in lib/, ever, and there is no such thing as a client-safe Linear key. If a script ever needs one, it reads it from the environment and .env.example carries the empty placeholder.

One privacy note worth stating: the M1 issue describing allow read: if true on /users is a written description of an unpatched PII leak. Keep the workspace private, don't paste that issue into a public thread, and close it before showing the board to anyone outside the project.

6. Escape hatch

Lock-in: LOW

QuestionAnswer
What data lives only here?Issue titles, descriptions, comments, milestones, and project documents. That is real — it is the thinking behind the plan — but it is text about the app, never the app itself and never user data.
How do I export?Workspace settings → Import / Export → CSV export of all issues. The GraphQL API (api.linear.app/graphql) gets everything including comments and documents if CSV is too lossy.
What does migrating cost?An hour. Export CSV, import to GitHub Issues or Jira, accept that comment threading and issue IDs get mangled. Nothing breaks; no code references Linear.
The real riskNot lock-in — abandonment. The failure mode for a solo tracker is that it quietly stops being updated and becomes the fifth stale status document in this project. That is why the setup above is deliberately minimal.

7. Cost & scale checkpoints

Linear's cost scales with issues and people, not app users — so the honest table tracks issue count alongside the user milestones.

ScaleCostWhat breaks
~10 users (today; ~50–100 issues as the plan lands)$0Nothing. Comfortably inside 250 issues and 2 teams.
~100 users (the Rec Center beta, M5)$0 — or $10/mo if the cap hitsThis is where the 250-issue wall most likely lands. Beta feedback is a bug-report firehose, and every crash report someone sends becomes an issue. Nothing degrades — issue creation simply refuses. Mitigate by triaging beta reports into a handful of parent issues instead of one issue per report.

Note Linear bills per user, so this is $10/mo solo and $20/mo with a teammate.

8. Teammate delta

QuestionAnswer
Does the free tier allow another member?Yes — Free allows unlimited members. Seats are not the constraint; the 250 issues are.
Extra seat cost$0 on Free. On Basic it is $10 per person per month billed yearly, so a second person doubles the bill the moment you upgrade.
Permission modelWorkspace-level roles (Admin / Member / Guest) plus team membership. A Guest sees only the teams you add them to — the right setting for a designer or a Rec Center contact who should see the beta board and nothing else.
What actually changesTwo habits become mandatory: assignees (a solo board doesn't need them; a two-person board is chaos without them) and issue descriptions written for someone else — "fix the calendar thing" is fine when you are the only reader and useless the moment you aren't.
Counter-pressureA second person roughly doubles issue creation rate, which pulls the 250-issue wall closer. Adding a teammate and staying on Free is possible but unlikely to last a month.

What to do next

Open ForgeAlt's team settings and read the current issue count against the 250 cap — before the plan's issues get created, so you know how much room the plan actually has.
  1. Then confirm whether archived issues still count toward the 250. That one answer decides whether Free is sustainable or whether Basic is inevitable.
  2. Then connect the GitHub integration so FOR- branch names auto-link.
  3. Keep the workflow at three states and resist every Linear feature that exists to coordinate a team.
