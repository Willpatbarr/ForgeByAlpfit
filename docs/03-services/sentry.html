Sentry PROPOSED

What this is: the setup plan and trade-off for Sentry, the proposed crash-and-error monitor for Forge — not yet wired into the app.
This is a coin-flip, not a settled decision. Sentry is proposed against Firebase Crashlytics and tagged PROPOSED pending William's review (decision brief §6, §9 question 3). Nothing described below is implemented yet.

What & why

Sentry (via the sentry_flutter package) would capture crashes and errors from the deployed app — web and mobile — into one dashboard, so failures reach William without a friend having to text him about it. It covers Milestone M4's definition of done directly: a deliberately-thrown test error from a production build showing up somewhere he'll see it.

Alternative consideredTrade-off
Firebase CrashlyticsFree and unlimited, already inside Firebase — matches the existing stack, which William weights heavily. But its Flutter web support is poor, and web is the beta channel.

Why Sentry wins by default: coverage of the platform the beta actually ships on beats stack consistency. Flip this back to Crashlytics if the beta ends up mobile-only.

Setup steps

  1. Create a Sentry account/organization — this is the account the free tier's "1 user" limit is scoped to.
  2. Create a Flutter project inside Sentry to get a DSN.
  3. Add the sentry_flutter package to pubspec.yaml.
  4. Initialize Sentry at app startup in main.dart, wrapping the app's entry point per the package's init pattern.
  5. Set tracesSampleRate low or 0 — performance traces consume the same free-tier quota as errors, and Forge doesn't need them yet.
  6. Read the DSN from a build-time config source rather than hardcoding it inline, even though the DSN itself is not secret the way an API key is.
  7. Deploy a build with Sentry initialized.
  8. Verify: deliberately throw a test error from the production build and confirm it appears in the Sentry dashboard — this is the literal Milestone M4 definition of done.

Secrets & config

ItemSecret?LocalProduction
DSNNot secret the way an API key is — client-side by design — but it should still come from config, not be hardcodedDev config valueSame DSN, or a separate Sentry project if dev noise needs to be kept out of prod
tracesSampleRateNot a secret, a tuning valueLow or 0Low or 0, to avoid burning the 5,000/mo quota on performance data instead of errors

Real secrets are never committed. Today Sentry doesn't introduce one, since the DSN is designed to be client-visible; a value for it belongs in .env.example as SENTRY_DSN= rather than typed into source. If source-map/symbol upload is added to CI later, that upload auth token would be a real secret — CI-only, never committed.
