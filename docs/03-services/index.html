Status is derived from the code, not from anyone's recollection: Auth, Firestore, and Storage are wired throughout lib/services/; the GitHub remote exists but there is no .github/ directory; Linear's ForgeAlt team exists per D10. App Check, FCM, and Crashlytics are absent from pubspec.yaml entirely — and push_service.dart is a 0-byte file.

The one thing on this page that can cost real money. Everything reads $0 — and that is true today — but Firebase Blaze is pay-as-you-go with no spending cap on Firestore or Storage. Since 3 February 2026 Cloud Storage requires Blaze on every project, and Forge uses Storage for avatars, so Forge is almost certainly already on a plan that can bill. A budget alert is the only guardrail, and it only sends an email. Read the Firebase free-tier section before trusting any $0 in this table.

Total cost

The whole stack is $0/month until the app stores. After that it's $99/year plus $25 once — and the only line that ever grows with users is Firestore.
StageRecurringOne-timeBreakdown
Today (~10 users, him and friends) $0 / mo $0 Firebase free allowance · GitHub Free · Linear Free
At beta (~100 users, the Rec Center beta, M5) ~$8–12 / mo $25 (Play, once) Apple $8.25/mo · Firebase ~$0–3/mo · rest $0
At 1,000 users ~$35–60 / mo (estimate) — Apple $8.25 · Firestore ~$25–40 · Linear ~$10
  • Today — Apple $99/yr is not yet being paid. Nothing has a card attached except possibly Blaze, which is currently billing $0.
  • At beta — Apple is $99/yr ≈ $8.25/mo; everything else beyond Firebase is $0. Linear may hit its 250-issue cap here (+$10/mo if it does). The $25 Play fee is the only true one-off in the plan.
  • At 1,000 users — Firestore is rising, driven by the calendar's 2×(friends+gyms)+1 listeners and N+1 fetches. Linear Basic is ~$10/mo. App Check, FCM, Crashlytics, Play, Cloudflare, and GitHub are all still $0.
Read the 1,000-user row as a design signal, not a budget. Firestore reaching ~$25/mo is the exact trigger D1 names for revisiting the architecture. Fixing the read amplification is what keeps that decision from being forced — see the Firebase cost section for the arithmetic. Everything else in the stack is flat at every scale.

Setup order

Keyed to the milestones. The ordering is not preference — each step below unblocks the next, and doing them out of order means doing several of them twice.

  1. Confirm Firebase's billing plan and set a budget alert. T0 M1
    Fifteen minutes, and it is the only step on this list that protects money. → firebase.html
  2. Fix allow read: if true on /users and deploy the rules. T0 M1 — Lock the doors
    The highest-severity item in the project. Every security step below is worthless while this is open. → firebase.html
  3. Confirm the GitHub repo is private; fix .gitignore. T0 M1
    Do the gitignore patterns now, while no signing key exists to forget about. → github.html
  4. Add the CI workflow (build + test) and tighten the analyzer. T0 M2 — Make "done" true
    One file, Linux runners only. → github.html
  5. Decide the bundle ID / package name and change it everywhere. T1 M2/M3
    PROPOSED com.alpfit.forge. This single decision gates steps 6–10 — it pins Firebase registration, App Check, APNs, and both store listings, and it is permanent after the first upload. → apple · → play
  6. Google Play Console: register ($25), real keystore, pinned SDK levels. T1 M3 — Ship to a device that isn't his
    Cheapest store, fastest track. Register early: identity verification and the 12-testers-for-14-days clock cannot be compressed. → google-play.html
  7. Crashlytics. T1 M3
    Goes in the first build that leaves his machine, not after. Free, and it introduces no secrets. → crashlytics.html
  8. Apple Developer Program: enrol ($99/yr). T1 M3
    Start a week early — approval takes 24–48h+, and the annual clock starts on payment. → apple-developer.html
  9. Cloudflare Pages + the legal pages. T1 M4 — Beta-ready
    Privacy policy and account-deletion URL are required store submission fields. Do not deploy docs/ publicly until step 2 is done — it documents the open hole. → cloudflare-pages.html
  10. App Check: monitor for a week, then enforce. T1 M4
    Needs real bundle IDs, a Play entry, and an Apple membership — hence its position. → app-check.html
  11. Cloud Messaging. T1 M4/M5
    Last, because it depends on the Apple membership for APNs and on an open PROPOSED decision about the sender. → cloud-messaging.html
The through-line: steps 1–4 cost $0 and are pure risk reduction. Step 5 is a decision, not work. Steps 6–11 all hang off that decision. Nothing below step 2 should start until step 2 is done.

What he is NOT doing

The list below is nine services deliberately not adopted — and that is the point of it. A solo developer's real failure mode is not picking the wrong tool; it is picking nine tools and maintaining none of them. Every row has a named trigger, so nothing here was silently dropped — it is scheduled for never, unless.

If one of these triggers fires, adopting it becomes a normal decision rather than a reversal. Until then, each row is a thing he gets to not think about.

  • Sentry — Crashlytics is already inside a service we've adopted, is free and unlimited with no event cap, and has zero marginal setup. Sentry's one decisive edge here was Flutter web support, and D3 cut web as a target, which removed the entire argument. Trigger: a single dashboard for everything he builds is a real reason; "Sentry is nicer" is not.
  • Dedicated analytics — product analytics answers questions about cohorts you don't have. With ~10 users he can ask them directly, and with 100 beta testers he can ask them in person at the Rec Center. Trigger: e.g. "do people who add three friends in week one stay?" — where asking users individually is no longer possible.
  • Algolia / Typesense — real search infrastructure for an app whose entire search is FirestoreRefs.users.limit(100).get() followed by an in-memory contains(). Trigger: past 100 users is a hard, known number and it will arrive during the beta. Note the cheaper intermediate fix first: displayNameLower is already written at signup and never queried, so a Firestore prefix query buys real headroom before any vendor is needed.
  • Cloud Functions — requires Blaze and adds a server-side component to a deliberately serverless app. Trigger: most likely the account-deletion cascade, moderation actions, or (see the FCM runbook) triggered push, which cannot be done from the client without shipping an admin credential.
  • RevenueCat — the only monetization signal in ~20 source documents is one line about a paid premium gym tier. Trigger: D8's own trigger is three separate gyms asking for something a free tier can't do.
  • Terraform / IaC — infrastructure-as-code for one Firebase project, one static site, and two store listings. firestore.rules + firestore.indexes.json are already versioned in git, which is the 90% of IaC that actually pays off here. Trigger: a real staging Firebase project that must stay in sync with production. Until there are two of something, there is nothing to reproduce.
  • Feature flags — flags exist to decouple deploy from release for teams shipping continuously. Trigger: realistically the first time a store review cycle stands between him and a broken feature. Remote Config is free and already inside Firebase when that day comes, so this is a cheap adoption, just not a useful one yet.
  • A status page — a public status page communicates outages to users who are watching for them. Trigger: users start asking "is it down?" through a channel he doesn't control, or a gym partner asks for uptime commitments.
  • A dedicated CDN — Firebase Storage already serves avatars from Google's edge, and Cloudflare Pages already puts the docs on Cloudflare's. Trigger: even then the first fix is thumbnails, not a CDN — profile_avatar_service.dart currently reads avatars up to 15 MB with no upload cap at all.
  • Auth0 / Clerk — Firebase Auth is already wired, already working, and free to 50,000 monthly active users. Adding a second identity provider would mean migrating every existing account for zero user-visible gain. Trigger: enterprise SSO for a gym chain, or a compliance requirement Firebase doesn't meet. Note that social sign-in, email verification, and password reset are all things Firebase Auth can do and Forge simply hasn't turned on; those are not reasons to switch.

Adjacent calls made elsewhere and not repeated here: Supabase/Postgres migration (D1), Riverpod (D5), and the desktop/web platform targets (D3).

Open calls — needs William's eye

Four genuine coin-flips across the runbooks. Everything else on this page is settled.

Bundle ID / package name PROPOSED

The question: com.alpfit.forge on both platforms, replacing com.example.*.

Why it matters: permanent after the first store upload, and it pins Firebase, App Check, and APNs. This is the highest-consequence unmade decision on the page.

Where: apple · play

Push needs a Cloud Function PROPOSED

The question: accept one small Cloud Function (Blaze, ~$0 within the free allowance), or accept that beta invites stay silent.

Why it matters: FCM delivery is free, but triggering a push on a new DM cannot be done from the client without shipping an admin credential.

Where: cloud-messaging

Domain for the docs / legal pages PROPOSED

The question: free *.pages.dev subdomain, or a bought domain (~$10–15/yr)?

Why it matters: the URL goes into two store listings and a privacy policy users agree to, so it's awkward to change afterwards. Not yet determined — no domain is named anywhere in the intake.

Where: cloudflare-pages

Stay on Cloudflare Pages PROPOSED

The question: Cloudflare has confirmed Pages and Workers are converging.

Why it matters: there is no deprecation notice and existing projects keep working. Recommendation is to stay on Pages and revisit only if a real deprecation date appears.

Where: cloudflare-pages
