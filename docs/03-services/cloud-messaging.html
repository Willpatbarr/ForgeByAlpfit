Firebase Cloud Messaging DECIDED T1 Before first real user

Runbook for push delivery and the server-side sender it requires.

1. What & why

FCM delivers a notification to a user's phone when something happens that they care about. For Forge that means the three things the app currently does entirely silently: a friend request arrives, a DM arrives, and a workout invite arrives. Right now the only way to learn any of those happened is to open the app and look — which, for an app whose entire thesis is planning workouts together, means the social loop never closes.

Alternatives considered, and why each lost:

  • OneSignal / Airship — nicer dashboards and segmentation, but a third-party vendor holding device tokens when the first-party one is free and already inside the project we've adopted.
  • Raw APNs + raw FCM per platform — two integrations, two token stores, two failure modes, for a solo dev; FCM already fronts APNs for you.
  • Local notifications only (flutter_local_notifications) — can't help: local notifications fire from the device, and the device doesn't know a DM arrived until it opens the app. Solves the wrong half.
  • In-app badges only (what exists today) — already built and genuinely useful, since getDirectUnreadCountsStream() badges the bottom nav, but it only works while the app is open.

Why FCM wins: free with no message quota, already in the Firebase project, and it is the only option that doesn't add a vendor.

2. Adoption trigger

Tier: T1 Before first real user

Trigger: part of M4, Beta-ready — before the Rec Center beta, not before the first internal build.

Why this tier: silence is survivable when the only user is him. It is fatal with 100 beta testers: an invite nobody sees looks like a broken feature, and the beta's whole purpose is finding out whether people actually plan workouts together.

When NOT to set this up yet. Not before real bundle IDs exist (APNs is keyed to the App ID). Not before an Apple Developer Program membership exists — you cannot create an APNs key without one, so iOS push is hard-blocked on $99. And not before the rules are fixed: a notification system that reaches into user data is a bad thing to build on top of a world-readable collection. Android-only push is possible earlier and is a reasonable partial step.

The catch: FCM needs something to press "send"

FCM delivers messages. It does not decide to send them. Something has to notice "a DM was written to directThreads/{t}/messages" and call the FCM API. Forge has no server. That leaves three options and none is free of consequence:

  • A. Send from the client — the sending device calls FCM directly. Do not do this. The FCM HTTP v1 API requires a service-account credential, which is a full-admin secret. Putting one in a shipped app hands every user the ability to push arbitrary notifications to every other user. This is not a tradeoff, it's a vulnerability.
  • B. Cloud Functions — a Firestore onCreate trigger sends the push. The correct design. ~30 lines. But Cloud Functions requires the Blaze plan — which, per the Firebase runbook, the project already needs anyway for Cloud Storage since Feb 2026. Blaze includes 2M invocations/month free, so the marginal cost of these functions is realistically $0.
  • C. Ship without triggered push — FCM only for manual/topic broadcasts from the console. Partial. Lets a gym announce something to a channel topic with zero server code. Does nothing for DMs or invites, which is the actual problem.

PROPOSED — this is the decision to make, and it is a real one. Adopting FCM properly is what trips the "Cloud Functions" trigger listed as rejected as premature. The recommendation is option B: DM/invite push is exactly the "first thing that genuinely can't be done in rules + client" that the trigger names, the Blaze plan is already required, and the free allowance swallows the cost. Flag for William: accepting this means accepting one small server-side component into an otherwise serverless app. The alternative is shipping a beta where invites stay silent.

4. Setup steps

Nothing here is done. push_service.dart is 0 bytes and there is no firebase_messaging dependency.

  1. Prerequisites: real bundle IDs (not com.example.*), a paid Apple Developer Program membership for iOS, and fixed Firestore rules. Android can proceed without Apple.
  2. Add dependencies: flutter pub add firebase_messaging flutter_local_notifications. The second one is not optional — on Android, a notification received while the app is in the foreground is not displayed by the system; you have to render it yourself.
  3. iOS — create the APNs auth key. Apple Developer portal → Certificates, Identifiers & Profiles → Keys → new key with Apple Push Notifications service (APNs) enabled. Download the .p8. Downloadable exactly once — save it to a password manager immediately. Note the Key ID and your Team ID. Prefer a .p8 auth key over the legacy .p12 certificate: it doesn't expire and covers all your apps.
  4. Upload the APNs key to Firebase: console → Project settings → Cloud Messaging → Apple app configuration → upload the .p8 with its Key ID and Team ID.
  5. Xcode: add the Push Notifications capability and the Background Modes → Remote notifications capability to the Runner target. Both are required; missing the second means silent/data messages never wake the app.
  6. Android: nothing extra is needed beyond the existing google-services.json. Add a POST_NOTIFICATIONS runtime permission request for Android 13+ — note AndroidManifest.xml currently declares no permissions at all, so this is a genuine addition.
  7. Write push_service.dart (the empty file that already exists): request permission via FirebaseMessaging.instance.requestPermission(), get the token with getToken(), write it to users/{uid}.fcmTokens as an array (one user has multiple devices — a single fcmToken string is a bug waiting to happen), and re-write it on onTokenRefresh. Handle onMessage (foreground), onMessageOpenedApp, and a top-level onBackgroundMessage handler.
  8. Add a Firestore rule for the token field so a user can only write their own fcmTokens. Forge's rules have no field validation anywhere; do not extend that pattern to a field that controls who gets pushed.
  9. Deep-link the tap. A DM notification must open that thread, and an invite must open the calendar at that event. The routing already exists — router.dart handles event-invite deep links from DMs today — so this is wiring, not new design.
  10. Implement the sender per the option B decision: a Cloud Function on directThreads/{t}/messages/{m} onCreate that looks up the recipient's tokens and sends via the FCM Admin SDK. Prune tokens that come back as unregistered — stale tokens accumulate forever otherwise.
  11. Respect the RSVP bug. direct_message_page.dart's Attend/Decline is local-only and never persisted; there is nothing to notify the inviter about until that's fixed. Push for RSVPs must wait on that repair, or it will notify nobody about nothing.
  12. Verify — four checks:
    (a) Firebase console → Cloud Messaging → "Send test message" to a pasted token reaches a physical device (iOS push does not work on the simulator).
    (b) A real DM sent from a second account produces a notification on the first account's locked phone.
    (c) Tapping it opens the correct thread, not the home screen.
    (d) The same works with the app foregrounded — this is the case Android silently drops without flutter_local_notifications.
Painful to change later: the APNs .p8 is download-once — lose it and you generate a new one and re-upload. The bundle ID is baked into the APNs key's App ID association. And the token storage shape (fcmTokens as an array vs a string) is a schema decision on the users collection that gets expensive to change once devices are registered — pick the array now.

  • messagingSenderId — already committed, and it ships in the app by design.
  • Per-device FCM registration token — it identifies a device. Store it in Firestore under the user and protect it with rules.
  • APNs auth key .p8 — keep a password-manager copy plus an offline backup. It is not stored in the project once uploaded.
  • Service-account JSON — server-only. It must never touch client code, and never be shipped in the app. Cloud Functions get it implicitly from the runtime — no key file needed at all, which is another argument for option B.

Never commit a real secret. Add *.p8 and *service-account*.json to .gitignore before downloading the APNs key — the GitHub runbook has this as a step for exactly this reason. The clean split: anything that receives a push is client-safe; anything that sends one is server-only.

6. Escape hatch

Lock-in: LOW (with one medium-lock-in footnote)

  • What data lives only here — device registration tokens, and only transiently, because the design above stores them in Firestore, not in FCM. FCM keeps delivery statistics; nothing irreplaceable.
  • How to export — nothing to export. Tokens live in your own users docs.
  • What migrating costs — a day or two. FCM tokens are FCM-specific, so moving to OneSignal or raw APNs means every device must re-register on next app launch; users with the app installed but never reopened simply stop receiving push. Annoying, not catastrophic.
  • The footnote — if option B is taken, the Cloud Function is the sticky part. It is Firebase-specific glue and it deepens the Firebase lock-in slightly by moving a piece of business logic server-side into Google's runtime. Small, but real: worth writing it as a thin trigger that calls plain, portable logic.

7. Cost & scale checkpoints

ScaleCostWhat breaks
~10 users$0Nothing — perhaps a few hundred pushes a month
~100 users (the beta — the reason this exists)$0Nothing on cost; what breaks is relevance
~1,000 users~$0–1/mo (Functions, estimated)Topic fanout limits and stale-token accumulation
  • ~10 users — FCM is free at any volume; Functions invocations are a rounding error against 2M/month.
  • ~100 users — with gym channels fanning out, a chatty channel can push every member on every post, and users turn notifications off permanently after roughly one bad day. Batch or debounce channel-post pushes; keep per-message push for DMs and invites only. Also watch the Firestore side: the sender function reads the recipient's user doc per message, which adds to the read amplification already flagged.
  • ~1,000 users — FCM itself is still free. The 1,000-concurrent-topic-fanout limit becomes a real number if every gym channel is a topic. Stale-token accumulation becomes a real cost too: without pruning unregistered tokens you send — and pay Firestore reads for — pushes to devices that no longer exist. Build the pruning in from day one; retrofitting it means auditing every user doc.

  • Permission model — Firebase Editor/Owner covers console sending and key upload. On the Apple side, creating or revoking the APNs key needs an Account Holder or Admin role in the Apple Developer account; a Developer-role teammate cannot do it. See Apple roles.
  • What actually changes — push is the hardest thing in this stack for a second developer to test. They need a physical device on the team's provisioning profile. Budget real onboarding time for that, and expect "push doesn't work on my machine" to be a provisioning problem roughly every time.

What to do next

Make the option B call — accept one Cloud Function as the push sender, or accept that beta invites stay silent. That single PROPOSED decision unblocks everything else on this page, and nothing else should start until it's answered.
  1. If yes: confirm the project is on Blaze (it likely already must be) and set a Functions spend cap — Functions is one of the few services the real cap covers.
  2. Then create the APNs .p8 key after the Apple membership exists, and add *.p8 to .gitignore before you download it.
  3. Fix the local-only RSVP in direct_message_page.dart before wiring RSVP notifications — right now there is nothing persisted to notify anyone about.
