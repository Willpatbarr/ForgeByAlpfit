Firebase Crashlytics DECIDED T1 Before first real user

Runbook for Firebase Crashlytics and global Flutter error reporting.

1. What & why

Crashlytics captures a stack trace, device, OS version, and breadcrumb trail every time Forge crashes on somebody else's phone, and groups those into ranked issues. Forge needs this specifically because it has identified crash paths it cannot currently observe: events_service._mapDocToEvent does an unchecked (d['startAt'] as Timestamp) cast on a field that createEvent writes as nullable, and calendar_page.dart and event_creator_page.dart have three more unchecked list casts — all reachable with data the app itself produces. Today, if any of those fire on a tester's phone, nobody finds out.

Alternatives considered, and why each lost:

  • Sentry (the previous proposal in this doc set) — better product in isolation, but Crashlytics is free with no event cap, inside a service already adopted, with zero marginal signup, and Sentry's one decisive advantage here was Flutter web support, which D3 made irrelevant by cutting web as a target. Moved to "rejected as premature" with a named trigger.
  • Firebase Analytics — answers "what did users do", not "what broke". Different question; also deferred.
  • catch (e) { print(e) } — roughly the current state, and it is worse than nothing: profile_page.dart has four catch (_) {} blocks that swallow write failures and report success to the user.
  • Nothing, and wait for bug reports — works with one user (him). At 100 beta testers, most people who hit a crash uninstall silently rather than write to you.

Why Crashlytics wins: free, unlimited, no new vendor, and it is already sitting inside the Firebase project — the marginal setup cost is one package and about twenty lines.

2. Adoption trigger

Tier: T1 Before first real user

Trigger: with M3, Ship to a device that isn't his — in the very first build that leaves his hands, and definitely before M4/M5.

Why this tier: the value of crash reporting is exactly proportional to how far the app is from the developer. On his own device he sees the stack trace in the debugger. On a tester's device he sees nothing at all. The transition happens at M3, so that is the trigger.

When NOT to set this up yet: not while he's the only user — a debugger is strictly better than a dashboard when you're holding the phone. And don't bolt on Firebase Performance Monitoring or Analytics at the same time "since you're in there"; they answer different questions and each is a new surface to ignore. Crashlytics alone, at M3.
One honest caveat about ordering. Crashlytics is cheap and useful, but it is observability, not a fix. The open Firestore rule (M1) and the store-blocking gaps (M2/M4) outrank it. Don't let installing a dashboard feel like progress on the things that are actually blocking.

Once web is out of scope, Crashlytics' only real weakness disappears and it wins on cost, integration, and setup effort simultaneously.

4. Setup steps

Nothing here is done. There is no firebase_crashlytics dependency and no error handling wired anywhere.

  1. Enable Crashlytics in the Firebase console (Release & Monitor → Crashlytics → Enable) for the forge-by-alpfit project. No plan change required — it works on Spark.
  2. Add the package: flutter pub add firebase_crashlytics.
  3. Android — add the Gradle plugin. In android/app/build.gradle.kts add id("com.google.firebase.crashlytics") to the plugins block (alongside the existing com.google.gms.google-services), and add the classpath to the project-level Gradle file. Without this, Android stack traces arrive unsymbolicated and useless.
  4. iOS — turn on dSYM upload. firebase.json currently has "uploadDebugSymbols": false for both the iOS and macOS entries. Set the iOS one to true and add the Crashlytics dSYM upload run-script build phase in Xcode. Left as-is, every iOS crash report is a wall of hex addresses.
  5. Wire the global handlers in main.dart, after Firebase.initializeApp(): route FlutterError.onError to FirebaseCrashlytics.instance.recordFlutterFatalError, and return true from PlatformDispatcher.instance.onError after calling recordError(error, stack, fatal: true). Both are needed — the first catches framework errors, the second catches raw async errors that would otherwise vanish.
  6. Disable collection in debug builds with setCrashlyticsCollectionEnabled(!kDebugMode), so his own development crashes don't pollute the dashboard.
  7. Set a user identifier — setUserIdentifier(uid) on sign-in, and clear it on sign-out. Use the Firebase uid, never the email: it makes "which tester hit this" answerable without putting PII in a crash report.
  8. Replace the silent-failure blocks. The four catch (_) {} blocks in profile_page.dart (lines ~91, 374, 721, 1002), plus the ones in friends_service, gyms_service, and plan_creator_sheet.dart, currently swallow write failures and tell the user it worked. Change each to catch (e, s) { FirebaseCrashlytics.instance.recordError(e, s); ... } and surface an honest error to the user. This is the step that converts Crashlytics from a dashboard into a fix — installing it without doing this means the app's most common failure mode stays invisible.
  9. Add breadcrumbs at the known crash paths — log() calls around events_service._mapDocToEvent's startAt cast and the unchecked list casts in calendar_page.dart, so a report arrives with the offending event ID attached.
  10. Verify — two checks:
    (a) Add a temporary debug-only button calling FirebaseCrashlytics.instance.crash(), tap it on a release build on a real device, reopen the app (reports upload on the next launch, not immediately), and confirm the crash appears in the console with readable symbol names, not hex addresses — on both platforms. The symbolication half is the part that usually fails silently.
    (b) Trigger a caught, non-fatal error through one of the rewritten catch blocks and confirm it lands under "non-fatals". Then delete the crash button.
Painful to change later: nothing structural — Crashlytics is genuinely low-commitment. The one thing that bites is missing dSYM uploads on old releases: if a version ships without symbol upload configured, its crash reports are permanently unreadable and cannot be retro-symbolicated. Get step 4 right in the first build that leaves his machine.

  • iOS dSYM files — build artifacts, uploaded by the build phase.
  • Fastlane/CI service account — only needed if CI ever builds iOS, which is T2.

Never commit a real secret — though notably, Crashlytics introduces none. It is the only service on this map that adds zero credentials, because it authenticates with the client config that already ships in the app. That config is not a secret.

The real privacy question here isn't keys, it's payloads. Crash reports carry whatever you put in them. Rules for Forge: use the Firebase uid as the identifier, never the email or contactInfo; never log() DM contents or channel-post text; and remember that crash reports are user data — Crashlytics collection has to be disclosed in the App Store privacy questionnaire and the Play Data safety form. See Apple and Google Play.

6. Escape hatch

Lock-in: LOW

  • What data lives only here — crash history: stack traces, affected-user counts, trends. Real but strictly diagnostic; nothing a user would miss and nothing the app reads back.
  • How to export — poorly. There is no "download my crashes" button. The only bulk path is the BigQuery export, which requires Blaze and has to be enabled before the crashes you want; it is not retroactive. Practically: if crash history ever needs preserving, enable BigQuery export up front or accept losing it.
  • What migrating costs — half a day. Swap the package, re-point the two global error handlers, redo the symbol-upload build step. The recordError call sites added in step 8 are the portable, valuable part and mostly survive a swap.
  • Realistic exit — the named trigger on the rejected list: he wants one error tool spanning Flutter and his Swift projects. That's when Sentry comes back, and it would be a genuine reason, not a regret.

7. Cost & scale checkpoints

ScaleCostWhat breaks
~10 users$0Nothing — a handful of reports, each worth reading
~100 users (the beta)$0Nothing on cost; what breaks is attention
~1,000 users$0Still free, still unlimited
  • ~10 users — this is where the known cast crashes should surface first, before strangers hit them.
  • ~100 users — no event cap exists to hit. A single unchecked cast fires across dozens of sessions and the dashboard fills with one issue repeated. That's Crashlytics working correctly; the fix is triage discipline, sorted by affected-user count. (A capped free tier like Sentry's would start dropping events here — the reason cost isn't in this row.)
  • ~1,000 users — Crashlytics is one of the very few services on this map whose cost line is genuinely flat at every scale; contrast Firestore's ~$25–40/mo at the same point. The constraint at 1,000 users is human: crash-free-users percentage becomes the number to watch instead of individual issues.

8. Teammate delta

QuestionAnswer
Extra seat cost$0, no seats — inherits Firebase project IAM
Does the free tier allow another member?Yes, unlimited members with no cap and no upgrade
Permission modelFirebase Viewer is enough to read Crashlytics
What actually changesIssue assignment starts mattering
  • Extra seat cost — worth contrasting: per-seat pricing is a standard cost of dedicated error-tracking vendors.
  • Permission model — Viewer makes Crashlytics a safe thing to grant a designer or a Rec Center contact without giving them Firestore write access. Editor is needed to change settings or enable BigQuery export.
  • What actually changes — the natural move is linking Crashlytics issues to Linear so a crash becomes a tracked ticket rather than a dashboard row two people both assume the other saw. Also, with two developers, "disable collection in debug" (step 6) stops being optional hygiene: two people's local crashes will otherwise drown the real signal.

What to do next

When the first build leaves his machine (M3), add firebase_crashlytics and wire both global error handlers before that build ships — a tester's crash you never hear about is the most expensive kind.
  1. Flip "uploadDebugSymbols" to true for iOS in firebase.json and add the Android Gradle plugin — unsymbolicated reports are close to worthless and cannot be fixed retroactively.
  2. Rewrite the four catch (_) {} blocks in profile_page.dart to recordError and show the user the truth. This is the highest-value line of work on the page.
  3. Verify with a real crash on a release build on a physical device, and confirm the trace comes back with symbol names.
