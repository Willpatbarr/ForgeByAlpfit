Firebase LOCKED T0 Now

Runbook for Firebase Auth, Firestore, Storage, and billing.

1. What & why

Firebase is Forge's whole backend: Auth (email/password), Firestore (every user, event, goal, plan, channel post, and DM), and Storage (avatars at avatars/{uid}/profile), all in one Google Cloud project — forge-by-alpfit, project number 532850332803. The Flutter client talks to it directly with no server layer in between, which is why it is fast to build on and expensive to leave.

Alternatives considered, and why each lost:

  • Supabase / Postgres — would be a rewrite of all 15 service files, not a swap: there is no repository seam to swap behind.
  • Custom API gateway in front of Firebase (from "Ideas for Future") — textbook premature abstraction for one developer with zero real users; DEFERRED with a trigger, see D1.
  • Auth0 / Clerk for identity only — Firebase Auth is already wired and already free to 50K MAU; adding a second identity vendor buys nothing.

Why Firebase wins: it is already built on, and nothing today has cleared the trigger that would justify paying the migration cost.

2. Adoption trigger

Tier: T0 Now

Trigger: already adopted — this is not a future decision.

Why: D1 LOCKED: Flutter + Firebase. The app does not run without it. There is no "not yet" option.

When NOT to do more: do not add Cloud Functions, Analytics, Remote Config, or Performance Monitoring right now. Each is a new surface with no user asking for it. Their triggers live on the service map's rejected list.

3. Free tier reality

The single most important fact on this page: since 3 February 2026, Cloud Storage for Firebase requires the Blaze pay-as-you-go plan on every project — including projects that predate the change and including the default bucket. Forge uses Storage for avatars. So Forge is either already on Blaze, or its avatar uploads are currently broken. Go find out which, today. Verify at firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024.

Budget alerts

Blaze has no spending cap for Firestore or Storage. Google's own wording: budgets and budget alerts do not cap usage or charges. They send an email. That is all they do.

Firebase does now have a budget spend cap feature that genuinely pauses a service — but it currently covers only Firebase AI Logic, App Hosting, Cloud Functions, and Extensions. Firestore and Cloud Storage are not covered. Even where it does apply, Google calls it "not a hard cap" because of reporting lag.

So the protection model for Forge is: a budget alert email, plus him reading it. Set the alert low ($5, $20, $50) so the first email arrives while the number is still small. Verify at firebase.google.com/docs/projects/billing/avoid-surprise-bills.

The realistic runaway scenarios for this app, in order of likelihood: (1) the calendar's 2×(friends+gyms)+1 listeners re-attaching in a reconnect loop, (2) getIncomingFriendRequestsStream's one .get() per thread on every snapshot, and (3) an unbounded avatar upload — profile_avatar_service.dart has no write size cap, so one user can push a multi-GB file into a billed bucket.

4. Setup steps

Steps 1–7 are already done — they are written out so the state is auditable, not because they need repeating. Steps 8–12 are the outstanding work.

  1. Google account signed in at console.firebase.google.com. Done
  2. Project created as forge-by-alpfit. Done Permanent — the project ID can never be changed, and it is baked into every config file and every console URL.
  3. Firestore database created. Done Permanent — the database location cannot be changed after creation. Record what it is; nothing in this repo says.
  4. Auth → Sign-in method → Email/Password enabled. Done. No social, phone, or anonymous providers are configured. Email link verification and password reset are not enabled — see next steps.
  5. Storage bucket enabled (forge-by-alpfit.firebasestorage.app). Done Permanent — bucket region is fixed at creation and determines whether the GCS always-free tier applies.
  6. Apps registered: Android, iOS, and web, per firebase.json. macOS reuses the iOS app ID and Windows reuses the web app ID — they are not independently provisioned targets. Done
  7. Config generated and committed by flutterfire configure: android/app/google-services.json, ios/Runner/GoogleService-Info.plist, lib/firebase_options.dart. Done — and correctly committed; see Secrets & config.
  8. Confirm which billing plan the project is on (console → gear → Usage and billing). If Storage works, it is Blaze. Write the answer down. Do this first
  9. Set a budget alert at Google Cloud Console → Billing → Budgets & alerts, thresholds at $5 / $20 / $50, emailing his real address. Do this the same hour he confirms Blaze. On Spark this is unnecessary; on Blaze it is the only guardrail that exists.
  10. Fix firestore.rules — allow read: if true on /users/{userId} makes the entire user table, emails included, readable by anyone unauthenticated. Change to if request.auth != null at minimum, then deploy with firebase deploy --only firestore:rules. This is M1 — Lock the doors and it is the highest-severity item in the project.
  11. Add a size and content-type cap to storage.rules (e.g. request.resource.size < 5 * 1024 * 1024 && request.resource.contentType.matches('image/.*')) and narrow storage-cors.json off origin: ["*"]. Unbounded upload size on a billed bucket is a cost hole as well as a security one.
  12. Add the missing index for findPlanByNameForCurrentUser (plans.name + plans.updatedAt) to firestore.indexes.json. Firestore will demand it at runtime otherwise, and channel_page.dart currently renders the resulting error as end-user UI telling them to run firebase deploy.
  13. Verify: from a signed-out client (or the Firestore Rules Playground), attempt an unauthenticated read of users/{anyUid} and confirm it is now denied. Then sign in on a device, upload an avatar, and confirm the file lands in Storage and the users/{uid} doc updates. Passing both is what "Firebase is set up correctly" means — not "the app launches".
Painful to change later — the permanent list. Project ID forge-by-alpfit · Firestore database location · Storage bucket region · Android applicationId and iOS bundle ID (still com.example.*, both stores reject them, and changing them means re-registering the Firebase apps and regenerating all three config files). Fix the bundle IDs before the first store upload, not after — see Apple and Google Play.

5. Secrets & config

Read this before anyone tells you to rotate your keys. lib/firebase_options.dart, google-services.json, and GoogleService-Info.plist are client configuration, not secrets. They identify the project. They are designed to ship inside the app binary, where anyone can extract them in about ninety seconds regardless of what your repo does. Committing them is normal and correct. The thing that actually protects your data is Firestore rules + App Check — nothing else ever did.
The caveat that applies to Forge specifically. Client config being non-secret assumes the rules are doing their job. Forge's rules say allow read: if true on /users and App Check is off. In that combination the committed config is a live exposure — not because the keys leaked, but because the door is unlocked. Fix the rule; don't rotate the key. If the GitHub repo is public, treat it as an active incident rather than a hygiene item.

6. Escape hatch

Lock-in: HIGH — the highest in the entire stack, by a wide margin. Every other service on the map could be swapped in a weekend. This one could not.

  • What data lives only here — everything. Every users/ doc plus its events, goals, plans, channelPosts subcollections; every directThreads doc and message; every avatar in Storage; and every user's password. There is no second copy of any of it.
  • How to export Firestore — gcloud firestore export gs://BUCKET, a full dump in Firestore's own binary format. It restores to Firestore. It is a backup, not a migration path; converting it to anything else is a script you have to write.
  • How to export Auth — firebase auth:export users.json --format=json. This does include password hashes, in Firebase's scrypt variant with project-specific parameters. The Admin SDK's user listing does not include hashes.
  • What leaving actually costs — five distinct pieces of work:
    • Stand up Postgres/Supabase and hand-translate a schemaless document model that has one Dart model class (goal.dart) and passes untyped Map<String,dynamic> everywhere else.
    • Rewrite all 15 files in lib/services/, because they are free functions calling FirebaseAuth.instance.currentUser directly with no repository interface and no abstraction seam.
    • Rewrite every StreamBuilder in the UI, because live snapshot streams are the app's core interaction model and Postgres does not hand you those for free.
    • Either import scrypt hashes into a system that can verify Firebase's scrypt variant, or force a password reset on every user.
    • Re-encode the security model — firestore.rules is 206 lines that encode the entire friend-request handshake and would become server code.
  • What would make this cheaper — a repository interface between the UI and Firestore. Not worth building today for its own sake, but if it ever gets built for testability it halves the migration cost as a side effect.

Forge is not currently portable. About 16,300 lines depend on Firebase, and the D1 migration trigger has not fired.

7. Cost & scale checkpoints

Forge reads Firestore far harder than a normal app of its size. From the code: the calendar opens 2×(friends+gyms)+1 live listeners with N+1 fetches throughout; getIncomingFriendRequestsStream issues one .get() per thread on every snapshot; dmAllowedBetween() in the rules costs 3–4 billed reads per message write; social_page.dart still runs an orderBy + limit(10) query per joined gym on every page load for a tab that was deleted; friends, gyms, and members lists all do sequential N+1 fetches. Read cost here scales with friend count, not just user count.

  • ~10 users — this is roughly today. Nothing breaks.
  • ~100 users — plausibly crosses 50K reads/day on a busy day. Rough arithmetic: 100 users × 5 app opens/day × ~300 reads per calendar+feed open ≈ 150K reads/day → ~100K/day billed → ~$0.06/day ≈ $1.80/mo. Not scary. But the limit(100) search breaks here — search_service.dart fetches the first 100 user docs and filters in memory, so at 101 users people become silently unfindable. That is a functional failure, not a cost one, and it lands exactly at this checkpoint.
  • ~1,000 users — same arithmetic ×10: ~1.5M reads/day ≈ 45M reads/mo, minus ~1.5M free → ~43.5M × $0.06/100K ≈ $26/mo in reads alone, before writes, storage, or egress. This is precisely the D1 trigger ("Firestore read cost past $25/mo") — which means the read-amplification fixes are not optional hygiene, they are what keeps the architecture decision from being forced. Also at this scale: dmAllowedBetween()'s 3–4 get() calls sit close to Firestore's 10-get()-per-rule-evaluation ceiling, and 1 GiB of Firestore storage starts to be a real number.

Every figure in the middle column is arithmetic from the free-tier rates above applied to assumptions about usage, clearly labelled. Nobody has measured Forge's actual reads-per-session. Measure it before trusting it — the Firebase console's Usage tab gives the real number for free.

Extra seat cost$0 — Firebase bills project usage, not people

The actual riskNot cost — blast radius
  • Does the free tier allow a second member — quotas are shared across everyone using the project, not multiplied per person.
  • Permission model — grant Editor for a working teammate; keep Owner to one person so billing and deletion stay with him. Add via Firebase console → Project settings → Users and permissions.
  • The actual risk — anyone with Editor can deploy rules to production, and there is no staging project. A second person makes a separate forge-by-alpfit-dev project go from "nice to have" to "the thing that stops a teammate wiping real data."

What to do next

Open the Firebase console and answer one question: is forge-by-alpfit on Spark or Blaze? If Blaze, set a $5 budget alert before you close the tab. If Spark, avatar uploads are already broken and you have a bug to file.
  1. Then fix allow read: if true on /users and deploy — M1, Lock the doors.
  2. Then read app-check.html: App Check is the second lock on that same door, and it is free.
  3. Record the Firestore database location and Storage bucket region somewhere permanent — both are unchangeable and neither is written down anywhere in this repo.
