Firebase LOCKED

What this is: the setup, limits, secrets, and exit plan for Firebase — the single backend (Auth, Firestore, Storage, Hosting) that all 15,500 lines of Forge already run on.

What & why

Firebase is Forge's entire backend: Auth, Firestore, Storage, and Hosting are one Google Cloud project (forge-by-alpfit) that the Flutter client talks to directly, with no server layer in between. It already stores every user, event, goal, plan, and message the app has — this is not a proposal being evaluated, it is what the working app is built against today.

Alternative consideredWhy it lost
Supabase / PostgresListed as a future migration target only if Firestore query limits or cost actually bite — not expected before roughly 1,000 users. Not a day-one contender; Firebase predates this brief.
Custom API gateway abstracting storage from the client (from the "Ideas for Future" note)Textbook premature abstraction for a solo developer with zero real users. Deferred, no trigger met.

Why Firebase wins: it's already built on. Migrating now is a rewrite, not a swap, and nothing today forces that cost.

Blaze (first paid tier)Pay-as-you-go, requires a credit card on fileExact per-operation rates: verify at signup — not stated in the brief.

The Spark hard stop is a genuine advantage: there is no way to get an unexpected Firebase bill on the current plan. Adding Cloud Functions would force an upgrade to Blaze, which is exactly why the plan avoids Functions — account deletion and every other business rule run client-side instead.

Setup steps

  1. Google account signed in, Firebase console project created as forge-by-alpfit. The project id and default resource region are effectively permanent once real data exists — both are already locked in for this project.
  2. Authentication enabled with the Email/Password provider (no social sign-in providers are configured).
  3. Firestore Database created; firestore.rules and firestore.indexes.json deployed from the repo.
  4. Storage bucket forge-by-alpfit.firebasestorage.app enabled, used for avatar uploads at avatars/{uid}/profile.
  5. Hosting connected to build/web and deployed at least once already (unbranded).
  6. Android, iOS, and web registered as separate apps in the console. macOS and Windows are not real, independently-provisioned targets — they reuse iOS's and web's app ids respectively.
  7. Each registration generated a config file, placed at its platform-standard path and committed to the repo: google-services.json (Android), GoogleService-Info.plist (iOS), and the values compiled into lib/firebase_options.dart (all platforms).
  8. Verify: log in against the live project and confirm a matching users/{uid} document appears in the Firestore console.
Painful to change later: Android and iOS are still registered under the default com.example.* bundle ID. Fixing this before any store submission means re-registering the Firebase app and regenerating config — cheap now, expensive once real users and store reviews are involved (Milestone M2).

Firebase's client config is intentionally not treated as a secret: access is governed entirely by the security rules, not by hiding the API key, which is why it is safe to commit. No real Firebase secret exists in this project today, because Cloud Functions were deliberately not adopted — there is no server-side service-account key anywhere. If that ever changes, a service-account key must never be committed, and only a placeholder belongs in .env.example.

Escape hatch

HIGH lock-in

QuestionAnswer
Data that lives only hereEvery users/ doc and its events, goals, plans, channelPosts subcollections; every directThreads doc and message; all avatar files in Storage.
Firestore exportgcloud firestore export to a Cloud Storage bucket — a full data dump, not a live migration path.
Auth user exportThe Admin SDK can export user records, but password hashes are not included that way. firebase auth:export is the command that pulls hashes, in Firebase's scrypt format.
What migrating actually costsEither carry the scrypt hashes into a target auth system that can verify scrypt, or force every user to reset their password. Either way, the client talks directly to Firestore with no repository layer, so swapping backends means rewriting every service file, not changing a config value.

Lock-in is high, stated plainly rather than softened. It is still the right call today: 15,500 working lines already depend on it, there are effectively zero real users to migrate, and no rejected alternative has cleared its own stated trigger yet.

~1,000Plausibly exceeds the 50,000-reads/day ceiling depending on how often each user opens the feed and calendar. When it does, requests are refused (hard stop) until the quota resets, forcing a conscious Blaze upgrade decision rather than a surprise charge.
