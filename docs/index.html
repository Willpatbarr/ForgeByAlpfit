Project status, plan, and documentation index.

Where the project stands

Forge is a consumer mobile app (iOS + Android) for planning workouts socially around a physical gym — you join the community your gym hosts, add friends, and plan workouts together on a shared calendar. The thesis is that gym intimidation is a social problem, not a fitness one.
QuestionAnswer
Is it built? Substantially — 58 Dart files, ~16,300 lines, on live Firestore
Is it shippable? No — four blockers, worst first: a world-readable user table
What's the actual risk? Several screens look finished and aren't — see features
Who is it for, first? A beta at the BYU-I Rec Center — real external users
  • Built — auth, feed, calendar with recurrence, event CRUD, goals, plans, friend requests, gym channels and DMs all run on live Firestore.
  • Not shippable — the entire user table is world-readable without authentication, there are zero tests, both bundle IDs are com.example.*, and release builds are signed with debug keys.
  • The risk — a grep for TODO returns two hits, both in dead code, so the incompleteness is invisible to tooling and only visible by reading.
  • Who for — real external users are what make account deletion, moderation and a privacy policy real work rather than paperwork.
Next: restrict /users reads in firestore.rules to authenticated users. The current allow read: if true exposes user data; see Milestone 1.

The plan

Six milestones in dependency order. Full detail, definitions of done, and risks: 04-plan/milestones.html.

#MilestoneTierGoal
M1 Lock the doors T0 Close the security holes, fix the crash path, stand up the first tests. Nothing ships before this.
M2 Make "done" true T0 Kill the hollow surfaces so "the app works" becomes a true sentence.
M3 Ship to a device that isn't his T1 Real bundle IDs, real signing, store accounts, TestFlight and Play internal testing.
M4 Beta-ready T1 Account deletion, report/block/moderation, privacy policy, push, gym approval.
M5 The Rec Center beta T1 Actually run it — onboarding, seeded content, a feedback loop, and the success metric.
M6 When it hurts T2 Scale and cost work, each gated behind a named threshold. Do not start early.

T0 Now = needed to build or run at all · T1 Before first real user = needed the moment someone who isn't William touches it · T2 When it hurts = only past a named threshold.

Needs your eye

Four PROPOSED calls are genuine coin-flips, not conclusions. They were decided one way to keep the plan coherent, and each is where your judgement should override it. Full context and the rest of the decision log: 01-product/decisions.html.
  • D5 — keep setState + StreamBuilder; no Riverpod migration. The most reversible-but-expensive call in the plan. Riverpod was recommended twice in old docs and adopted zero times; a working app doesn't need rewriting for a solo dev. Milestone 2 is the evidence that would reopen it.
  • D7 — rename forge_senior_project_version/ to app/. Cheap now, annoying later. The directory name is a daily reminder of a finished class.
  • The milestone table itself. It is a first pass built from the code, deliberately put at the top of the plan page so you can rewrite the whole thing in one edit.
  • Whether M6 exists at all. Every item in it is gated behind a threshold that has not fired. Cutting it is a defensible call.
